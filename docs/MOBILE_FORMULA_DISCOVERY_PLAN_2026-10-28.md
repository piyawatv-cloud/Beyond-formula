## เป้าหมายและขอบเขต

สร้างระบบสำหรับมือถือแยกจากหน้าระบบเดิม แต่ใช้ข้อมูลและกระบวนการ R&D เดิมร่วมกัน ครอบคลุมทุกบทบาท โดยทดลองบนข้อมูลจำลองและพื้นที่ทดสอบก่อนเชื่อมฐานข้อมูลปัจจุบัน รายการนี้เป็นแผน ไม่อนุญาตให้แก้ฐานข้อมูล production หรือเปลี่ยนสิทธิ์

Task ID / Issue ID: ยังไม่มี · เจ้าของงาน / ผู้ตรวจ: รอยืนยัน · ตำแหน่ง repository ใหม่: รอยืนยัน · ความเสี่ยง: สูงเมื่อเกี่ยวข้องกับข้อมูล สิทธิ์ การซิงก์ และระบบจริง

## วิธีสำรวจและข้อจำกัด

- ตรวจ `AGENTS.md`, `CLAUDE.md`, `README.md`, `index.html`, `supabase/schema.sql` และชุดทดสอบในเครื่อง บนสาขา `codex/job-alerts-chat-save` ที่ HEAD `a3f4859` โดยมีการแก้ไขค้างอยู่ ผลนี้จึงอ้างถึง **สำเนาการทำงาน** ไม่ยืนยันว่าเหมือนรุ่นที่เผยแพร่
- เปิดสำเนาชั่วคราวที่ตัดค่าการเชื่อมต่อ Supabase และบังคับห้ามเชื่อมเครือข่าย สร้างผู้ใช้และงานจำลอง 2 รายการ ตรวจหน้าหลักทุกบทบาทบนจอ 390 × 844; ตรวจฟอร์ม Customer Data ของ Sales, รายละเอียดงานของ Sales และ PD และ Activities log ของ Admin
- สำเนาดังกล่าวอยู่ในโหมดเครื่องเดียว ไม่ใช่โหมดเซิร์ฟเวอร์ บัญชีเป็นข้อมูลจำลองที่ใส่เพื่อดูหน้าจอ ไม่ใช่การตรวจการเข้าสู่ระบบจริง ไม่ใช้ตรวจสิทธิ์ฐานข้อมูล
- การเปิดห้องแชตและอนุมัติถูกล็อกเพราะต้องยืนยันใบงานจากเซิร์ฟเวอร์ จึงยังไม่ได้เดิน workflow แชต/อนุมัติครบตั้งแต่ต้นจนจบ และยังไม่ได้ทดสอบการส่งออก การนำเข้า การสร้าง/แก้/ปิดงานจริง การเข้าถึงผ่านคีย์บอร์ดหรือตัวอ่านหน้าจอ และจอขนาดอื่น ทุกบทบาทในตารางเป็นการสำรวจหน้าหลักและอ่านโค้ด ไม่ใช่ผลทดสอบครบทุกการกระทำ
- รัน browser harness จากสำเนาแยกพร้อมบริการจำลอง รายงานภายในมี 80 ผ่าน 0 ล้มเหลว แต่คำสั่ง `node harness.js` ออกด้วยสถานะ 1 จึง **ไม่ถือว่าชุดทดสอบผ่าน** จนกว่าจะวิเคราะห์ผลของ browser/harness เพิ่ม ไม่ได้รัน SQL tests หรือเชื่อมฐานข้อมูลจริง

## ภาพ workflow และสิทธิ์ที่พบ

| บทบาท | สิ่งที่โค้ดระบุ | การตรวจหน้าจอรอบนี้ |
|---|---|---|
| Admin | ทุกความสามารถ รวมประวัติ จัดการผู้ใช้ ลบ/ปิดงาน | หน้าหลัก รายละเอียดผ่านตัวอย่างร่วม และหน้าประวัติ; โหมดเซิร์ฟเวอร์ให้เจ้าของระบบจัดการบัญชี |
| Sales | สร้าง/แก้ข้อมูลงาน แชต อนุมัติ Sales ปิดงาน; หน้าจอกรองงานที่ตนสร้าง | หน้าหลัก ฟอร์ม และรายละเอียดงานของตน |
| PD | แก้สูตรและบางหมวดข้อมูล แชต อนุมัติ PD | หน้าหลักและรายละเอียด; ไม่ได้ทดสอบแก้สูตร |
| RA | แชตและอนุมัติ RA | หน้าหลัก; แชต/อนุมัติยังไม่ทดสอบ |
| RD | แชตและอนุมัติ RD | หน้าหลัก; แชต/อนุมัติยังไม่ทดสอบ |
| OPC | สร้าง/แก้ข้อมูลงาน แชต ส่งออก และปิดงาน | หน้าหลัก; การดำเนินการยังไม่ทดสอบ |
| MKT | สร้าง/แก้ข้อมูลงานและแชต | หน้าหลัก; การดำเนินการยังไม่ทดสอบ |
| Purchasing | แชต | หน้าหลัก; การดำเนินการยังไม่ทดสอบ |

สิทธิ์ในตารางสรุปจาก `index.html` ส่วนสิทธิ์แท้จริงต้องตรวจการทำงานร่วมกับฐานข้อมูลและผู้รับผิดชอบ ไม่ใช่ถือว่าปุ่มที่แสดงเป็นหลักฐานความปลอดภัย

กระบวนการหลักตามโค้ด: เข้าระบบ → รายการและค้นหางาน → สร้าง/แก้บรีฟและสูตร → ยืนยันการบันทึก → แชต/แก้ข้อมูล/อนุมัติ PD, RA, RD, Sales → ส่งออก/ปิด/เปิดงาน; การนำเข้า การพิมพ์ ประวัติ และการจัดการสมาชิกต้องตรวจแยกตามบทบาทและโหมดระบบ

## ข้อค้นพบและความเสี่ยง

1. **สูง — สิทธิ์การอ่านต้องยืนยัน:** `visibleRecords()` ใน `index.html` กรอง Sales เฉพาะผู้สร้าง แต่ `records_member_select` ใน `supabase/schema.sql` อนุญาตสมาชิกที่ active อ่าน record; ยังไม่ทราบสิทธิ์ที่ติดตั้งจริงและเจตนาของเจ้าของงาน ต้องตรวจด้วยบัญชีจำลองผ่านบริการโดยตรง ไม่ขยายสิทธิ์เพื่อให้แอปใหม่ทำงาน
2. **สูง — แก้พร้อมกันและรหัสซ้ำ:** `sbSaveRecords()` ส่ง record แบบทั้งชุด และมีตัวนับรหัสร่วมใน `fs_meta` ต้องพิสูจน์กรณีสองช่องทางแก้ข้อมูลหรือสร้างงานพร้อมกัน รวมทั้งกู้คืนเมื่อเครือข่ายขาด ก่อนอนุญาตให้เขียนข้อมูลจริง; ผลเสียเป็นความเสี่ยงที่ต้องพิสูจน์ ไม่ใช่ข้อสรุปว่าเกิดแล้ว
3. **สูง — ความสอดคล้องแชตและอนุมัติ:** โค้ดใช้ `fs_append_chat_event` และมีเงื่อนไขยืนยันใบงานก่อนแชต; การแก้สูตรทำให้อนุมัติเดิมใช้ไม่ได้ตามชุดทดสอบ ระบบใหม่ต้องรักษาพฤติกรรมและทดสอบข้ามสองระบบ
4. **กลาง — หน้าจอมือถือ:** ที่ 390 × 844 เมนูและการ์ดสรุปหลายใบกินพื้นที่ก่อนถึงรายการงาน ฟอร์มมีหลายหมวดและตารางสารหลายคอลัมน์ ควรตรวจการเลื่อนและทำงานจริงก่อนกำหนดวิธีแก้
5. **ยังไม่ยืนยัน — แหล่งข้อมูลจริง:** โค้ดและเอกสารระบุ Supabase/PostgreSQL แต่ไม่ได้ตรวจ deployment, schema, grants, accounts, backup หรือฐานข้อมูลจริง; `docs/architecture/CURRENT_STATE.md` เป็น baseline เก่าลงวันที่ 18 ก.ย. ไม่ใช่หลักฐานสภาพปัจจุบัน

## แนวทางออกแบบ: TPS และ ISO/IEC 33000

Toyota Production System เน้นลดความสูญเปล่าและแสดงความผิดปกติให้เห็น; นำมาปรับกับงานหน้าจอโดยไม่อ้างว่าเป็นข้อกำหนดมาตรฐานหน้าจอ:

- ลดการสลับหน้าและกรอกข้อมูลซ้ำ: เปิดงานแล้วเห็นข้อมูลที่ใช้ตัดสินใจและการกระทำที่บทบาททำได้ในบริบทเดียว
- แสดงเฉพาะสิ่งที่จำเป็นต่อขั้นนั้นก่อน แต่เปิดดูข้อมูลสำคัญเพิ่มเติมได้ ไม่ซ่อนข้อมูลที่จำเป็นต่อความปลอดภัยหรือการอนุมัติ
- เห็นงานค้าง สิ่งที่ต้องทำต่อ และปัญหาจากข้อความพร้อมวิธีแก้ ไม่ใช้สีอย่างเดียว แยกกำลังส่ง/ยืนยันแล้ว/ส่งไม่สำเร็จ
- ป้องกันความผิดพลาด: ตรวจข้อมูลก่อนส่ง ป้องกันกดซ้ำ แจ้งความขัดแย้ง ไม่แสดงว่าบันทึกสำเร็จก่อนยืนยัน
- ใช้มาตรฐานเดียวกันในทุกหน้าสำหรับการบันทึก ย้อนกลับ สถานะ และการแก้ข้อผิดพลาด แล้ววัดเวลา ขั้นตอน และข้อผิดพลาดเพื่อปรับปรุงร่วมกับผู้ใช้

ISO/IEC 33000 เป็นชุดมาตรฐานกรอบประเมินกระบวนการ ไม่ใช่มาตรฐานรับรองว่าหน้าจอสะอาดหรือใช้มือเดียวได้ ให้ประยุกต์โดยกำหนดกระบวนการ เจ้าของ ผลลัพธ์ เกณฑ์ หลักฐาน และทบทวนผลอย่างเป็นระบบ เช่น การเก็บข้อกำหนด → ออกแบบ → ทดสอบตามบทบาท → ตรวจผล → ปรับปรุง ทั้งนี้ยังไม่ได้ทำการประเมินอย่างเป็นทางการ และห้ามกล่าวอ้างการรับรองหรือระดับความสามารถจากแผนนี้

อ้างอิง: https://global.toyota/en/company/vision-and-philosophy/production-system/ และ https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiec-33000-family.html

## ข้อเสนอหน้าจอมือถือ

- ลำดับหลัก: งานของฉัน/ค้นหา → รายละเอียดงาน → การกระทำในงาน → ผลที่ยืนยันแล้ว โดยยังเข้าถึงงานทั้งหมดตามสิทธิ์จริงได้
- แต่ละจอมีหัวข้อ รหัสงาน สถานะ และการกระทำหลักที่มองเห็นได้; รายละเอียดรองแบ่งหมวดเปิดเพิ่ม ตารางสูตรปรับเป็นรายการอ่านง่ายโดยคงชื่อสาร ปริมาณ หน่วย และข้อมูลที่จำเป็นครบ
- วางปุ่มหลักในบริเวณที่เอื้อมถึงได้ แต่ทดสอบกับผู้ถนัดซ้าย/ขวา ขนาดจอและแป้นพิมพ์จริง ไม่สมมติว่าตำแหน่งเดียวเหมาะกับทุกคน ปุ่มรองและรายการที่สำคัญยังเข้าถึงได้
- ธีมสว่าง ขาว–ส้ม–น้ำเงิน และมืด ดำ–ส้ม–เทา ตามเอกสารต้นทาง ทดสอบความต่างของสี ข้อความและการโฟกัสจริง; สถานะมีข้อความหรือสัญลักษณ์ร่วมด้วย
- หลีกเลี่ยงแนวนอนในงานหลัก ตรวจตัวอักษรไทยเมื่อขยาย ข้อความยาว ปุ่มสัมผัส ความสูงแป้นพิมพ์ การเลื่อน และการใช้งานมือเดียว; เป้าหมายขนาดปุ่มประมาณ 44 × 44 CSS pixels ตามแนวทางออกแบบของโครงการ ไม่ใช่ข้ออ้างว่าผ่านทุกมาตรฐาน

## แผนและหลักฐานตรวจรับ

1. **ยืนยัน baseline และสำรวจให้ครบ** — เจ้าของงานระบุรุ่นที่อนุมัติและขอบเขต repo; เดินหน้าจอทุกบทบาทกับข้อมูลจำลองที่มีทั้งงานเปิด/ปิด สูตรหลายรายการ แชตและสถานะอนุมัติ บันทึกสิ่งที่ทำได้และทำไม่ได้; ตรวจทั้งจอเล็ก/ใหญ่และมือซ้าย/ขวา
2. **กำหนดกติกาและแหล่งข้อมูล** — ตรวจสิทธิ์จริงโดยใช้พื้นที่ทดสอบ แยกสิทธิ์ UI กับ database ยืนยันรูปแบบข้อมูล รหัสงาน ประวัติ แชต ข้อกำหนด offline และเจ้าของข้อมูล จัดตาราง role × operation × allow/deny และให้เจ้าของงานยืนยัน
3. **เปรียบเทียบสถาปัตยกรรม** — เว็บมือถือแยก / แอปติดตั้ง โดยเปรียบเทียบอุปกรณ์ offline การดูแล ความปลอดภัย ต้นทุน และการเข้าถึง ผู้ใช้เลือก; ข้อเสนอเริ่มต้นเว็บมือถือแยก ใช้บริการยืนยันตัวตนและช่องทางที่มีอยู่ถ้าทดสอบได้ปลอดภัย ไม่ต่อฐานข้อมูลด้วยรหัสผ่านที่ฝังในแอป
4. **ออกแบบและทดสอบต้นแบบ** — สร้างแบบด้วยข้อมูลจำลองทั้งสองธีม ครอบคลุมทุก workflow แต่ละบทบาทและข้อผิดพลาด ให้ผู้ใช้จริงทดลองมือเดียว กำหนดวิธีวัดและค่าฐานก่อน เปรียบเทียบเวลา จำนวนขั้นตอน การกรอกซ้ำ ความผิดพลาด และอัตราทำงานสำเร็จโดยไม่ช่วย
5. **ตรวจความพร้อมการใช้ข้อมูลร่วม** — สร้างชุดทดสอบ server จำลอง/พื้นที่ทดสอบที่ระบุชัด; ทดสอบสิทธิ์บวก/ลบ แก้พร้อมกัน/ข้อมูลเก่า รหัสซ้ำ ส่งซ้ำ เน็ตหลุด สลับบัญชี สิทธิ์ถูกถอน อ่านกลับ แชต การอนุมัติและประวัติข้ามสองระบบ หยุดการเขียนจริงถ้าความปลอดภัยหรือความสอดคล้องไม่ผ่าน
6. **พัฒนาเป็นช่วง** — สร้างระบบแยกบน feature branch ใน repo ที่อนุมัติ เริ่มเข้าระบบและรายการงาน ต่อด้วยบรีฟ/สูตร แชต/อนุมัติ ปิดงาน ส่งออก และงานดูแล ตามลำดับที่ owner เลือก ทุกช่วงมี automated checks และตัวอย่างที่ตรวจได้; เก็บ workflow เดิมครบก่อนสรุปว่าทดแทนได้
7. **ทดสอบรับและเผยแพร่** — ทดสอบกับผู้ใช้ทุกบทบาทและอุปกรณ์เป้าหมาย ตรวจความเข้ากันได้กับระบบเก่า ให้ผู้ตรวจอิสระพิจารณาการเปลี่ยนแปลงสำคัญ จัดทำ backup/rollback และขออนุมัติ deployment ตาม governance; ตรวจสุขภาพและผลหลังเผยแพร่

## เรื่องที่ต้องตัดสินใจ

- ยืนยันว่า PostgreSQL เป้าหมายคือ Supabase ชุดปัจจุบัน และระบุ test/staging ที่ปลอดภัย
- เจ้าของงานกำหนดขอบเขตข้อมูลที่ Sales และบทบาทอื่นควรมองเห็น
- เลือกที่เก็บระบบใหม่ อุปกรณ์เป้าหมาย การติดตั้ง และความจำเป็น offline
- ตกลงเกณฑ์ความสำเร็จและกลุ่มผู้ทดสอบ; กำหนด owner/reviewer ก่อนทำรายการสำคัญ

## ผลกระทบและการย้อนกลับ

รอบสำรวจนี้ไม่แก้โค้ด ระบบ ข้อมูลจริง สิทธิ์ ฐานข้อมูล หรือ dependencies; เอกสารนี้เป็นไฟล์ใหม่ ลบไฟล์นี้เพื่อย้อนกลับเอกสารได้ ไม่มี PR ไม่มี deployment และไม่มี business acceptance. แผนระบบแยกต้องรักษาเส้นทางกลับสู่ระบบเดิมและกำหนดแผนกู้ข้อมูล/แก้ความขัดแย้งก่อนเชื่อมใช้งานจริง
