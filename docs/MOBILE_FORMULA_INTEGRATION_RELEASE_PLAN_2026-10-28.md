# Formula Studio Mobile — แผนเชื่อมระบบ แจ้งเตือน ติดตั้ง และอัปเดต

สถานะ: ข้อเสนอเพื่อทบทวน ไม่ใช่การอนุมัติให้เชื่อมข้อมูลจริง เปลี่ยนสิทธิ์ สร้างบริการ เสียค่าใช้จ่าย หรือเผยแพร่ · วันที่ 28 ต.ค. 2026

## เป้าหมาย

ระบบมือถือแยกใช้ workflow Formula Studio เดิมและข้อมูลแหล่งเดียวกัน รองรับ Android, iOS, Windows และ macOS พร้อมแจ้งเตือนข้อความ/งานอัปเดต และมีวิธีอัปเดตที่ตรวจสอบและย้อนกลับได้ ไม่สร้าง master data หรือกฎธุรกิจชุดใหม่โดยไม่มีเจ้าของและแนวทางควบคุม

## สภาพที่ตรวจพบ / สิ่งที่ยังไม่ยืนยัน

- `index.html`, `CLAUDE.md` และ `supabase/schema.sql` ในสำเนา repository ระบุ Supabase Auth และ PostgreSQL, ตาราง `fs_records`, `fs_chats`, `fs_chat_events`, `fs_chat_reads`, `fs_memberships`, `fs_activities`, `fs_meta`; ข้อมูล record เก็บรูป JSON เดิม แชตใช้ `fs_append_chat_event` และ `fs_mark_chat_seen` ใน secure mode
- ยังไม่ได้ตรวจรุ่นที่ deploy อยู่, schema/grants/policies จริง, production data, บัญชีทดสอบ หรือความเป็นเจ้าของข้อมูลและความสอดคล้องของสองระบบ
- การอ่าน record ใน schema ที่ตรวจให้ active member อ่าน ขณะที่ UI กรอง Sales: ต้องให้เจ้าของงานยืนยันขอบเขตข้อมูลและทดสอบการเรียกบริการโดยตรงก่อนเปิดช่องทางใหม่
- `sbSaveRecords` ส่ง record แบบทั้งชุด และมี counter ผ่าน `fs_meta`; ยังไม่มีหลักฐานว่าการแก้/สร้างพร้อมกันจากสองระบบจะปลอดภัยครบทุกกรณี
- มี Android SDK บางส่วนในเครื่อง; `xcodebuild -version` ระบุว่ามีเพียง Command Line Tools ไม่มี Xcode เต็ม จึงยังสร้าง/ทดสอบ iOS ไม่ได้ การมี SDK บางส่วนไม่ใช่หลักฐานว่าชุด build Android พร้อม
- หน้าทดลอง `mobile-preview` ใช้ข้อมูลจำลองในหน่วยความจำ ไม่เชื่อมบริการจริง ไม่มี push เมื่อปิดแอป และไม่ได้สร้าง APK/แพ็กเกจติดตั้ง

## สถาปัตยกรรมที่เสนอ

```text
มือถือ / คอมพิวเตอร์
  → เข้าสู่ระบบและใช้ session ของผู้ใช้จริง
  → บริการเดิมหรือบริการกลางที่อนุมัติ
  → ตรวจสิทธิ์และความถูกต้องฝั่งบริการ/ฐานข้อมูล
  → PostgreSQL แหล่งเดียว + ประวัติการทำรายการ
  → เหตุการณ์ที่ได้รับยืนยัน → บริการแจ้งเตือน → อุปกรณ์ที่ได้รับอนุญาต
```

แนวทางเริ่มต้น: สำรวจว่าใช้ Supabase Auth และ Data API/RPC ที่มีอยู่ได้ตรงตามสิทธิ์และสัญญาข้อมูลหรือไม่ โดยผู้ใช้มีสิทธิ์จริงของตนเท่านั้น ห้ามใส่รหัสผ่านฐานข้อมูลหรือ service-role key ในแอป หากสิทธิ์ การทำรายการ หรือการป้องกันแก้ทับไม่เพียงพอ ให้เสนอการแก้บริการ/ฐานข้อมูลแยกเป็น Critical Change พร้อม migration ที่เข้ากันได้และทดสอบก่อน ไม่ใช้ UI กรองแทนสิทธิ์จริง

ตารางตรวจให้เสร็จก่อนเขียนจริง: วิธี login/logout/ถอนสิทธิ์; role × read/create/edit/formula/approve/chat/close/export; ใบงานเก่า; รหัสงาน; สถานะยืนยันใบงานก่อนแชต; chat append/read; approval reset; activity; การส่งซ้ำ; การแก้พร้อมกัน; timeout และ read-back. ต้องทดสอบทั้งจากเว็บเดิมไปมือถือและมือถือไปเว็บเดิม

### การอ่านงานพร้อมอนุมัติ — ข้อเสนอรอทบทวน

การทดลอง `mobile-preview/integration/current-read-e2e.extra.mjs` พบว่าการอ่านงานและอนุมัติผ่านคำขอแยกอาจรวมสถานะคนละช่วงเวลา ส่วน SQL คำสั่งเดียวใน PostgreSQL ชั่วคราวอ่านข้อมูลสองส่วนจากภาพเดียวกันได้แม้มีการถอนอนุมัติระหว่างอ่าน ข้อเสนอสองทางคือ (1) ให้บริการเดิมที่ได้รับอนุมัติอ่านงานและอนุมัติด้วยคำสั่งเดียว แล้วตรวจตัวตน/สิทธิ์และส่งเฉพาะข้อมูลที่บัญชีนั้นมีสิทธิ์เห็น หรือ (2) อ่านแยกโดยมีหลักฐานรุ่นข้อมูลที่ตรวจร่วมกันได้และปฏิเสธเมื่อไม่สอดคล้อง ทางแรกสั้นกว่าเมื่อมีช่องบริการที่เหมาะสม ทางที่สองต้องพิสูจน์การเปลี่ยนและย้อนสถานะระหว่างอ่าน ไม่ควรสมมติว่าการอ่านซ้ำอย่างเดียวรับประกันได้

ไม่ว่าจะเลือกทางใด ผลอ่านเป็นสถานะ ณ เวลาหนึ่ง ไม่ใช่การล็อกหรือหลักฐานว่าสถานะยังไม่เปลี่ยนเมื่อผู้ใช้กดอนุมัติ/บันทึก ต้องตรวจข้อมูลตั้งต้นอีกครั้งฝั่งบริการก่อนเขียน และทดสอบบัญชีที่ไม่มีสิทธิ์ session เปลี่ยน ข้อมูลหาย บริการล้มเหลว และการเปลี่ยนพร้อมกัน การทดลอง SQL ยังไม่ใช่ endpoint ที่แอปใช้ได้ การเพิ่ม endpoint หรือเปลี่ยนสิทธิ์/ฐานข้อมูลต้องผ่าน governance และการทบทวนก่อนนำไปใช้

ผลตรวจเส้นทางเดิมเพิ่มเติม: ในชุด gateway commit `91d5fde5a17abf70d9ac5764b6b31529d69f913c` กับ PostgreSQL และบัญชีจำลอง คำขออ่าน `fs_records` โดยขอแนบ `fs_approvals(part,data)` ได้ HTTP 400 ขณะที่การอ่านงานแบบปกติด้วยบัญชีเดียวกันได้ HTTP 200 และพบงาน ชุดทดสอบรวมผ่าน 16/16 หลักฐานนี้จำกัดอยู่ที่รูปแบบคำขอและรุ่นที่ระบุ ไม่พิสูจน์ว่าไม่มีช่องทางอ่านพร้อมกันอื่นในระบบจริง และไม่ให้ผ่อนการตรวจสิทธิ์เพื่อทำให้คำขอผ่าน

ตรวจบริการที่มีอยู่ `__formula/scoped-chat-history` เพิ่ม: ในสภาพจำลอง บัญชี Sales อ่านห้องและข้อความของงานตนได้ ผู้ไม่เข้าสู่ระบบถูกปฏิเสธ และการขอประวัติงานของผู้สร้างอีกคนได้ 403 แต่ผลตอบไม่ได้รวมรายการงานหรืออนุมัติ จึงเป็นทางเลือกสำหรับประวัติแชตที่ควรพิจารณา ไม่ใช่คำตอบสำหรับภาพรวมงานพร้อมอนุมัติ การทดสอบรวมผ่าน 17/17; ยังไม่ยืนยันสิทธิ์ในระบบจริงหรือครบทุกบทบาท และต้องทดสอบ session/ขอบเขตข้อมูลในระบบทดสอบที่อนุมัติก่อนเชื่อม

## แจ้งเตือนจริงแม้ปิดแอป

1. ระบุเหตุการณ์ที่ต้องแจ้งและผู้มีสิทธิ์รับจากกฎที่เจ้าของงานยืนยัน เช่น ข้อความใหม่และการเปลี่ยนแปลงงาน ไม่เดาผู้รับหรือส่งหาทุกคน
2. ให้บริการที่เชื่อถือได้สร้างเหตุการณ์จากการบันทึกที่ยืนยันแล้ว พร้อมรหัสกันส่งซ้ำ และคิวส่งที่ทนต่อความล้มเหลว; อ่านสถานะงาน/ข้อความจริงเมื่อเปิด ไม่ใช้ข้อความแจ้งเตือนเป็นหลักฐานว่าบันทึกสำเร็จ
3. จัดเก็บ registration ของอุปกรณ์อย่างปลอดภัยและจำกัดผู้เข้าถึง จัดการออกจากระบบ เปลี่ยนบัญชี ถอนสิทธิ์ token หมดอายุ และอุปกรณ์ที่ถูกปิดการใช้งาน
4. ใช้ผู้ให้บริการ push ตามแพลตฟอร์ม เช่น Android ผ่าน FCM และ Apple ผ่าน APNs หรือ Web Push เมื่อเลือกเว็บที่ติดตั้งได้; การแสดงผลขึ้นกับการอนุญาตและข้อจำกัดของระบบปฏิบัติการ ห้ามรับประกันส่งถึงทุกครั้ง
5. ค่าเริ่มต้นที่เสนอสำหรับหน้าจอล็อกคือข้อความทั่วไป เช่น “มีข้อความใหม่ใน Formula Studio” โดยไม่เผยรายละเอียดลูกค้า/สูตร; แตะแล้วเข้าสู่ระบบและตรวจสิทธิ์อีกครั้งก่อนเปิดงาน เจ้าของงานต้องตัดสินใจว่าจะอนุญาตข้อความตัวอย่างบนหน้าจอล็อกหรือไม่
6. ทดสอบ foreground/background/ปิดแอป สิทธิ์แจ้งเตือนถูกปิด การสลับบัญชี เน็ตหลุด ส่งซ้ำ การกดแจ้งเตือนเก่า ความเป็นส่วนตัว การส่งถึงอุปกรณ์ที่ถอนสิทธิ์แล้ว และการกู้จากบริการล่ม ด้วยอุปกรณ์จริงและบัญชีจำลอง

Push ของเว็บบน iOS/iPadOS ต้องเพิ่มเว็บแอปไปหน้า Home Screen และขออนุญาตจากการกระทำของผู้ใช้ตามความสามารถและเวอร์ชันที่รองรับ; Android 13+ มีสิทธิ์การแจ้งเตือนที่ต้องขอ. อ้างอิง https://webkit.org/blog/13878/ และ https://developer.android.com/develop/ui/compose/notifications/notification-permission

## ตัวเลือกติดตั้ง

| วิธี | Android | iPhone / iPad | Windows / macOS | ข้อดีและข้อจำกัด |
|---|---|---|---|---|
| เว็บติดตั้งได้ (PWA) | เปิดเว็บ/เพิ่มไอคอน; ไม่ใช่ APK | เพิ่มไป Home Screen บนระบบที่รองรับ | เปิดเว็บหรือติดตั้งผ่าน browser ที่รองรับ | แก้และแจกเวอร์ชันได้ง่าย; ต้องทดสอบ push และ offline ในเครื่องเป้าหมายตามข้อจำกัดแต่ละ OS |
| แอปข้ามแพลตฟอร์ม | APK/AAB | แอป iOS ผ่านช่องทางที่ Apple อนุญาต | แอป Windows/macOS แยกแพ็กเกจ | ติดตั้งแบบแอปและใช้ความสามารถระบบได้ แต่มีเครื่องมือ บัญชีนักพัฒนา การลงนาม และบำรุงรักษาเพิ่ม |
| เว็บสำหรับ PC/Mac + แอป Android/iOS | APK/AAB | แอป iOS | ใช้เว็บ | ลดแพ็กเกจ desktop แต่ต้องดูแลแอปมือถือและเว็บให้ตรงกัน |

ข้อเสนอสำหรับการตัดสินใจ: เริ่มทดสอบ PWA กับ workflow และ push บนอุปกรณ์เป้าหมาย แล้วสร้างแพ็กเกจ Android เมื่อจำเป็นต้องมี APK; หากจำเป็นต้องใช้ native iOS หรือ desktop ให้เลือกเทคโนโลยีและขอบเขตแยกหลังทดลอง ไม่ยืนยันว่า PWA ทดแทนแอป native ได้ทุกความต้องการ APK ไม่ใช่รูปแบบติดตั้ง iOS, Windows หรือ macOS

## อัปเดตเวอร์ชันและ patch

- **Android:** พิจารณา Play managed update เมื่อเหมาะสม หรือช่องทางแจกภายในที่ได้รับอนุมัติ หากแจก APK เองให้เผยแพร่แพ็กเกจใหม่ที่ลงนามถูกต้อง ตรวจ application ID และ version code โดยใช้ช่องทางที่อุปกรณ์อนุญาต Google Play อาจใช้เทคนิค patch เพื่อลดข้อมูลดาวน์โหลด; ไม่สร้างตัวอัปเดตโค้ดเองโดยไม่มีการทบทวนความปลอดภัย การส่งเฉพาะ delta ให้ผู้ใช้ทำได้หรือไม่ขึ้นกับช่องทางที่เลือก ไม่ถือว่ามีแล้ว
- **iOS:** ใช้ช่องทางแจกและอัปเดตที่ Apple อนุญาต เช่น App Store หรือช่องทางองค์กรที่เหมาะสม โดยตรวจข้อกำหนดปัจจุบัน; ไม่สมมติว่าสามารถส่ง patch ที่เปลี่ยนโค้ดแอปเองโดยข้ามกระบวนการได้
- **PWA:** อัปเดตไฟล์เว็บและ service worker ผ่าน release ที่อนุมัติ ออกแบบแจ้งเตือนเวอร์ชัน รอจังหวะปลอดภัยก่อนรีโหลด ไม่ทิ้งข้อมูลร่าง และดูแล cache ให้เข้ากันกับ API เวอร์ชันเก่า
- **Windows/macOS native:** เลือกตัวติดตั้งและช่องทางอัปเดตที่อนุญาต แยกตามแพลตฟอร์ม ลงนามและตรวจสอบความถูกต้อง; หากใช้ Mac App Store ให้ปฏิบัติตามข้อกำหนดของช่องทางนั้น
- **ทุกช่องทาง:** กำหนด version, minimum compatible API/schema, immutable artifact, signature/checksum, release notes, rollout ทดสอบ/จำกัดกลุ่ม, ความพร้อม backup, monitoring และ rollback target; ป้องกันการ downgrade ที่กระทบข้อมูล และทดสอบอัปเดตขณะมีร่าง/เน็ตหลุด/พื้นที่ไม่พอ

อ้างอิง Android update: https://developer.android.com/google/play/app-updates และ Apple guideline: https://developer.apple.com/app-store/review/guidelines/

## ลำดับดำเนินงานและเกณฑ์ผ่าน

1. **ระบุ baseline และผู้รับผิดชอบ:** ยืนยัน repo/commit ที่ deploy จริง จุดเชื่อม Supabase, staging แยก, เจ้าของข้อมูล, owner/reviewer, การเข้าถึงและวิธีแจกแอป — ผลเป็นขอบเขตตรวจสอบได้ ไม่ดึงข้อมูลจริงมาใช้ทดสอบ
2. **ปิดช่องว่าง workflow:** เปรียบเทียบฟอร์มและบทบาทกับระบบเดิม; ทดสอบนำเข้า/ส่งออก สูตร/อย. แชต การอนุมัติ ประวัติ ปิด/เปิดงาน ด้วยข้อมูลจำลอง และบันทึกสิ่งที่ยังไม่รองรับ
3. **สร้างบริการจำลองหรือ staging ที่แยกจริง:** ทดสอบสองช่องทางกับฐานข้อมูลทดสอบ แก้พร้อมกัน รหัสซ้ำ สิทธิ์ถูกถอน/ข้ามบทบาท การส่งซ้ำ timeout และอ่านกลับ โดยห้ามลดระดับการตรวจสิทธิ์
4. **ออกแบบและทดสอบ notification:** ให้ owner ยืนยันผู้รับ ประเภทข้อความ ระยะเวลาจัดเก็บและความเป็นส่วนตัว; ทดสอบ push ด้วยอุปกรณ์จริงทั้งขณะเปิดและปิดแอป รวมถึงกรณีปฏิเสธสิทธิ์/อุปกรณ์ถูกถอน
5. **เลือกแพลตฟอร์มและช่องทางแจก:** วัด PWA เทียบกับแพ็กเกจ native ตาม workflow, offline, push, ต้นทุน, เวลา และการดูแล พร้อมยืนยันอุปกรณ์รุ่นขั้นต่ำและผู้มีสิทธิ์ติดตั้ง
6. **เตรียม release:** แยก Critical Change สร้าง PR และ independent review ตาม governance; ตรวจ signing, backup/rollback, UAT, staged rollout และผู้รับผิดชอบ ก่อนอนุญาต deploy; ตรวจผลหลังใช้งานจริง

## ประเด็นให้ System Owner ตัดสินใจ

- PostgreSQL เป้าหมายและ staging ที่อนุญาต; สิทธิ์ Sales ในระดับฐานข้อมูล
- รายชื่อผู้รับและเนื้อหาแจ้งเตือน รวมถึงข้อมูลที่อนุญาตให้แสดงบนหน้าจอล็อก
- Android จะแจกผ่าน Play หรือระบบภายใน; iOS ผ่านช่องทางใด; ความจำเป็นของแอป native บน Windows/Mac
- อุปกรณ์และ OS ขั้นต่ำ การใช้งาน offline นโยบายเครื่องหาย และผู้ถือ signing keys / release approver

ไม่มีการเชื่อม เปลี่ยน schema, permission, secrets, runtime หรือ deployment ในการจัดทำแผนนี้; ไม่ใช่หลักฐาน UAT, security approval หรือ production readiness
