## เป้าหมายและขอบเขต

ผู้ใช้ต้องการแอปที่ใช้งาน workflow เดิมของ Formula Studio ได้ครบทุกบทบาท และเชื่อมระบบเดิมได้ โดยใช้ประสบการณ์มือถือที่เรียบง่าย ใช้งานมือเดียวได้ มีแชตและแจ้งเตือน การทำงานปัจจุบันจำกัดเฉพาะข้อมูลและบริการจำลอง **ยังไม่ได้รับอนุญาตให้เชื่อมฐานข้อมูลจริง** ผู้ใช้สั่งพักงานแจ้งเตือนและ APK แล้วให้ทำ workflow/หน้าจอต่อ และสั่งหยุดงานเพื่อส่งต่อในรอบล่าสุด

เปิดอ่าน `AGENTS.md` ของ repository และคำสั่งผู้ใช้ก่อนทำงานต่อ: GitHub เป็นแหล่งอ้างอิงหลัก ต้องใช้ feature branch และห้ามแก้ production runtime โดยตรง การเปลี่ยนสิทธิ์ การยืนยันตัวตน ฐานข้อมูล หรือความถูกต้องของประวัติเป็นการเปลี่ยนแปลงสำคัญ ต้องมีผู้ตรวจอิสระและผ่านขั้นอนุมัติที่เกี่ยวข้อง ห้ามอนุมัติงานของตนเองหรือสมมติกฎธุรกิจแทนเจ้าของงาน

## หลักฐานและสถานะที่สำคัญ

1. **ความต่างของรุ่นและกฎสิทธิ์:** ดู `docs/RECONCILE_2026-10-28_MOBILE_BASELINE.md` ตัวอย่างมีแปดบทบาทแต่ไม่มี Oversea; กติกา MKT และ Oversea ระหว่างหน้าเว็บกับ gateway รุ่นที่ตรวจต่างกัน ต้องให้ System Owner ยืนยันรุ่นที่ใช้งานจริงและเจ้าของกระบวนการยืนยันกติกา ห้ามขยายสิทธิ์จากการคาดเดา
2. **การบันทึกและ session:** มีตัวเชื่อมทดลอง `mobile-preview/integration/runtime-job-save.js` และข้อเสนอ `mobile-preview/integration/SESSION_BOUNDARY_PROPOSAL.md` การทดสอบจำลองพบว่าการเปลี่ยน session ระหว่างตรวจฝั่งผู้ใช้กับส่งคำขออาจทำให้ gateway รับคำขอภายใต้ session ใหม่ แม้ฝั่งผู้ใช้รายงานว่าไม่ยืนยันผล ต้องออกแบบร่วมกับผู้รับผิดชอบ ไม่ถือว่าทดสอบตัวตนหรือระบบจริงแล้ว
3. **ประวัติแชต:** gateway commit `91d5fde5a17abf70d9ac5764b6b31529d69f913c` ที่ตรึงไว้ถูกทดสอบกับ PostgreSQL/PostgREST ชั่วคราวและ IAM จำลอง พบข้อความรหัสเดิมที่มีเนื้อหาต่างกันสามารถเขียนทับข้อความเดิมหรือย้ายไปอีกงานได้ ชุดรวมรอบล่าสุดจบ 20 ผ่าน 2 ไม่ผ่าน จาก 22 กรณี; สองกรณีที่ไม่ผ่านเป็นข้อค้นพบนี้ ไม่ใช่ผลผ่าน
4. **ตัวป้องกันแชตทดลอง:** ผู้ใช้อนุญาตให้สร้างและทดสอบเฉพาะในพื้นที่จำลองเท่านั้น ดู `mobile-preview/simulation/chat-id-guard.sql` และ `mobile-preview/integration/current-chat-guard-e2e.extra.mjs` ผล `python3 mobile-preview/integration/run-current-approval-e2e.py --chat-guard-only` ผ่าน 2/2: ทดสอบส่งซ้ำที่เหมือนเดิม การส่งข้อมูลต่างกัน การส่งพร้อมกัน และสังเกตพฤติกรรมลบแล้วใช้รหัสเดิม กรณีหลังยืนยันว่าตัวป้องกัน UPDATE ยังไม่กันการใช้รหัสใหม่หลังลบ ไม่ใช่การรับรองความปลอดภัย กรณี Sales/Admin ใช้ session และ IAM สมมติเท่านั้น
5. **การลบข้อความ:** Admin จำลองลบข้อความได้และนำรหัสกลับมาใช้ได้; Sales เจ้าของงานที่ยังเปิดอยู่ถูกปฏิเสธ ตัวอย่างหน้าเดิมยังลบข้อความตามรหัสงานเมื่อซิงก์การลบห้องแชท จึงห้ามใช้การบล็อก DELETE ทั้งหมดโดยไม่ตรวจผลต่อการลบงาน ผู้ใช้ยังไม่ได้ตัดสินใจว่าควรอนุญาตนำรหัสกลับมาใช้หรือไม่: เมื่อถาม ผู้ใช้ตอบให้หยุดงานและส่งต่อ ห้ามตีความคำตอบนั้นเป็นการเลือกนโยบาย
6. **ชุดทดสอบค้าง:** ขั้นตอนปิดบริการเคยทำงานก่อนชุดทดสอบที่เพิ่มภายหลัง ใน `run-current-approval-e2e.py` ปรับเฉพาะสำเนาชุดทดสอบชั่วคราวให้เตรียมข้อมูลและจัดกลุ่มการทดสอบก่อนเริ่ม ผลชุดเฉพาะจบ exit 0 และตรวจไม่พบ container ทดสอบที่ยังรันหลังจบ ดูหลักฐานใน `docs/DEBUG_LOG.md` ไม่ได้แก้ gateway หรือฐานข้อมูลจริง
7. **หน้าจอแชตและงานค้างในรอบหยุด:** ตอนแรกเข้าใจว่าข้อความที่ยังไม่ส่งหายโดยไม่มีคำเตือน แต่ตรวจแล้วพบว่า `main` มีตัวจัดการ `input` ตั้งสถานะเตือนอยู่แล้ว ไม่มีการแก้ UI เพื่อประเด็นนี้ เพิ่ม `mobile-preview/integration/chat-draft-native.test.mjs` และเพิ่มชื่อใน `run-portable-browser-tests.py` การทดสอบรอบแรกผิดเพราะคาดค่าเริ่มต้นเป็น Admin ทั้งที่เป็น Sales จึงแก้การทดสอบ รอบถัดมารายงานกรณีแชตผ่าน แต่ชุดรวมถูกหยุดตามคำสั่งผู้ใช้ก่อนจบ และมีการเพิ่มกรณียืนยันการทิ้งข้อความในไฟล์หลังเริ่มรัน: **กรณีที่เพิ่มท้ายสุดยังไม่ได้ทดสอบ** อย่าอ้างว่าชุดใหม่ผ่านครบ
8. **ผลก่อนเพิ่มกรณีใหม่:** `python3 mobile-preview/integration/run-portable-browser-tests.py` ผ่าน 7/7 บน Chromium ในพื้นที่จำลอง ครอบคลุมฟอร์ม การเปลี่ยนบทบาทแปดบทบาท การนำเข้าและเตือนรีโหลด แต่ไม่ใช่การรับรองโดยผู้แทนบทบาทหรือการทดสอบกับระบบจริง
9. **แจ้งเตือน/อุปกรณ์:** ก่อนพัก ผู้ใช้ยืนยันว่าเห็นแจ้งเตือนงานและแชตอย่างละหนึ่งครั้งบน A001T ในการทดสอบจำลองบางรอบ แต่มีผลไม่ครบในอีกรอบ และเครื่องเคยหลุดการเชื่อมต่อ ผลนี้ไม่พิสูจน์บริการผลิตจริงหรือ APK ดู `docs/MOBILE_PUSH_*` และ `docs/MOBILE_AUTH_APK_PREP_2026-10-28.md` ผู้ใช้สั่งพักหัวข้อนี้ จึงไม่กลับไปทำก่อนรับคำสั่งต่อ
