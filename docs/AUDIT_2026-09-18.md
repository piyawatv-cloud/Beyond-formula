## Findings

### F-01 — Shared job/user identity is absent

**Severity: HIGH**

The application uses local `A00001`-style IDs and human-readable user fields. The locked record/activity/chat contracts do not contain `central_job_id`, `central_user_id`, `source_system` or `source_record_id`.

**Recommendation:** define an additive mapping contract owned by Central Job Core/Central IAM; preserve legacy IDs and mark unmapped records as pending.

### F-02 — Formula-to-OPC handoff is not implemented as a proven contract

**Severity: HIGH**

Phase 3 requires a handoff with central job/formula references, customer requirement, selected formula, owner, timestamp, attachments and status. No live API/event client or acknowledgement store was found in this repository.

**Recommendation:** approve the proposed contract in `docs/architecture/INTEGRATION_CONTRACTS.md` before implementation; never read the OPC database directly.

### F-03 — Canonical stage/status and reporting event vocabulary are incomplete

**Severity: HIGH**

The current lifecycle is represented by `closed` plus Chat approvals and activity/chat action values. There is no canonical Formula stage/status, delay reason or cross-system event envelope.

**Recommendation:** approve a state machine and versioned event envelope; keep existing raw activity/chat evidence as backward-compatible source data.

### F-04 — Authorization controls have strong repository evidence, but live parity is unverified

**Severity: MEDIUM**

Browser and isolated PostgreSQL tests pass, including Auth boundary, RLS, actor checks, chat RPC and rollback. Those tests do not prove the currently deployed environment matches the reviewed commit/configuration.

**Recommendation:** perform staging UAT and deployment/health evidence through the Runtime Operator workflow. This audit does not authorize deployment.

### F-05 — Locked JSON contract constrains future integration/reporting

**Severity: MEDIUM**

The project forbids breaking localStorage and JSON keys. Any shared mapping or event projection must therefore be additive, backward-compatible and idempotent.

**Recommendation:** use adapters/projections and versioned events; treat schema/RLS/sync changes as Critical Change.

## Missing evidence / decisions required

- Accountable owner and format for central user/job IDs
- Formula ID/revision authority and Phase 3 state machine
- Approved service-to-service endpoint or event bus
- OPC acknowledgement/retry/idempotency policy
- Attachment/object-storage owner and access policy
- Sanitized UAT dataset and independent reviewer
- Deployment/config parity evidence for the real environment

## Decision

Accept the five architecture baseline documents as a discovery artifact only. Do not begin cross-system implementation or claim production readiness until G1/G2 decisions above are approved.
