## Findings

### F1 — HIGH: A03132 มีห้องแต่ใบงานไม่อยู่ในข้อมูลที่ Admin โหลดมา

**Evidence:** metadata ข้างต้น และเว็บจริง `visibleChats()` ใช้ `chats.filter(c => canSeeRecord(records.find(x => x.id === c.jobId)))`; `canSeeRecord(undefined)` คืน false

**Observation:** สาเหตุโดยตรงที่ Admin ค้นหาห้องไม่เจอคือไม่มี record A03132 ประกอบห้องในเครื่องนี้ แม้ role เป็น Admin ห้องแชตยังอยู่ใน fs_chats ปัญหาไม่ได้จำกัดแค่ A03132: มี orphan rooms รวม 6 ในชุดที่โหลดขณะตรวจ

**Gap:** ผลข้อมูลร่วมกันไม่เป็นไปตามเป้าหมายที่ทุกเครื่องเห็นชุดข้อมูลเดียวกันเมื่อเปิดซิงก์ ทั้งนี้ยังแยกไม่ได้ว่า record ไม่เคยอัปโหลด, ถูกลบ, ถูกจำกัดการอ่าน, หรือมีปัญหา sync/แหล่งข้อมูลอื่น

**Recommendation:** ตรวจเฉพาะ A03132 ใน browser ต้นทางของ Sales และหลักฐาน acknowledgement/error ที่เกี่ยวข้อง เทียบ record id, สถานะ pending และ metadata ของ endpoint/environment โดยไม่เปิดเผย credential ก่อนวางแผน reconcile ห้ามสร้างใบงานใหม่ด้วยเลขใหม่หรือเขียนทับข้อมูลจาก log เพียงอย่างเดียว

### F2 — HIGH: การบันทึกแต่ละส่วนแยกกัน ไม่รับประกันว่ามีใบงานกลางก่อนส่งห้อง

**Evidence:** deployed `createChat` ตรวจ record ใน memory ของ client เท่านั้น; deployed `sbPush` แยก recUp, chtUp, msgUp, apvUp, actUp และส่งคนละ operation; เมื่อ `sbSnap.records[id]` ไม่มีและ `recTouched[id]` ไม่ได้ตั้งไว้ จะพัก record (`recHeld`) แต่ยังพิจารณาส่งห้อง/กิจกรรมได้ อีกทั้ง bulk guard สามารถล้าง recUp แล้วปล่อยแชต/อนุมัติส่งต่อได้

**Observation:** เว็บมีช่องทางที่ log/ห้องไปต่อได้โดย record ไม่ได้อยู่ในชุดส่งรอบนั้น การเรียงส่ง fs_records ก่อน fs_chats ในบางเส้นทางไม่ใช่ transaction เดียวกัน และไม่ช่วยในกรณี record ถูกพัก ส่วนใบงานใหม่ที่สร้างหลัง initialization ตามปกติถูก `trackRecordVersions` ตั้ง recTouched จึงยังไม่มีหลักฐานว่า guard นี้ทำให้ A03132 หายจริง

**Recommendation:** รักษา workflow เดิมที่เปิดห้องภายหลัง แต่ทำให้สถานะ local saved / pending / server acknowledged ชัดเจน และกำหนด consistency check ของ record-room ผ่าน approved requirement/PR หากจะบังคับรอ server acknowledgement ต้องตัดสินใจเรื่อง offline workflow ก่อน เป็น Critical Change เมื่อแก้ sync/data handling

### F3 — HIGH: implementation ของเว็บจริงต่างจาก repository ที่ตรวจ

**Evidence:** build เว็บ `2026-09-23.1` เทียบ repository `2026-09-25.1`; เว็บมี server ID pool, recTouched/bulk guard, paginated sbReqAll, fs_messages/fs_approvals และ direct chat upsert; repository ใช้ secure chat event RPC/outbox และไม่ได้ใช้ helpers ดังกล่าว เว็บที่ตรวจไม่มี function authSignIn แบบ repository ไม่ได้ตรวจ credential หรือทดลองสิทธิ์ server

**Gap:** ผล local tests ของ repository ยืนยันพฤติกรรมเว็บจริงไม่ได้ และไม่สามารถผูก runtime กับ approved immutable commit/release ได้จาก build stamp เพียงอย่างเดียว การต่างกันไม่ใช่หลักฐานว่าไม่มี approval แต่ approval/release correlation ยังไม่พบในการตรวจครั้งนี้

**Recommendation:** System Owner/Runtime Operator ระบุ approved artifact/commit ของ domain นี้ก่อนเตรียม patch; ตรวจย้อนหลังว่าความเปลี่ยนแปลงของ sync/permissions ผ่าน review หรือไม่ ไม่ deploy repository ทับเว็บเพียงเพื่อให้เลข build ตรงกัน

**Correction to earlier hypothesis:** สมมติฐาน cap 1000 rows ของ repository ไม่ใช่ root cause ที่พิสูจน์ได้สำหรับเว็บนี้ เว็บจริงมี pagination sbReqAll และ metadata ที่ตรวจมีเพียง 225 records ผลทดลอง partial pull จาก repository ใช้ยืนยันเว็บจริงไม่ได้

### F4 — MEDIUM: client creation helper ไม่ตรวจสิทธิ์เห็นใบงานก่อนสร้างห้อง

**Evidence:** ทั้ง initial commit, current repository และ deployed createChat ตรวจเพียงว่ามี record และมีห้องเดิมหรือไม่; newChatFromRecord ตรวจ requireUser แล้ว createChat ก่อน openChatRoom ซึ่งค่อยตรวจ canSeeRecord; picker จำกัด visibility แต่ helper ไม่ได้ enforce ตรงจุดสร้าง

**Observation:** synthetic local test ของ original/repository ทำให้ Sales สร้างห้องสำหรับ record ของผู้อื่นที่มีใน memory ได้ แม้ canSeeRecord=false ไม่ได้เรียกทดสอบผิดสิทธิ์บนเว็บจริง และไม่ได้พิสูจน์ว่าฐานข้อมูลยอมรับการกระทำนั้น

**Recommendation:** เพิ่ม guard ตามสิทธิ์ที่ helper สร้างห้องและตรวจ server authorization ผ่าน staging/approved review เป็น Critical permission change หากแก้ ไม่ใช่สาเหตุที่ยืนยันของ A03132

### F5 — MEDIUM: สิทธิ์บาง role เปลี่ยนจาก baseline เดิม

**Evidence:** original e93e1d8 และ repository ปัจจุบันให้ MKT createData/chat เท่านั้น; deployed ROLES ให้ MKT editFormula, approve PD/Sales, export, closeJob เพิ่ม และเพิ่ม role Oversea ที่ ownOnly

**Observation:** การสร้าง/เปิดห้องยังเป็นรูปแบบเดิม แต่ permission matrix ไม่เหมือน baseline ไม่ได้ตรวจว่ามี owner approval สำหรับการเปลี่ยนเหล่านี้แล้วหรือไม่ และไม่ได้สรุปว่าเป็น unauthorized change

**Recommendation:** ให้ owner ยืนยัน intended role matrix เทียบ approved requirement/release; ไม่แก้สิทธิ์บน runtime ระหว่าง audit
