## Scope and expected standard

ประเมินว่า Sale brief มีข้อมูลตั้งต้นพอสำหรับ 3 ระดับหรือไม่:

1. เปิด project/รับโจทย์และเริ่มงาน RD
2. ทำ draft formula และ cost scenario
3. ส่งราคาพร้อมให้ Sales เสนอและเข้า CEO approval

เกณฑ์อ้างอิงจาก `cost calculator by project/SPEC.md` และ `REGISTRY.md`: project brief ต้องเป็น source ของโจทย์และ project identity; quotation ต้องมี version, source evidence, selected Tier, commercial confirmation, routing/rate, policy, approval และ disclosure ที่ตรวจสอบย้อนกลับได้

## Findings

### F-01 — Sale brief is sufficient only to start work, not to release a quotation

**Severity: HIGH**

The application allows creation when only customer or brand is present (`index.html:2448-2451`). The template also marks almost every product field optional (`index.html:5447-5468`). This supports fast intake, but it does not establish the minimum data needed for costing or a quote.

**Required interpretation:**

- `PASS` for opening a project and starting RD discovery.
- `FAIL` for “ready to calculate total / ready to quote”.

### F-02 — Missing explicit project and revision identity

**Severity: HIGH**

The record has a generated application id and timestamps, but the project registry requires a Formula project reference, formula revision, scenario/calculation revision and quote version (`REGISTRY.md:20`). Current status says Formula/Sales integration mapping is pending (`REGISTRY.md:5,16`). A job id alone must not be treated as the external project identity or as a formula revision.

### F-03 — Commercial data required for costing is absent from the brief

**Severity: BLOCKER for quote readiness**

The Sale brief has a target selling price, but not the governed cost inputs: material identity/spec, selected Tier, price and MOQ from the same commercial version, currency/unit, effective/expiry date, Procurement confirmation, planned loss/yield, PK snapshot/version and leftover exposure. The current specification explicitly requires these before quotation (`SPEC.md:49-56`; `REGISTRY.md:7-18, 64-70`).

Do not interpret `price/หน่วย` in the brief as supplier price or as a margin rule.

### F-04 — Operation cost inputs are not represented

**Severity: HIGH**

There is no Sale-brief data for the full RD routing, setup/run time, crew/person-hours, machine-hours/capacity, rate version, allocation basis, yield/loss basis or batch constraints. The specification requires Operation routing with separate DL/OH and no double counting (`SPEC.md:23-31`). This must be supplied/confirmed by RD, Production and Cost Accounting/Finance as applicable.

### F-05 — Missing versus zero is not safe in the current intake path

**Severity: HIGH**

The runtime converts blank ingredient weight to `0` and blank concentration to `100` (`index.html:2431-2433`). The create path also injects generic benefits, selling points and a default target when the brief is incomplete (`index.html:2494-2499`). This can make “unknown” look like a confirmed value. The cost workflow requires missing data to remain visible and not silently become zero (`SPEC.md:59-61`; `REGISTRY.md:44,67`).

### F-06 — Sales/OPC disclosure boundary is not consistently enforced in the current UI

**Severity: HIGH**

The project registry says Sales/OPC receive adjusted category amounts and must not see supplier, supplier price or full raw material names (`REGISTRY.md:15,31,47`). However, `jobDetailHTML` renders full ingredient name/origin/quantity rows (`index.html:4389-4404`), and the record popup calls it without hiding the table (`index.html:4501`). This is a disclosure-path gap even though the chat view hides the table for non-formula editors.

### F-07 — Approval path is not the same as quotation approval

**Severity: HIGH**

The current app has PD/RA/RD/Sales pass states and export gating (`index.html:4521-4526, 5288-5295`), but the project rule requires CEO commercial approval and an immutable quotation snapshot/revision (`REGISTRY.md:17-20`; `SPEC.md:54-55`). Existing departmental passes must not be treated as CEO quote approval.

There is also a contract inconsistency: the locked `CLAUDE.md` chat example lists approvals only for `pd, ra, rd`, while runtime and Supabase guard include `sales` (`index.html:4521-4526`; `supabase/schema.sql:294-325`). This should be resolved before changing the locked contract or implementing quote gates.

## Minimum additions before each gate

### Gate A — Accept intake / start RD

Add or confirm:

- stable Formula project reference and customer/brand identity owner
- requested product/form/pack/selling unit and target quantity or scenario range
- target market, claims, prohibited claims, dietary/regulatory constraints and required evidence
- packaging requirement/spec reference, not only free-text pack description
- brief owner, date received, source attachment/link and brief revision
- clear status for `unknown`, `not applicable`, `pending confirmation` and `confirmed`

### Gate B — Draft cost scenario

Add or confirm:

- formula revision and material identity/spec per line
- RM and PK source references; selected Tier as one linked set of price + MOQ/order multiple
- currency, price unit, MOQ unit, validity/effective date and Procurement confirmation event
- planned loss/yield by step and by RM/PK where applicable
- PK request/quote/snapshot or adopted PU-PK version, linked to current packaging requirement and quantity
- RD routing; Production time/capacity/crew; DL/OH rate version and allocation basis
- scenario quantity, batch size, pack size and selling-unit conversion
- explicit list of missing/ambiguous/excluded/obsolete inputs

### Gate C — Ready for Sales proposal / CEO approval

Add or confirm:

- RM/PK/Operation adjusted amounts and total, with internal base cost kept role-restricted
- purchase cash and leftover exposure shown separately from consumption cost
- pricing policy version; no assumed markup/margin and no blank-as-zero behavior
- applicable/fresh confirmed source versions and quote validity
- quote revision, calculation revision and frozen snapshot
- CEO approval event with approver/time/scope; any change creates a new revision
- restricted Sales/OPC payload and a verified Formula chat send status/link
- rollback reference to the prior approved quote

## Must-not-skip controls

1. **Do not quote from a target price alone.** It is customer expectation, not cost evidence.
2. **Do not treat missing as zero or generic defaults as customer-confirmed requirements.**
3. **Do not use raw ingredient name as material identity.** RD owns identity/spec; Procurement owns commercial terms.
4. **Do not split price and MOQ across different rows/versions.** One selected Tier must carry both.
5. **Do not use unconfirmed, expired, ambiguous, excluded, obsolete or “latest row” data as quote-ready.**
6. **Do not mix consumption cost, procurement cash and leftover exposure.**
7. **Do not skip full RD routing and DL/OH rate/owner confirmation.**
8. **Do not let PK delay block formula/RM draft work, but do block quote readiness when required PK evidence is missing.**
9. **Do not expose supplier, supplier price, raw material full name or restricted base cost to Sales/OPC.**
10. **Do not treat PD/RA/RD/Sales pass or Excel export as CEO commercial approval.**
11. **Do not overwrite an approved quote when source data changes.** Create a new revision and preserve the old snapshot.
12. **Do not implement against headers alone.** PU-PK semantic mapping, status meaning, equations, referential integrity and permissions still require validation.
13. **Do not change the locked storage/schema/permission contract without the required governance, owner approval and independent review.**

## Missing evidence / decisions required

- Formula project/revision integration contract and stable linkage to the brief
- Required-field matrix for intake versus draft versus quote-ready
- PU-PK semantic/status/runtime validation, not only header inspection
- RM Data Center current/approved semantics and commercial confirmation record
- RD routing and Production/Finance rate evidence
- Pricing policy/markup/margin owner and effective version
- CEO quotation snapshot/reapproval contract
- Role-filtered UI/export/chat payload acceptance tests
- Authorized sanitized projects for UAT and independent reviewer assignment

## Decision

Treat the current Sale brief as an **intake brief**, not a **quote-ready commercial brief**. The smallest safe next step is to define the three-gate field/ownership matrix above and validate it against one authorized sanitized project before implementation or production change.
