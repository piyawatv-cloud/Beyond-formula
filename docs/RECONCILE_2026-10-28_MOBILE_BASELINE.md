## ความต่างที่กระทบงานมือถือ

1. **VERSION_MISMATCH:** ตัวกลาง ตัวซิงก์ และ SQL ต่างจากชุดส่งมอบอย่างมีนัยสำคัญ GitHub รุ่นที่ตรวจมี `handleApprovalChange`, `fs_change_approval` และ `fs_approval_protocol_guard`; ชุดส่งมอบ SQL ที่เปรียบเทียบไม่มีสองฟังก์ชันหลัง การทดสอบมือถือที่ใช้ชุดส่งมอบจึงยังไม่ทดสอบเส้นทางอนุมัติรุ่น GitHub นี้
2. **RULE_CONFLICT / ยังไม่สรุปข้อบกพร่อง:** หน้าเว็บที่ตรงกับ GitHub ระบุ MKT อนุมัติ PD/Sales และ Oversea อนุมัติ Sales ได้ แต่ `rolePartAllowed` ของตัวกลาง GitHub commit ข้างต้นอนุญาต admin หรือบทบาทใน `FORMULA_APPROVAL_PARTS` ซึ่งมีเพียง PD, RA, RD, Sales และ `handleApprovalChange` ตรวจเงื่อนไขดังกล่าวก่อนตรวจสิทธิ์ส่วนกลาง การตีความสิทธิ์ที่ถูกต้องและผลในระบบที่ deploy จริงยังต้องยืนยัน
3. **ตัวอย่างมือถือ:** มี 8 บทบาท ไม่มี Oversea; ขอบเขตมองเห็นงานอาศัยบทบาทจำลอง ไม่ใช่การแยกบัญชีบุคคล ต้องไม่ใช้เป็นระบบตัดสินสิทธิ์
4. **ข้อจำกัดการทดสอบ:** ชุด gateway/SQL ที่ผ่านก่อนหน้าใช้ runtime ชุดส่งมอบ ไม่ใช่ GitHub commit ปัจจุบัน ไม่ยืนยันว่าสถานะจริงมีปัญหา หรือว่ากติกาใน GitHub เป็นกติกาที่ owner อนุมัติล่าสุด

นี่เป็นการควบคุมสถานการณ์ในตัวส่งจำลอง ใช้ central user ID จำลองเดียวกันแต่เปลี่ยนบทบาท ไม่ใช่การทดสอบการสลับบัญชีจริงหรือพฤติกรรมคุกกี้ในเบราว์เซอร์ ไม่มีหลักฐานว่าเกิดใน production การทดลองยืนยันเพียงว่าการตรวจรอบฝั่งผู้เรียกอย่างเดียวไม่ห้ามการเขียนในสถานการณ์นี้ ยังต้องให้ System Owner อนุมัติแนวทางผูกคำขอกับ session ฝั่งบริการและยืนยัน baseline ก่อนพัฒนาการแก้

### ผู้ใช้จำลองคนละรหัส

ขยาย fake IAM ของ test harness ในสำเนาชั่วคราวให้รองรับผู้ใช้สมมติสองคนและรัน `run-current-approval-e2e.py` อีกครั้ง ผล 6/6 ผ่าน: เมื่อผู้ส่งจำลองเปลี่ยน session ไปเป็นผู้ใช้ Admin คนใหม่หลัง client precheck คำขอถูกบันทึกใน PostgreSQL ชั่วคราวแต่ client รายงานไม่ยืนยันผล; เมื่อเป็นผู้ใช้ RA คนใหม่ gateway ปฏิเสธและข้อมูลไม่เปลี่ยน ทดสอบเฉพาะ transport ที่ควบคุมกับ IAM จำลอง ไม่พิสูจน์การเปลี่ยนคุกกี้จริงหรือ production

### คุกกี้จริงในเบราว์เซอร์ทดสอบ

รันชุดเดิมเพิ่มกรณี Chromium จริงด้วย profile แยกและหน้า harness ที่โหลดตัวเชื่อมมือถือ หยุดตัวส่งหลัง precheck เปลี่ยนคุกกี้เป็น Admin ผู้ใช้สมมติอีกคน แล้วส่งผ่าน relay ภายในเครื่องไปยัง gateway และ PostgreSQL ชั่วคราว; ตรวจว่าคุกกี้ที่ relay รับเป็นผู้ใช้คนใหม่และข้อมูลจำลองถูกบันทึก ขณะที่ client ไม่ยืนยันผล ชุดทดสอบรวม 7/7 ผ่าน

นี่เป็นการควบคุมคุกกี้และจังหวะด้วยเครื่องมือ ไม่ใช่การทดสอบหน้ามือถือ/หน้าล็อกอินจริง และไม่แสดงผลของระบบที่ deploy อยู่; IAM ยังจำลอง รอบแรกตัวทดสอบล้มเหลวจากการอ่านรูปแบบผลตอบเครื่องมือผิดและผ่านหลังแก้ตัวทดสอบ

## คัดลอกงานและเจ้าของ: ผลทดลองเพิ่มเติม

ใช้ฟังก์ชันคัดลอกจากหน้าเว็บที่ตรวจ hash โดยจำลองการกดและส่วนประกอบหน้า แล้วส่งผลผ่าน gateway, PostgREST และ PostgreSQL ชั่วคราว: Sales เจ้าของคัดลอกได้โดยคงเจ้าของ, MKT คนอื่นถูกปฏิเสธเมื่อคง `ownerEmail` เดิม, Admin คนอื่นสร้างสำเนาได้โดยยังคง `createdBy` และ `ownerEmail` เดิม ชุด `run-current-approval-e2e.py` ผ่าน 9/9 บริการสิทธิ์และบัญชีเป็นแบบสมมติ ฟังก์ชันหน้าเดิมถูกทดสอบใน harness ไม่ใช่การกดจริงและไม่พิสูจน์ระบบ production ต้องให้เจ้าของงานตัดสินใจว่าเจ้าของสำเนาควรเป็นใครก่อนปรับระบบมือถือ
