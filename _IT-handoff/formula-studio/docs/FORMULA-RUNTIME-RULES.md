# กฎการทำงานกับ Formula Studio runtime

กฎทุกข้อในเอกสารนี้มาจากเหตุการณ์ที่เกิดขึ้นจริงบนระบบนี้ ไม่ใช่ข้อควรระวังทั่วไป
แต่ละข้อมีหลักฐานกำกับ เพื่อให้คนอ่านรู้ว่าทำไมกฎนี้ถึงมีอยู่ และรู้ว่าจะยกเลิกได้เมื่อไหร่

เอกสารนี้คือแหล่งความจริงเดียวของโปรเจกต์นี้ — อ้างอิงไฟล์นี้ ไม่ใช่สำเนาของมัน
กฎของระบบพี่น้องอยู่ที่ `~/Desktop/OPCworkflow/docs/OPC-RUNTIME-RULES.md` ซึ่งใช้ร่วมกัน
ไม่ได้ทั้งหมด เพราะระบบนี้ครอบแอปที่เราไม่ได้เป็นเจ้าของ

## 0. ข้อที่ต่างจากระบบพี่น้อง และต้องรู้ก่อนอ่านข้ออื่น

**0.1 เราไม่ได้เป็นเจ้าของ `index.html`** — มันเป็นไฟล์เดียว ~500 KB จาก
`phossatron/Beyond-formula` ที่เราไม่มีสิทธิ์ push · เราแตะมันไม่ได้เลย
ทุกอย่างที่เราเพิ่มต้องทำจากนอกไฟล์: แทนที่ข้อความตอนเสิร์ฟ หรือแทรกสคริปต์เข้าไป

**0.2 ไม่มีสแตกทดสอบแล้ว — ห้ามทดลองบนปลายทางที่เขียนได้ของ production** — `formulatest`
ถูกลบเมื่อ 3 ต.ค. 2569 (เจ้าของตัดสินใจ) · การยิงทดลองใส่ `formula` = เขียนข้อมูลจริง
*เหตุผล: 24 ส.ค. 2569 การยิง `POST fs_meta` เพื่อดูว่า PostgREST ตอบอะไรกับ body ว่าง
เขียนทับรายชื่อ Tag จริงเป็นลิสต์ว่าง กู้กลับจากไฟล์สำรองที่ทำไว้ 10 นาทีก่อนหน้า*
ถ้าจะสร้างสแตกทดสอบใหม่ ต้องมีฐาน volume network และ secret แยกของตัวเอง และห้าม mount
`formula-proxy.mjs`/`releases/` จาก tree เดียวกับ production

**0.3 ทุกคำสั่ง docker compose ต้องมี `-p` เสมอ** — `formularuntime` / `formuladata` · ชื่อโปรเจกต์ต้องอ่านจากไฟล์ env ห้ามคำนวณเอง
*หลักฐาน: ชื่อที่คำนวณได้กับชื่อที่ตอนยกสแตกใช้จริงเคยไม่ตรงกัน แล้ว compose ไปสร้าง
คอนเทนเนอร์ใหม่ชนชื่อเดิม โดย error ที่ได้พูดถึงแค่ "ชื่อซ้ำ"*

## 1. ข้อมูลจริงและการกู้คืน

**1.1 ห้ามลบข้อมูลของแอป** — ตาราง `fs_*`, WAL, volume `formula_pgdata`, ไฟล์สำรอง
ห้ามลบ ตัดทอน เขียนทับ หรือย้าย เพื่อเรียกคืนพื้นที่ ไม่ว่ากรณีใด

**1.2 ห้าม `docker system prune --volumes`** หรือคำสั่งล้างแบบกวาดทั้งระบบ
คอนเทนเนอร์ของเราติดป้าย `com.beyond.formula-runtime.managed=true` ทุกตัว
ส่วนสคริปต์เก็บกวาดของ OPC ดูป้าย `com.beyond.opc-workflow.*` — สองชุดนี้แยกกัน

**1.3 การลบในแอปยังลบจริง แต่ต้องมีสำเนาเสมอ** — trigger `*_keep_deleted` เก็บทั้งแถว
ลง `fs_archive` ก่อนทุกครั้ง และ `anon` ไม่มีสิทธิ์แตะตารางนั้นเลย
**ห้าม `drop table fs_archive`** ในนั้นคือสำเนาของสิ่งที่ถูกลบไปแล้ว ซึ่งไม่มีที่อื่นเก็บอีก

**1.4 ก่อนทำอะไรที่ทำลายได้ ต้องมีจุดกู้คืนที่ยืนยันแล้ว** — `sh scripts/backup-formula.sh`
แล้วตรวจ checksum · สำรองที่ยังไม่ได้ตรวจ ไม่นับเป็นจุดกู้คืน

**1.5 ทดลองกับปลายทางที่เขียนได้ ต้องไม่แตะแถวจริง** — ใช้คีย์/ชื่อที่ไม่มีอยู่จริง
(`name=in.("zzz-ไม่มีจริง")`) หรือทำใน `psql` ด้วย `begin; ... rollback;`
ถ้าเลี่ยงไม่ได้ ให้เลือกค่าที่คืนกลับได้เป๊ะ แล้วคืนในสคริปต์เดียวกันทันที
*ดูข้อ 0.2 — นี่คือกฎที่ตามมาจากเหตุนั้น*


**1.6 ประวัติเวอร์ชันของใบงานเป็นข้อมูลกลาง ไม่ใช่ของเครื่อง** — ฐานเก็บแถวเดิมเข้า `fs_archive`
ด้วย `source='fs_records_version'` ทุกครั้งที่ `fs_records.data` เปลี่ยน (`runtime/record-versions.sql`)
และเบราว์เซอร์อ่านผ่าน `GET /__formula/job-versions` เท่านั้น · `source='fs_records'` ยังแปลว่า "ถูกลบ"
ห้ามใช้ปน · สำเนาใน `fs_recbak` ของเครื่องเป็นแค่ตาข่ายสำรองที่มีเพดาน
*หลักฐาน: 16 ต.ค. 2569 admin ไม่เห็นเวอร์ชันของ `A02071` ที่ pd แก้บนเครื่องของเธอ และ `fs_recbak` กิน 1.5M
จาก 5M ของทุกคน*

## 2. เซิร์ฟเวอร์เป็นเจ้าของความจริง ไม่ใช่เบราว์เซอร์

*บริบท: แอปนี้ออกแบบมาให้เบราว์เซอร์คุยกับฐานตรง ๆ และตัดสินสิทธิ์เองทั้งหมด
โค้ดที่ทำแบบนั้นยังอยู่ครบและเราแก้ไม่ได้ · ทุกข้อในหมวดนี้คือการครอบทับจากข้างนอก*

**2.1 คีย์ของฐานต้องไม่ปรากฏในหน้าเว็บ** — proxy แทนที่ `SB_URL`/`SB_KEY` ตอนเสิร์ฟ
ถ้าแทนที่ไม่สำเร็จ `x-fs-sb-gateway: unchanged` และด่านก่อนสลับสีจะไม่ยอมให้สลับ
CSP ไม่มี `*.supabase.co` ใน `connect-src` เป็นด่านที่สอง — พังแบบปิด ไม่ใช่พังแบบเปิด

**2.2 ตัวระบุถาวรต้องออกจากเซิร์ฟเวอร์** — เลขงานออกจาก `fs_next_rec_seq()` เท่านั้น
เขียน `fs_meta` คีย์ `reccounter` ตรง ๆ ไม่ได้ ทั้งที่ proxy (กรองทิ้ง) และที่ฐาน (trigger ปฏิเสธ)
**รหัสที่ออกไปแล้วห้ามออกใหม่** เพราะอาจอยู่บนเอกสารที่ออกจากบริษัทไปแล้ว

**2.3 บทบาทและรหัสผ่านของผู้ใช้ ห้ามรับจากเบราว์เซอร์** — ฐานตรึง `role`/`pass` ไว้ทุกครั้ง
ที่แถวเดิมถูกแก้ · ทางเดียวที่เปลี่ยนบทบาทได้คือ `fs_set_user_role()` ซึ่ง proxy เรียกให้
หลังตรวจแล้วว่าเซสชันเป็น admin จริง

**2.4 `ALLOWED_RPC` คือด่านจริงของประตูเปลี่ยนบทบาท ไม่ใช่สิทธิ์ในฐาน**
PostgREST เรียกทุกฟังก์ชันในนาม `anon` จะไม่ให้ `anon` เรียกก็เท่ากับปิดประตูทิ้ง
**ห้ามเติมชื่อฟังก์ชันใด ๆ ลง `ALLOWED_RPC` โดยไม่คิดว่าเบราว์เซอร์จะเรียกมันได้ทันที**
`tests/write-policy.test.mjs` มีข้อที่ยืนยันว่า `fs_set_user_role` ไม่อยู่ในรายการนั้น

**2.5 ตัวตนของผู้ทำ ประทับจากเซสชัน ไม่ใช่จากสิ่งที่ส่งมา** — `user` และ `role` ใน
`fs_activities` ถูกเขียนทับด้วยค่าจากคุกกี้เสมอ · แต่ **ห้ามแตะ `uid` และ `ts`**
`uid` คือกุญแจกันรายการซ้ำ ไม่ใช่รหัสประจำตัว แก้เมื่อไหร่ได้แถวซ้ำทุกรอบซิงก์
`ts` อยู่สองที่ (คอลัมน์ `ts` และ `data.ts`) แก้ที่เดียวแล้วลำดับที่แสดงกับที่เรียงไม่ตรงกัน

**2.6 รูปแบบของเนื้อคำขอ ต้องถูกทำให้เป็นแบบเดียวก่อนตรวจกฎ ไม่ใช่ปล่อยผ่าน**
PostgREST รับทั้ง `[{...}]` และ `{...}` เท่ากัน · โค้ดที่เขียนว่า "ไม่ใช่รายการ = ส่งผ่าน"
ไว้เหนือกฎทุกข้อ เท่ากับเปิดทางข้ามด่านทั้งหมดด้วยคำขอเดียว
*หลักฐาน: 24 ส.ค. ผู้ตรวจพิสูจน์ว่าเซลล์คนหนึ่งส่งก้อนเดียวขึ้นมาแล้วสร้างผู้ใช้บทบาท
admin ได้ ปลอมชื่อผู้ทำในประวัติได้ และเขียนตัวนับเลขงานทับได้ — โค้ดนั้นขึ้นระบบไปแล้ว*
ส่วนที่ไม่ใช่ทั้งรายการและก้อนข้อมูล (ตัวเลข ข้อความ ค่าว่าง) ให้ปฏิเสธไปเลย
*หลักฐาน: ปลายทางตอบ 201 ให้เนื้อคำขอที่เป็นข้อความ `"xxx"`*

**2.7 กฎที่ "จริงเสมอ" ห้ามฝากไว้กับชั้นเดียว** — ถ้าฐานทำได้ ฐานต้องทำด้วย
*หลักฐาน: `data-policy.sql` เคยเขียนเหตุผลไว้ว่า "การสร้างผู้ใช้ใหม่ยังใส่บทบาทได้
เพราะมีด่านของ proxy คุมอยู่อีกชั้น" แล้วชั้นนั้นมีรู · ตอนนี้ฐานถอด `role` ออกจากแถวใหม่
ที่ `anon` ส่งมาเสมอ และบทบาทออกได้ทางเดียวคือ `fs_set_user_role()`*

**2.8 Activity Log แก้ไม่ได้ ลบไม่ได้** — ทั้งที่ proxy (ไม่รับ `DELETE`/`PATCH`)
และที่ฐาน (เพิกถอน `update, delete` จาก `anon`)

**2.9 การเพิ่มรหัสเจ้าของให้แถวเก่า ไม่ใช่การเปลี่ยนเจ้าของ** — แถวที่ยังไม่มี `ownerEmail`
รับอีเมลของเซสชันที่ยืนยันแล้วได้หนึ่งครั้ง เมื่อ `createdBy`/`salesOwner` ไม่เปลี่ยน และเซสชันนั้น
เป็นเจ้าของตามกติกาชื่อเดิม (`storedJobOwner`) · อีเมลของคนอื่น หรือทับอีเมลที่มีอยู่แล้ว
ยังเป็นการเปลี่ยนเจ้าของและต้องผ่าน admin + `FORMULA_EDIT`
*หลักฐาน: 12–14 ต.ค. 2569 หลังปล่อย PR #53 client เติม `ownerEmail` ให้แถวที่คนแก้ แต่ proxy นับ
"ว่าง → มีอีเมล" เป็นเปลี่ยนเจ้าของ ทุกการแก้ใบงานเก่าของคนที่ไม่ใช่ admin จึงถูกตอบ
`FORMULA_OWNER_IMMUTABLE` · เทสต์ `the first edit after the owner-email release is saved` ล็อกไว้*

## 3. นโยบายสองชั้น และเส้นแบ่งระหว่างชั้น

**3.1 ฐานถือกฎที่จริงเสมอ · proxy ถือกฎที่ต้องรู้ว่าใครเรียก**
ฐานไม่รู้จักใครเลย ทุกคำขอมาถึงในนาม `anon` เหมือนกันหมด
เขียนกฎผิดชั้น = กฎที่ข้ามได้ หรือกฎที่ทำงานผิดคน

**3.2 `data-policy.sql` ต้องรันหลัง `data-grants.sql` เสมอ**
ไฟล์แรกให้ `grant all` กับ `anon` ไฟล์ที่สองเป็นตัวเพิกถอนกลับ
ทางกู้คืนหรือ re-init ไหนที่รันไฟล์แรกโดยไม่รันไฟล์ที่สอง จะคืนสิทธิ์ `TRUNCATE`
และทิ้ง trigger เก็บสำเนา **โดยไม่มีอาการอะไรเลยจนถึงวันที่มีคนกดลบ**
`scripts/verify-data-policy.sh` มีด่านจับเรื่องนี้ 7 ข้อ และถูกเรียกทั้งจาก
`monitor-formula.sh` (ทุก 15 นาที) และ `safe-deploy-formula.sh` (ก่อนและหลังปล่อยของ)

**3.3 กรองแล้วตอบสำเร็จ ไม่ใช่ตอบปฏิเสธ**
`sbPush()` ของแอปเรียง `await` เปลือย ๆ สิบกว่าบรรทัด มีแค่ `msg` กับ `apv` ที่ครอบ
`try/catch` · ตอบไม่ใช่ 2xx หนึ่งครั้ง = ทุกบรรทัดหลังจากนั้นไม่ได้ทำงานทั้งรอบ
ของที่ "ตั้งใจกรอง" ต้องกรองแล้วตอบสำเร็จ · ของที่ "ไม่ควรมีทางเกิด" (เมธอด/ตาราง
นอกรายการ) ตอบปฏิเสธดัง ๆ — สองอย่างนี้ไม่เหมือนกัน
**ตารางที่รอบซิงก์ส่งเองโดยผู้ใช้ไม่ได้สั่ง (`fs_users`) อยู่ฝั่ง "ตั้งใจกรอง" เสมอ** และบรรทัดปฏิเสธทุกบรรทัด
ต้องมี `by/byRole` (ดู 3.6)
*หลักฐาน: 16 ต.ค. 2569 แท็บของผู้ใช้ที่ไม่ใช่ admin ส่ง `POST fs_users` ทุกรอบ 308 ครั้งใน 2 ชม. ได้ 403 ทุกครั้ง
→ `fs_activities` ของแท็บนั้นไม่ถูกส่งทั้งช่วง และบรรทัด `denied` ไม่มีชื่อ จึงหาแท็บต้นทางไม่ได้*

**3.4 สร้างฟังก์ชันใหม่ในฐานแล้วต้องสั่ง PostgREST อ่านสคีมาใหม่**
`notify pgrst, 'reload schema';` ต้องอยู่ท้าย `data-policy.sql` เสมอ
*หลักฐาน: 24 ส.ค. ประตูเปลี่ยนบทบาทตอบ 404 `PGRST202` ทั้งที่ฟังก์ชันอยู่ในฐานครบ
ข้อความนั้นอ่านเหมือนพิมพ์ชื่อฟังก์ชันผิด ซึ่งพาไปหาผิดทางทั้งหมด*

**3.5 PL/pgSQL ผูกชื่อคอลัมน์ตอนคอมไพล์ ทุกกิ่งของ `CASE` ไม่ใช่เฉพาะกิ่งที่ทำงาน**
trigger ที่ใช้กับหลายตาราง ต้องอ่านค่าจาก `to_jsonb(old)` ไม่ใช่ `old.<ชื่อคอลัมน์>`
*หลักฐาน: 24 ส.ค. `fs_keep_deleted()` เขียน `old.job_id` ไว้ในกิ่งของ `fs_chats`
แล้วการลบจาก `fs_records` ล้มทั้งคำสั่ง — ตั้งใจแค่จะเก็บสำเนา แต่ทำให้ลบอะไรไม่ได้เลย*

**3.6 ทุกทางที่หยุดการบันทึกใบงานต้องทิ้ง audit line ที่บอกว่าใคร ใบไหน เพราะอะไร** —
ที่ proxy คือ `job-save-blocked` (หยุดก่อนรับเข้า intake) และ `job-received` ที่ไม่ใช่ `saved`
พร้อม `reason`/`by`/`byRole` · ที่เบราว์เซอร์คือ `client-blocked` ผ่าน
`POST /__formula/client-diagnostic` (บันทึกอย่างเดียว จำกัดอัตรา) เพราะด่านฝั่งหน้าเว็บ
(รอ handshake · `canEdit` เท็จ · สำเนาในเครื่องไม่ตรงของกลาง · คิวค้าง `forbidden`) หยุดผู้ใช้ได้
โดยไม่มีคำขอใดออกไปเลย · `monitor-formula.sh` นับทั้งสามอย่างในหน้าต่าง 15 นาที
**คำตัดสิน `forbidden` ในเบราว์เซอร์ต้องไม่ถาวร** — ลองใหม่หนึ่งครั้งต่อการโหลดหน้า
เพื่อให้คำตัดสินล่าสุดเป็นของจริงและถูกบันทึก
*หลักฐาน: 14 ต.ค. 2569 ผู้ใช้แจ้งว่าบันทึกไม่ได้และเปิดแชตไม่ได้ · gateway log ของวันนั้นไม่มี
บรรทัดใดเกี่ยวกับใบงานเลย เพราะทางออกก่อน intake เงียบ และคิวที่ได้ `forbidden` เมื่อ 12 ต.ค.
ถูกข้ามตลอดไปโดยไม่ส่งซ้ำ · บรรทัด `job-save-blocked` เดิมอยู่ในกิ่งที่ production ไม่เดินถึง
(นับได้ 0 ทุกวัน) — เทสต์ที่ไม่เปิด intake จึง "เขียวทั้งที่ไม่มีอะไรให้ทดสอบ" (ดู 6.2)*

## 4. Blue / Green

**4.1 สองสีต้องรันโค้ดเดียวกันเสมอ** — `sh scripts/verify-formula-parity.sh <prefix>`
**รับ prefix เป็น argument ไม่ใช่ตัวแปรสภาพแวดล้อม** ลืมใส่แล้วมันไปตรวจสแตกจริง
ข้อที่สำคัญที่สุดคือข้อ 5 (เทียบของที่เสิร์ฟกับไฟล์บนดิสก์) เพราะเป็นข้อเดียวที่จับได้ว่า
โปรเซสยังรันโค้ดเก่ากว่าไฟล์ที่เพิ่งแก้

**4.2 `runtime/formula-proxy.mjs` ถูก mount เข้าไปตรง ๆ ไม่มีขั้นตอน build**
แก้ไฟล์แล้วดิสก์เปลี่ยนทันที แต่โปรเซสยังเป็นโค้ดเก่าจนกว่าจะ recreate
**ผลที่ต้องระวัง: การ recreate ผิดจังหวะ = ปล่อยโค้ดที่ยังแก้ไม่เสร็จขึ้นระบบ**
และผลตรงข้ามก็จริงเหมือนกัน — `bootstrap` ใช้ `compose up -d` เฉย ๆ ไม่มี
`--force-recreate` คอนเทนเนอร์ที่ขึ้นอยู่แล้วจึงยังเสิร์ฟไฟล์ฉบับเก่าต่อไปเงียบ ๆ
ต้องใช้ `prepare <สี>` ถ้าอยากให้หยิบไฟล์ใหม่
*หลักฐาน: 24 ส.ค. แก้สคริปต์ฝังแล้วสั่ง bootstrap บน testlab — ยังเสิร์ฟไฟล์เก่า
ด่าน parity ข้อ "เสิร์ฟตรงกับไฟล์บนดิสก์" เป็นตัวที่จับได้*
ไฟล์ที่ยาวขึ้นระหว่างที่คอนเทนเนอร์ยังรันอยู่ เคยทำให้คอนเทนเนอร์เห็นไฟล์ถูกตัดกลางคัน
ในระบบพี่น้องมาแล้ว — **ให้ recreate ไม่ใช่ restart**

**4.3 ด่านก่อนสลับคือ "รอ" ด่านหลังสลับคือ "ถอย"**
และด่านของ `rollback` ต้องหลวมกว่าด่านขาไปเสมอ เพราะรุ่นเก่าที่ยังดีอยู่อาจไม่รู้จัก
กฎที่เพิ่งเขียนเมื่อวาน การถูกกฎใหม่บล็อกไม่ให้ถอย คือกับดัก

**4.4 ห้ามผ่อนด่านเพื่อให้ deploy ผ่าน** ไม่ว่ากรณีใด

**4.5 เพิ่มไฟล์ที่ mount ใหม่ = ต้องแก้ทั้งสองสีใน `docker-compose.formula.yml`**
รายชื่อ mount ถูกล็อกตอน "สร้าง" คอนเทนเนอร์ · ลืมสีไหน สีนั้นจะพังตอนรีสตาร์ตครั้งถัดไป
ไม่ใช่ตอนนี้ · ไฟล์ที่เป็นแค่ของเพิ่มจึงต้องอ่านแบบ `readOptional` ไม่ใช่อ่านเข้ม

**4.6 backend รายสีและ standby (เพิ่มในงานเตรียม Supabase 19 ต.ค. 2569)** — ระบบนี้เป็น
active/passive บนเครื่องเดียว ไม่ได้แบ่งผู้ใช้ระหว่างสองฐาน: สีที่รับผู้ใช้อยู่ใช้ฐานเดียว
ส่วนอีกสีจะรับแทนได้ก็ต่อเมื่อผ่านด่านทั้งหมดแล้วเท่านั้น การมี container สองสีไม่ใช่การสำรองข้ามเครื่อง

Compose รองรับ `FORMULA_BLUE_BACKEND` / `FORMULA_GREEN_BACKEND` (`local` หรือ `supabase`)
และ `FORMULA_BLUE_TRAFFIC_MODE` / `FORMULA_GREEN_TRAFFIC_MODE` (`serving` หรือ `standby`)
โดยส่งเป็น `FORMULA_BACKEND` / `FORMULA_TRAFFIC_MODE` เข้า proxy ของแต่ละสี พร้อมส่ง mode รายสีเข้า edge
ค่าเดิมที่ไม่ตั้งตัวเลือกเหล่านี้ยังเป็น local + serving และใช้ `SB_*` ชุดเดิมทั้งคู่
การตั้ง Blue ไม่เปลี่ยน Green หรือกุญแจเซสชันร่วม ตัวอย่างอยู่ที่ `runtime/data.env.example`
ค่าต่างรายสีทำผ่าน `FORMULA_<BLUE|GREEN>_SB_ORIGIN`, `_SB_REST_BASE`, `_SB_UPSTREAM_AUTH`,
`_SB_SERVICE_KEY` / `_SB_ANON_KEY` และต้องอยู่ในช่องทางจัดเก็บความลับที่อนุมัติแล้วเท่านั้น

เลือก Supabase ต้องระบุ backend และ traffic mode ชัดเจน พร้อม REST path `/rest/v1`,
auth `bearer` และกุญแจฝั่งเซิร์ฟเวอร์; HTTPS บังคับยกเว้น loopback สำหรับข้อมูลจำลองในเครื่อง
การชี้ origin ไป Supabase โดยยังใช้ backend ค่าเริ่มต้น หรือ mode/ค่าตั้งไม่ถูกต้อง จะปิดทางข้อมูล
กุญแจยังอยู่ฝั่งเซิร์ฟเวอร์ browser ใช้ session เดิมและไม่คุยกับ Supabase โดยตรง

`standby` เปิดเฉพาะ `/__formula/health` เท่านั้น ทุกเส้นทางอื่นตอบ 503 ก่อนตรวจ session
หรือเรียกข้อมูล รวมถึงหน้ากู้คืนและประตูสร้าง profile; ไม่เปิด/อ่าน/แก้ shared job-intake
ไม่เล่นคิวซ้ำ ไม่เปลี่ยน receipt และไม่ส่งคำขอไปฐาน Edge ไม่ส่งผู้ใช้ ไม่ retry และไม่ failover
เข้าสีนี้ และ `switch` / `rollback` ปฏิเสธสีที่ยังเป็น standby หรือ configuration ไม่ถูกต้อง
**ห้ามใช้ standby เป็นปลายทางทดสอบข้อมูลจริง**

Health แยก `configuredBackend` (local/supabase/unknown), `backendConfiguration` (valid/invalid),
`trafficMode` และ `servingEligible` โดยไม่เผย URL หรือกุญแจ ค่าตั้ง valid บอกเพียงว่ารูปแบบถูกต้อง
ไม่ได้ยืนยันว่าฐานมีข้อมูลล่าสุดหรือ schema/RPC พร้อม `status=standby` แปลว่าโปรเซสทำงานและตั้งใจ
ไม่รับข้อมูล; Docker healthcheck ยอมรับสถานะนี้เพื่อไม่ให้ตัวกู้คืน restart วน แต่ readiness ของ
edge/สคริปต์ยังต้องผ่าน `status=ok` และไม่ถูกปิดสิทธิ์รับผู้ใช้ `status=degraded` คือ configuration
หรือส่วนประกอบไม่พร้อม; `servingEligible=true` เป็นสิทธิ์จาก configuration ไม่ใช่ใบรับรองข้อมูล
ด่าน parity ยังคงเข้ม และรายงาน standby ว่ายังใช้รับผู้ใช้/rollback ไม่ได้ก่อนตรวจหน้าเว็บ
ด่านตรวจปลายทาง local เดิมใน `verify_color` ยังไม่ถูกยกเว้นสำหรับ Supabase ในงานนี้

ก่อนนำ Supabase มารับผู้ใช้ ต้องมีหลักฐานความสดของข้อมูลและการเทียบสองฝั่ง, schema/RPC,
สิทธิ์ และการเขียนพร้อมอ่านกลับตรงทุกค่า รวมทั้งแบบจำลองการถือครอง/ส่งต่อคิวค้างจากฐานเดิม
เมื่อได้รับอนุมัติจึงเปลี่ยน mode จาก standby เป็น serving อย่างชัดเจน และผ่าน release/switch gates
ของงานย้ายฐานที่อนุมัติแยกอีกครั้ง ห้ามเรียก Supabase ว่า rollback-ready ก่อนมีหลักฐานครบ
งานเตรียมนี้ไม่ย้ายข้อมูล ไม่เปลี่ยน production config ไม่ deploy และไม่สลับสี

## 5. การเฝ้าระวัง

**5.1 ตัวตรวจห้ามซ่อมตัวเอง** — ห้ามรีสตาร์ตอะไรเพื่อให้ด่านของตัวเองผ่าน
ตัวตรวจที่ซ่อมให้ตัวเองผ่าน คือทางที่ระบบสุขภาพดีจบลงด้วยการรีสตาร์ตวนไม่หยุด

**5.2 ทุกบรรทัดเตือนต้องมีช่อง `why=`** — เตือนที่บอกไม่ได้ว่าเจออะไร คือเตือนที่คนเลิกอ่าน

**5.3 การเฝ้าระวังที่รายงานความล้มเหลวของตัวเองไม่ได้ ไม่ใช่การเฝ้าระวัง**
`recover-formula.sh` นับความล้มเหลวติดต่อกัน ส่งเสียงเมื่อครบ 3 ครั้ง และ
**ไม่จดว่า "เตือนแล้ว" ถ้าส่งไม่ออก** ไม่งั้นรอบถัดไปจะนิ่งเพราะติด cooldown

ผลพิสูจน์กู้คืนของงานสำรองประจำวันไปถึงเจ้าของทาง Telegram ตรงจากสคริปต์
(`monitor-formula.sh` → `alert-backup-proof.sh` → `notify-telegram.sh`) ไม่ผ่านโมเดล
ใช้บอทและห้องเดียวกับ Hermes จาก `~/.hermes/.env` (`TELEGRAM_BOT_TOKEN`,
`TELEGRAM_HOME_CHANNEL`) — **ย้าย/เปลี่ยนชื่อคีย์ในไฟล์นั้น = ทางเตือนนี้ตาย** (ขึ้น WARN
และเด้งบนจอ Mac แทน) · โทเค็นถูกเพิกถอนก็ตายพร้อมกันทั้ง Hermes และทางนี้

**5.3.2 ปลายทางสำรองที่ใช้งานอยู่ตั้งแต่ 12 ต.ค. 2569** — งานตามตารางของ iMac เก็บสำเนา
ไว้ในโฟลเดอร์แยก `.formula-backups/` ภายใน repository `formula-runtime` และตรวจ

แต่ **ไม่ใช่สำรองนอกสถานที่** เพราะยังอยู่บน iMac เครื่องเดียวกัน · หากต้องการความทนทาน
กรณีเครื่องเสียหรือสูญหาย ต้องเพิ่มปลายทางคนละเครื่อง/คนละสถานที่ภายหลัง โดยไม่อ้างว่า
สำเนาใน `.formula-backups/` เป็น offsite

**5.4 ตัวกู้คืนสั่งได้แค่ `docker start` / `docker restart` ของคอนเทนเนอร์ที่มีอยู่**
**ห้าม `compose up -d`** เพราะมันสร้างคอนเทนเนอร์ใหม่ — ดูข้อ 4.2
การสร้างคอนเทนเนอร์เป็นงานของ `blue-green-formula.sh` เท่านั้น

**5.5 ตัวกู้คืนต้องเคารพล็อกช่วงเปลี่ยนผ่าน** — เข้าไปสั่งระหว่างที่ `blue-green` กำลัง
สลับสี = สองคนขับรถคันเดียวกัน

**5.6 ตัวนับใน `/__formula/health` ใช้วัดช่วงเวลาไม่ได้** — มันสะสมตั้งแต่โปรเซสเปิดตัว
รีเซ็ตทุกครั้งที่ recreate และแต่ละสีนับแยกกัน · ให้นับจากบรรทัดใน
`monitoring/gateway-<วัน>.ndjson` แทน โดยต้อง **อ่านสองวันเสมอ** (หน้าต่างเวลาคร่อม
เที่ยงคืน UTC ได้ทุกวัน ซึ่งตรงกับเจ็ดโมงเช้าตามเวลาไทย) และต้อง **กรองด้วยช่อง `stack`**
เพราะสองสแตกเขียนกองไฟล์เดียวกัน ไม่กรองแล้วการทดลองบน testlab หนึ่งครั้ง
จะทำให้เตือนว่าสแตกจริงมีปัญหา

บรรทัดที่ไม่มีช่อง `stack` ต้องถูกนับแยกและรายงาน ไม่ใช่เมินทิ้ง —
**"นับได้ 0 เพราะกรองผิด" หน้าตาเหมือน "ไม่มีอะไรเลย" ทุกประการ**

**5.7 launchd รันไฟล์ที่ plist ชี้ไป** — ของโปรเจกต์นี้ชี้เข้าเรโปตรง ๆ โดยตั้งใจ
แก้สคริปต์แล้วมีผลทันที ไม่ต้องติดตั้งซ้ำ · ถ้าวันหนึ่งเปลี่ยนไปใช้สำเนาที่ติดตั้ง
ต้องเขียนกฎข้อใหม่ทับข้อนี้ ไม่ใช่ปล่อยให้คนเดาเอง

## 6. การตรวจงานก่อนบอกว่าเสร็จ

**6.1 เทสต์เขียวไม่ใช่หลักฐานว่าใช้งานได้** — ต้องเดินของจริงผ่าน HTTP อย่างน้อยหนึ่งรอบ
บนสแตกจริงทันทีหลังสลับสี (ขณะที่สีเดิมยังถอยกลับได้) ด้วยโค้ดชุดเดียวกับที่ปล่อย

**6.2 เทสต์ที่ยืนยันว่า "มีข้อความนี้อยู่ในไฟล์" ไม่นับ** — ยกบล็อกโค้ดออกมารันจริงด้วย
`node:vm` แล้ว assert ว่าเครื่องหมายขอบเขตยังอยู่ · เทสต์ที่ตัดบล็อกไม่ได้แล้วเขียวเงียบ ๆ
คือเทสต์ที่ไม่มีอะไรให้ทดสอบ

**6.3 เทสต์ที่เทียบสำเนากับสำเนา ผ่านทั้งคู่ผิด** — ข้อที่กันข้อมูลเคลื่อนจากต้นทาง
ต้องอ่าน **บันเดิลที่ผนึกไว้จริง** มาเทียบ ไม่ใช่ตารางที่พิมพ์เองไว้ในเทสต์

**6.4 `vm.createContext` สร้าง realm ใหม่** — `[]` ที่ออกมาจากข้างในไม่เท่ากับ `[]`
ของเทสต์ แม้เนื้อในเหมือนกัน (`assert` แจ้งว่า "same structure but not reference-equal")
ให้ใช้ `vm.runInThisContext` ห่อด้วยฟังก์ชันแทน

**6.5 อ้างกฎข้ามเล่ม ต้องเขียนชื่อเล่มกำกับเสมอ** — ระบบนี้อยู่ใต้กฎสามเล่ม:

## 7. ขอบเขตอำนาจ

**7.1 ไม่ล็อกอินแทนผู้ใช้จริง และไม่สร้างเซสชันสวมรอยบนสแตกจริง**
คุกกี้ที่เซ็นเองใช้ทดสอบกลไกได้ แต่ไม่ใช่หลักฐานว่าคนจริงใช้งานได้

**7.2 การกระทำที่ย้อนกลับยาก ต้องถามเจ้าของก่อน** — หมุนคีย์ ย้ายโดเมน ลบผู้ใช้
เปลี่ยนบทบาทของคนอื่น · ถ้าจำเป็นต้องทดสอบเรื่องบทบาท ให้ใช้แถวของเจ้าของระบบเอง
แล้วคืนค่าทันที และรายงานว่าทำอะไรไป

**7.3 runtime และด่านทั้งหมดต้องทำงานได้โดยไม่มี AI** — ไม่มีขั้นตอนไหนในการปล่อยของ
การเฝ้าระวัง หรือการกู้คืน ที่รอคำตอบจากโมเดล

**7.4 ผู้ตรวจ (`formula-runtime-auditor`) รายงานอย่างเดียว ไม่ซ่อม**
ข้อที่ขึ้นว่า **Blocking** ต้องเคลียร์ก่อนส่งมอบหรือก่อนปล่อยของ
ไม่เห็นด้วยได้ แต่ต้องเขียนเหตุผลถึงเจ้าของ ไม่ใช่เงียบแล้วข้ามไป
