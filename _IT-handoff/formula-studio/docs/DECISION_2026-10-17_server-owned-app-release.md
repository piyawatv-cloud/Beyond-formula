# คำตัดสินที่เสนอ — ให้ระบบกลางเป็นเจ้าของข้อมูลและสิทธิ์ของแอป

วันที่: 17 ต.ค. 2569  
สถานะ: `PROPOSED` — ยังไม่ใช่คำอนุมัติให้ออกแอป เปลี่ยนสัญญาข้อมูล หรือขึ้นระบบจริง

## สรุป

เสนอให้รุ่นแอปถัดไปโหลดเฉพาะห้องแชตที่ผู้ใช้มองเห็น และไม่ส่ง `fs_users` หรือ `fs_meta` จากเบราว์เซอร์; ใช้ผลยืนยันตัวตนและสิทธิ์จาก `/sb/session`; แสดงสถานะเมื่อถูกปฏิเสธพร้อมทางแก้ที่ปลอดภัย; ใช้ประวัติเวอร์ชันกลาง; และเก็บสถานะอ่านแชตไว้ที่ระบบกลาง

runtime มีกลไกตรวจ role/สิทธิ์และขอบเขตเจ้าของใบงานในบางเส้นทาง แต่หลักฐานที่ตรวจยังไม่ยืนยันว่า gateway กรอง `fs_chats`/`fs_messages` ตามห้องที่ผู้ใช้มองเห็นได้ครบถ้วน จึงถือว่าการกรองห้องยังไม่ทำหรือยังไม่พิสูจน์จนกว่าจะตรวจ endpoint และผลตอบกลับจริง ประวัติเวอร์ชันกลางมี source และทางเชื่อมอยู่ใน repository แต่ยังต้องตรวจ release parity และสถานะ production ก่อนอ้างว่าใช้งานจริง การหยุดแอปที่ปิดผนึกไม่ให้โหลด/ส่งข้อมูลตั้งแต่ต้นทาง และการย้ายสถานะอ่านไปเก็บกลาง ต้องมีการออกแอปใหม่หรือการเปลี่ยนสัญญาข้อมูลที่ผ่านการอนุมัติแยกต่างหาก เอกสารนี้เสนอทิศทางและลำดับงานเท่านั้น

## หลักฐานที่ตรวจ

- รายงานหลังใช้งาน 14–16 ต.ค. ระบุว่าช่วงที่วัดพบการดึงห้องแชต 243 ห้องพร้อมข้อความทุกครั้ง และการย่อข้อมูลเกิด 151 ครั้งวันที่ 15 ต.ค. กับ 119 ครั้งวันที่ 16 ต.ค. เอกสารเดียวกันระบุว่าเป็นพฤติกรรมจาก full pull ของแอป sealed และเป็นปัญหาที่ต้องตัดสินใจระยะกลาง (`docs/POSTLIVE_2026-10-14_user-save-first-failure.md`, หัวข้อพื้นที่เก็บข้อมูล, บรรทัด 61–65)
- ข้อเสนอกลางเรื่องเวอร์ชันระบุซ้ำว่ามี 243 ห้อง และ runtime ย่อสำเนาในเครื่องภายหลัง (`docs/DECISION_2026-10-16_central-versions.md`, บรรทัด 5–11)
- โค้ด runtime ปัจจุบันครอบ `saveChats` เพื่อเขียนรูปย่อหลังจากข้อมูลกลางรับข้อความแล้ว และคงการบันทึกสถานะอ่านในเบราว์เซอร์ (`runtime/assets/fs-job-sync.js`, บรรทัด 2084–2102) จึงลดภาระการเขียนซ้ำได้ แต่ไม่เปลี่ยนต้นทางการโหลดของแอป
- เอกสารกลางเวอร์ชันอธิบายทางเชื่อมผ่าน RPC และ `/__formula/job-versions`; การกู้คืนยังใช้ทางบันทึกปกติ (`docs/handoff/2026-10-16-central-versions-and-storage.md`, บรรทัด 24–38)
- เอกสารแก้สิทธิ์ตาม IAM แสดงรูปแบบที่ runtime ส่งผล `canFormulaEdit` จาก `/sb/session` ให้แอป และยังคงตรวจสิทธิ์จริงที่ gateway (`docs/handoff/2026-10-16-formula-edit-ui-by-grant.md`, บรรทัด 12–23)
- `243` เป็นจำนวนที่รายงานในข้อมูลย้อนหลัง 14–16 ต.ค. และอ้างซ้ำในความเห็นโค้ดของ runtime ไม่ใช่การนับสด ณ 17 ต.ค. ก่อนออกแบบจริงให้ตรวจจำนวนห้องที่ผู้ใช้มีสิทธิ์เห็นจากระบบกลางอีกครั้ง โดยไม่ส่งเนื้อหาแชตออกจากขอบเขตที่อนุมัติ

## แนวทางที่เสนอ

1. **โหลดเฉพาะห้องที่ผู้ใช้เห็นได้**: ให้เซิร์ฟเวอร์เป็นผู้กรองรายการห้องตามเซสชันและขอบเขตข้อมูลก่อนส่งข้อความ เบราว์เซอร์ไม่ควรโหลดห้องที่ซ่อนแล้วค่อยกรองภายหลัง
2. **ไม่ส่ง `fs_users` หรือ `fs_meta` จากเบราว์เซอร์**: การจัดการผู้ใช้และตัวนับส่วนกลางเป็นความรับผิดชอบของเซิร์ฟเวอร์/ทางเฉพาะที่มีสิทธิ์ตรวจสอบ ไม่ใช่การอัปโหลดทั้งสำเนาจากทุกแท็บ
3. **ใช้ `/sb/session` เป็นคำตอบเรื่องตัวตนและสิทธิ์**: บทบาทหรือ grant ที่เบราว์เซอร์ส่งเอง หรือการตัดสินจากตาราง `ROLES` ในแอป ไม่ใช่หลักฐานสิทธิ์สำหรับข้อมูลที่ระบบกลางคุม แอปใช้ผลเซสชันเพื่อแสดงความสามารถ ส่วน gateway ต้องตรวจซ้ำทุกการอ่าน/เขียน
4. **ปฏิเสธอย่างชัดเจนและกู้คืนอย่างปลอดภัย**: เมื่อเซิร์ฟเวอร์ปฏิเสธ ให้บอกว่ารายการนั้นยังไม่บันทึก/ยังเปิดไม่ได้ และแสดงรหัสเหตุการณ์ที่ไม่เปิดข้อมูลลับ พร้อมปุ่มลองใหม่หลังตรวจเซสชัน หรือคำแนะนำให้ติดต่อผู้ดูแลเมื่อสิทธิ์ไม่พอ ห้ามแสดงปุ่มที่ชวนให้เขียนทับหรือยกระดับสิทธิ์เอง และห้ามลบคิว/สำเนาที่รอส่งโดยอัตโนมัติ
5. **ใช้ประวัติเวอร์ชันส่วนกลาง**: แสดงเวอร์ชันที่ระบบกลางบันทึกและใช้เส้นทางกู้คืนปกติซึ่งผ่านการตรวจสิทธิ์ทุกครั้ง สำเนาในเครื่องเป็นทางสำรองที่ระบุชัด ไม่ใช่แหล่งประวัติหลัก
6. **เก็บสถานะอ่านที่ระบบกลาง**: ระบุผู้ใช้ ห้อง และตำแหน่ง/เวลาอ่านบนบริการที่ตรวจสิทธิ์ได้ ให้การอ่าน/เขียนของผู้ใช้หนึ่งคนไม่ทับสถานะของอีกคน และให้ใช้งานได้หลังเปลี่ยนอุปกรณ์

## สิ่งที่ runtime ปัจจุบันทำได้ และสิ่งที่ต้องมีรุ่นแอปใหม่

| เรื่อง | Runtime ปัจจุบันทำได้ | ต้องมีแอปใหม่หรือสัญญาข้อมูลที่อนุมัติ |
|---|---|---|
| ห้องแชตที่มองเห็น | มีการตรวจ role/สิทธิ์และเจ้าของใบงานในบางเส้นทาง แต่ยังไม่มีหลักฐานยืนยันว่า gateway กรอง `fs_chats`/`fs_messages` ตาม visible-room scope; runtime ลดข้อมูลใน `localStorage` หลังรับข้อมูลกลางแล้ว ซึ่งไม่ใช่การกรองสิทธิ์ | ตรวจ endpoint และเพิ่ม/ยืนยัน server-side room filter ก่อนส่งข้อมูล; เปลี่ยนตัวโหลดแอปให้ขอเฉพาะห้องที่มองเห็น และจัดการหน้า/คิวเมื่อสิทธิ์เปลี่ยน; จนกว่าจะพิสูจน์ให้ถือว่าการกรองยังไม่ทำ |
| `fs_users`, `fs_meta` | gateway ปฏิเสธหรือกรองคำขอที่ไม่มีสิทธิ์ได้; มีทางเฉพาะบางรายการ เช่น `/sb/session` | เอาคำขออัตโนมัติ/การเขียนทั้งชุดออกจาก sealed client; `fs_meta` โดยเฉพาะต้องใช้ API เฉพาะงาน เช่น ตัวนับที่ server-owned |
| Role/grant | runtime bridge สามารถเผยแพร่ผลจาก `/sb/session`; gateway ยังคงผู้ตัดสินสิทธิ์ | แอปต้องเลิกใช้ `ROLES` เป็นแหล่งอนุญาตสำหรับความสามารถที่ IAM คุม และแสดงสถานะกำลังตรวจ/ปฏิเสธโดยไม่เปิดสิทธิ์ชั่วคราว |
| ปฏิเสธและกู้คืน | gateway ส่งรหัสเหตุผลและบันทึกเหตุการณ์แบบไม่ต้องเปิดเนื้อหาธุรกิจได้ | แอปต้องเชื่อมรหัสเหตุผลกับข้อความที่เข้าใจได้ ปุ่มลองใหม่ และการเก็บคิวเดิมอย่างปลอดภัย |
| ประวัติเวอร์ชัน | source ใน repository มีทางอ่านเวอร์ชันกลางและผสานเข้าหน้าประวัติ; สถานะ release parity และ production ยังต้องตรวจ จึงยังไม่ถือว่าใช้งานจริง | ตรวจ approved artifact และ production parity ก่อนอ้างความพร้อม; หากจะย้าย UI/ทางเก็บประวัติไปอยู่ในแอปโดยตรง ต้องออกแอปและรักษาความเข้ากันได้กับเส้นทาง runtime ที่อนุมัติ |
| สถานะอ่าน | ปัจจุบันมีการเก็บในเบราว์เซอร์พร้อม IndexedDB เป็นสำเนาช่วยเมื่อ localStorage เต็ม | ย้ายหลักฐานสถานะอ่านไปบริการกลางต้องกำหนดเจ้าของข้อมูล/API/สิทธิ์/การย้ายค่าที่มีอยู่; อาจต้องแก้ schema หรือเพิ่ม endpoint จึงเป็น Critical Change หากกระทบ schema/สิทธิ์ |

## ความเสี่ยงและข้อจำกัด

- `fs_users`, `fs_meta`, `fs_chats`, `fs_messages` และโครงสร้างประวัติเวอร์ชันมีสัญญาที่ใช้งานอยู่ การเปลี่ยน key, ฟิลด์, รูปแบบข้อมูล หรือสิทธิ์โดยไม่มีแผนรองรับรุ่นเก่าอาจทำให้บันทึกไม่ได้หรือทำให้ข้อมูลสูญหาย
- การซ่อนห้องในหน้าจอไม่ใช่การควบคุมสิทธิ์ ต้องกรองที่เซิร์ฟเวอร์และตรวจทุก endpoint; cache เก่าต้องไม่เปิดข้อมูลหลัง role หรือ scope เปลี่ยน
- สถานะอ่านส่วนกลางต้องแยกตามผู้ใช้และห้อง และจัดการกรณีออฟไลน์/ชนกัน/บัญชีเปลี่ยน โดยไม่เขียนทับค่าของคนอื่น
- การใช้ประวัติเวอร์ชันกลางทำให้ข้อมูลก่อนแก้สะสมในระบบกลาง ต้องกำหนดระยะเก็บ การเข้าถึง และการตรวจสอบการกู้คืน ผู้ใช้ที่ไม่มีสิทธิ์อ่านใบงานต้องไม่เห็นเวอร์ชัน
- ทางเชื่อม runtime ที่ดัดแปลงโค้ดแอป sealed อาจหยุดทำงานเมื่อข้อความต้นทางเปลี่ยน ต้องล้มแบบปิดและตรวจความตรงกับ release ที่อนุมัติ
- จำนวน 243 และค่าพื้นที่เก็บเป็นหลักฐานในช่วงเวลาที่ระบุ ไม่ใช่ตัวเลขสดหรือเป้าหมายออกแบบที่อนุมัติแล้ว

## ลำดับดำเนินงานที่เสนอ

1. **ยืนยันกฎธุรกิจ**: เจ้าของระบบยืนยันนิยาม “มองเห็นห้อง” แหล่งสิทธิ์/ขอบเขตห้อง และผู้มีอำนาจกู้เวอร์ชัน
2. **ตรวจสัญญาปัจจุบัน**: ระบุ API, key/ฟิลด์ที่ล็อก, ข้อมูลเก่า, การใช้งาน offline และความเข้ากันได้ระหว่าง release; บันทึกใน `REGISTRY.md` หรือเอกสารตัดสินใจที่เกี่ยวข้องก่อนออกแบบ migration
3. **ทำ runtime ทางฝั่งเซิร์ฟเวอร์**: ให้ตัวกรองห้องและการปฏิเสธมีผลจริง, ปิดทางเขียนเบราว์เซอร์ที่ไม่จำเป็น, เพิ่ม endpoint เฉพาะสำหรับรายการที่ยังต้องใช้; ห้ามทดสอบโดยใช้ production payload
4. **ทำแอปรุ่นใหม่**: เปลี่ยนตัวโหลดแชต, ตัวตัดสินการแสดงผลตาม `/sb/session`, ป้ายปฏิเสธ/ลองใหม่, การอ่านเวอร์ชันกลาง และสถานะอ่านกลาง โดยคงการบันทึกผ่าน gateway เดิม
5. **ตรวจด้วยข้อมูลสังเคราะห์**: ทดสอบบทบาทที่มี/ไม่มีสิทธิ์, ห้องที่เห็น/ไม่เห็น, เปลี่ยน role ระหว่างเปิดแท็บ, เน็ตขาด, เซิร์ฟเวอร์ปฏิเสธ, คิวค้าง, การใช้หลายอุปกรณ์ และสถานะอ่านชนกัน
6. **เปิด PR และผ่านการตรวจอิสระ**: เนื่องจากแตะ runtime, สิทธิ์ และอาจแตะ schema ให้จัดเป็น Critical Change; ต้องผ่าน CODEOWNER/ผู้ตรวจที่กำหนดและ checks ก่อนการอนุมัติ release
7. **UAT และปล่อยแบบควบคุม**: ใช้ผู้ทดสอบ/ข้อมูลสังเคราะห์หรือขอบเขตที่เจ้าของอนุมัติ, บันทึก backup/checksum, commit/artifact ที่แน่นอน, health check, parity และแผนย้อนกลับก่อน deploy

## แผนทดสอบที่ต้องจัดทำก่อนอนุมัติการพัฒนา

- ผู้ใช้ที่มีสิทธิ์ได้รับเฉพาะห้องที่มองเห็น; ผู้ไม่มีสิทธิ์ไม่ได้รับทั้ง metadata และข้อความของห้องที่ซ่อน
- ไม่มีคำขอจากเบราว์เซอร์ที่เขียน `fs_users`/`fs_meta`; คำขอที่ถูกปฏิเสธไม่หยุดการซิงก์ส่วนอื่นโดยไม่แจ้งผู้ใช้
- ค่าบทบาทที่ปลอมใน browser storage/body ไม่เปลี่ยนผล `/sb/session` และไม่ผ่าน gateway
- เมื่อสิทธิ์หมดอายุ/เซิร์ฟเวอร์ล่ม UI แสดงสถานะปิดการเขียนอย่างชัดเจน คิวที่ยังไม่บันทึกคงอยู่ และลองใหม่ได้หลังเซสชันกลับมา
- ประวัติเวอร์ชันแสดงเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์ดู; restore ผ่านกฎเขียนปกติและบันทึก audit ตามเดิม
- สถานะอ่านแยกตาม user/room, โหลดคืนหลังเข้าสู่ระบบอีกอุปกรณ์, และไม่สูญเมื่อ local storage เต็มหรือ offline ชั่วคราว
- ทดสอบรุ่นก่อน/รุ่นใหม่ร่วมกันและ rollback: ไม่มีข้อมูลถูกลบหรือเขียนทับระหว่างการเปลี่ยนผ่าน

## แผนย้อนกลับ

- ให้เก็บ release เดิมและ immutable artifact/commit ที่อนุมัติไว้ พร้อม backup และ checksum ก่อนแตะ production
- หาก UI รุ่นใหม่ผิดพลาด ให้ย้อนแอปไป release เดิมที่ยังเข้ากันได้; คง endpoint แบบอ่านและข้อมูลกลางที่เพิ่มไว้จนตรวจผลกระทบครบ ห้ามลบประวัติหรือสถานะอ่านที่สร้างใหม่โดยอัตโนมัติ
- หาก endpoint/runtime ผิดพลาด ให้ปิดเฉพาะทางใหม่ผ่าน release ที่ผ่าน review แล้ว; กลับไปใช้เส้นทางเดิมเฉพาะเมื่อยังผ่านสิทธิ์และไม่ทำให้ข้อมูลรั่ว/สูญ
- schema migration ถ้ามี ต้องมี rollback ที่ทดสอบแล้วและ backward-compatible; การย้อนโค้ดไม่ทำให้ข้อมูลในตารางถูกลบเอง
- หยุดและแจ้งเจ้าของเมื่อ parity, backup/checksum, สิทธิ์, หรือเงื่อนไข rollback ไม่ผ่าน ห้ามแก้ source/schema ตรงใน production

## การตัดสินใจที่ยังเป็นของ System Owner

1. อนุมัตินิยาม “ห้องที่มองเห็น” และแหล่งข้อมูลสิทธิ์ที่เป็น authoritative รวมถึงพฤติกรรมเมื่อสิทธิ์เปลี่ยนระหว่างเซสชัน
2. อนุมัติการย้ายสถานะอ่านขึ้นระบบกลางหรือเลือกคงสถานะเฉพาะเครื่อง พร้อมกำหนดอายุข้อมูลและนโยบายใช้งานออฟไลน์
3. กำหนดระยะเก็บและผู้มีสิทธิ์ดู/กู้ประวัติเวอร์ชันกลาง
4. กำหนดการกู้คืนเมื่อถูกปฏิเสธ: ผู้ใช้ลองใหม่เองได้เมื่อใด และกรณีใดต้องให้ผู้ดูแลแก้สิทธิ์
5. ยืนยันว่ารุ่นเก่าจะถูกปิด/หมดอายุอย่างไรเมื่อรุ่นใหม่เปลี่ยนสัญญาการอ่านหรือเขียน
6. อนุมัติ migration/schema หรือ endpoint ใหม่เป็นงาน Critical แยก พร้อม reviewer, backup, UAT และ release window

## ขอบเขตเอกสารนี้

การเปลี่ยนแปลงใน PR นี้เป็นเอกสารเท่านั้น ไม่มีการแก้ runtime, แอป, SQL/schema, IAM, production data หรือ dependency; ไม่ได้อนุมัติให้พัฒนา, merge หรือ deploy ข้อเสนอนี้
