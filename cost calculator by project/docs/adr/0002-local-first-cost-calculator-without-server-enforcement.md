# Local-first Cost Calculator without server-enforced cost segregation

## Decision

System Owner เลือกให้ Cost Calculator เป็น **local-first เต็มรูปแบบ** เก็บข้อมูลใน `localStorage` แบบเดียวกับ `fs_records` และ **ไม่ใช้ Supabase** เป็นผู้ตัดสินสิทธิ์ ตัดสินเมื่อ 2026-09-05 หลังได้รับแจ้งผลกระทบด้านการเปิดเผยข้อมูลอย่างชัดเจนแล้ว

การตัดสินใจประกอบอีกสามข้อในรอบเดียวกัน:

- แทน 7 บทบาทด้วย **ตารางสิทธิ์แยกต่างหาก** ไม่แตะ `fs_memberships` role enum ที่ล็อกไว้
- **RD เปิดได้ทุกโครงการ** ไม่ผูกกับการมอบหมายรายโครงการ
- **deep link ดู revision เก่าได้เฉพาะ RD และ Admin**

## ผลที่ยอมรับแล้ว

ตัวเลือกที่เลือกระบุไว้ตรง ๆ ว่า *"การแยก RM/PK เป็นแค่ UI ทุกคนที่เปิดเครื่องได้อ่านราคาซัพพลายเออร์ทั้งหมด"* ดังนั้น:

1. การแยก Procurement RM ออกจาก PU-PK, การกัน RD ไม่ให้เห็นราคา PK, และการกัน Sales/OPC ไม่ให้เห็นราคาซัพพลายเออร์ **เป็นการควบคุมการแสดงผล ไม่ใช่การควบคุมการเข้าถึง** ใครเปิด devtools หรืออ่าน `localStorage` ก็เห็นข้อมูลดิบทั้งหมด
2. ตารางสิทธิ์แยก (ข้อ 1) และขอบเขต deep link เฉพาะ RD/Admin (ข้อ 4) จึงเป็น **ข้อตกลงระดับ UI** ไม่ใช่ security boundary
3. รายการใน `SECURITY_VERSION_CONTRACT.md` หัวข้อ "Trusted access boundary" และ acceptance ข้อ 2–4 (ยิง REST/RPC ตรงด้วยบัญชีสังเคราะห์, RD อ่าน PK ไม่ได้, ปฏิเสธ forged confirmation) **ทำไม่ได้ในโหมดนี้** ไม่ใช่ TODO ที่ค้างอยู่ — ต้องเปลี่ยนสถาปัตยกรรมก่อนจึงจะกลับมาทำได้
4. ข้อมูลต้นทุนที่อ่อนไหวจะอยู่บนเครื่องผู้ใช้แต่ละคน การถอนสิทธิ์ภายหลังไม่สามารถเรียกคืนสำเนาที่ผู้ใช้มีอยู่แล้วได้

## ทำไมจึงไม่ขัดกฎภายใน

Formula Studio มี local-only mode อยู่แล้วที่ Role เป็นฝั่ง client และใช้ `pwHash()` เป็นการอำพรางเท่านั้น (CLAUDE.md กฎข้อ 8 และ 9) การตัดสินใจนี้จึงสอดคล้องกับโหมดที่ระบบรองรับอยู่ ไม่ใช่การเลี่ยง control ที่มีอยู่ กฎข้อ 8 ยังบังคับใช้ในความหมายเดิมคือ ฟังก์ชันที่ลงมือทำจริงต้องตรวจสิทธิ์ ไม่ใช่ซ่อนปุ่มอย่างเดียว แต่ในโหมดนี้ "สิทธิ์" คือสิทธิ์ฝั่ง client ตามที่ระบบ local-only นิยามไว้

กฎข้อ 2 ไม่ถูกละเมิด: เพิ่ม `localStorage` key ใหม่เป็นการเพิ่มแบบ additive ไม่เปลี่ยนชื่อ ไม่ลบ และไม่แก้ชนิดข้อมูลของ key ที่ล็อกไว้ store ใหม่ต้องมี loader ของตัวเองและห้ามเขียนก่อน loader ทำงานเสร็จ ตามกฎข้อ 4

## สิ่งที่เก็บไว้ ไม่ลบ

`supabase/migrations/20260905140000_cost_gateway_contract.sql` และ `tests/sql/cost_gateway_test.sql` **ยังคงอยู่และยังต้องผ่าน** ไม่ได้ต่อเข้ากับ Cost Calculator ภายใต้การตัดสินใจนี้ แต่เก็บไว้เป็นทางเลือกที่ผ่านการตรวจแล้วสำหรับกรณีที่เจ้าของระบบต้องการ server-enforced segregation ในภายหลัง `run-sql-tests.sh` ยังเรียก migration นั้นอยู่ และ SQL suite ยังเป็นเกณฑ์บังคับตามกฎข้อ 7

`COST_GATEWAY_CONTRACT.md` อธิบาย gateway ที่ calculator ไม่คุยด้วยแล้ว เอกสารนั้นถูกติดสถานะกำกับไว้ที่หัวไฟล์ ไม่ได้เขียนใหม่และไม่ได้ปล่อยให้อ่านเหมือนยังเป็นสถานะปัจจุบัน

## ทางเลือกที่ไม่เลือก

- **Supabase RPC ตรง** — บังคับสิทธิ์ได้จริงและมี migration พร้อมแล้ว แต่เจ้าของระบบไม่ต้องการผูกกับ Supabase
- **Apps Script เหมือน PU-PK** — ยังมี server ตัดสินสิทธิ์และต่อยอดจาก `RmData.gs`/`PkAdapter.gs`/`CostWorkflow.gs` ที่มีอยู่ ไม่ถูกเลือก
- **สร้าง service `/v1/cost/*`** — เป็น component ใหม่ที่ต้อง deploy และต้อง security review เพิ่ม ไม่ถูกเลือก

## ผลต่อสถานะงาน

สถานะโดยรวมยังเป็น LOCAL_VERIFIED / INTEGRATION_BLOCKED และยังไม่ใช่ 27/27 การตัดสินใจนี้ปลด blocker ข้อ 1–4 ในรายการของ `COST_GATEWAY_CONTRACT.md` §7 ด้วยการเปลี่ยนสถาปัตยกรรม ไม่ใช่ด้วยการทำให้สำเร็จ ส่วน blocker ข้อ 6 (PK source semantics) และข้อ 7 (UAT/review/deploy) ยังเปิดอยู่เหมือนเดิม
