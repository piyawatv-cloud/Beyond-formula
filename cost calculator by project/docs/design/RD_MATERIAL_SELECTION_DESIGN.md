### ข้อสรุปที่เปลี่ยนจากรอบแรก

ควรปรับ RD Data Center จริง เพราะปัจจุบันมีทั้งหน้าค้น หน้า mapping หลักฐานราคา ทำสูตร และทบทวนจัดซื้อซ้อนกันอยู่ ไม่ใช่เพียงปัญหาความสวยงาม แต่เป็นความสับสนว่าหน้าใดใช้ “เลือก” และหน้าใดใช้ “ยืนยัน”

แนะนำให้ปรับ 00_README เป็นทางเข้าตามหน้าที่, ใช้ 01 เป็นมุมมองค้นสำหรับ RD ที่เน้น spec และข้อเสนอ, ให้ 02/08/parent/tier/raw เป็นงานผู้ดูแล, และกำกับ 03/09 ว่าบทบาทสัมพันธ์กับ Cost Calculation อย่างไรหลังตรวจผู้ใช้งานเดิม ไม่ลบ tab หรือ business rules

### ประเด็น mapping ที่ยังต้องตรวจ ไม่ควรกลบด้วย UI

ผู้ใช้ยืนยัน workbook แล้ว แต่ไม่ได้ยืนยันว่า tab ใดเป็น authoritative offers สำหรับ calculator:
- code costParseCatalogWorkbook ตรวจ Name/Supplier/Price/kg/MOQ เพื่อเข้า RmPriceSource ก่อน
- Price of Ingredients ที่เห็นจริงเป็น parent/raw schema คนละรูปทรง จึงไม่ใช่หลักฐานว่าแท็บนี้เข้า direct-price route ได้
- code ยังมี fallback RD-Code + Price Tiers (Raw) ผ่าน RmCatalogBuild; workbook นี้มี 02_Price_Map รูปทรงดังกล่าว
- ยังไม่ตรวจ raw tabs ทุกหน้า จึงไม่อ้างว่า workbook จะเข้า route ใดแน่นอน หรือแปลงไม่ได้ทั้งไฟล์
- ก่อน implementation ให้ตรวจ header mapping + completeness + version/confirmation provenance จาก snapshot ที่ได้รับอนุญาต เปรียบเทียบจำนวน record ตาม route; ไม่กลับไปจับคู่แบบกำกวม ไม่ทำ engine ราคาใหม่
- การชี้แหล่ง RM ครั้งนี้ไม่เปลี่ยน PK owner หรือกฎ local-first และไม่ได้ authorize เปลี่ยน source/schema/runtime

สถานะ: **design review มีหลักฐานหน้าจอจริงแล้ว**; รอ manual walkthrough และตัดสิน mapping/บทบาทหน้าที่ก่อนแก้ app/Sheet. ไม่มี UAT, live import test, deployment หรือการยืนยันค่าธุรกิจในรอบนี้.

## ข้อสรุป

ควรปรับทั้งหน้าเลือกในสูตรและมุมมองของ RD Data Center แต่ไม่ควรนำ Data Center กลับมาเป็นตัวกลางจับคู่ราคาอีกครั้ง ปัญหาหลักคือ RD ต้องประกอบข้อมูลสำหรับตัดสินใจเองจากหลายตำแหน่ง ทั้งที่การค้นหาเร็วแล้ว

ให้ RD ทำงานในพื้นที่เดียว: ชื่อสารในสูตร → ดูวัสดุที่ต่าง spec → เปรียบเทียบผู้ขาย/Tier → ตรวจผลต่อปริมาณที่ต้องใช้ → เลือกด้วยตัวเอง → ใส่ปริมาณ/ไปแถวถัดไป โดยไม่ต้องออกไปค้น sheet อีกครั้งในกรณีข้อมูลครบ

หน้าดูแลข้อมูลทำหน้าที่เตรียมและแก้ข้อเสนอให้พร้อมใช้ แยกจากหน้าตัดสินใจของ RD ใช้ record/offer IDs และกฎเดิม ไม่มี master หรือ calculation engine ใหม่

## 2. สิ่งที่ต้องลด

- ลดการสลับจากแถวสูตรไปตารางค้นหาอีกชุด
- ลดการอ่านชื่อยาวซ้ำทุก Tier เพื่อหาว่าวัสดุต่างกันตรงไหน
- ลดการจำ spec, MOQ และ LT จากแถวหนึ่งไปอีกแถว
- ลดการเปิด sheet เพียงเพื่อตรวจที่มา/เงื่อนไข
- ลดการถามจัดซื้อซ้ำว่าข้อมูลขาดอะไร โดยแสดงเจ้าของและทางไปแก้
- ห้ามลดการตรวจ spec หรือเงื่อนไขเพื่อให้เร็วขึ้น

## 3. หน้าสำหรับ RD — ตัวเลือกวัสดุหนึ่งชุดใช้ร่วมกัน

วางแถวสูตรทางซ้าย และพื้นที่ค้น/เทียบขนาดกว้างทางขวาภายใน tab เดิม (จอแคบเป็นพื้นที่เต็มกว้างพร้อมปุ่มกลับแถว) คลิก “เลือก/เปลี่ยนวัสดุ” แล้วคงชื่อแถว ปริมาณ หน่วย และ revision ไว้ด้านบน

ลำดับการแสดง:
1. ค้นด้วยชื่อที่ Formula ส่งมาเป็นค่าเริ่มต้น แก้คำค้นได้; ไทย/อังกฤษ/ชื่อเรียกตามกฎเดิม ไม่มี fuzzy substitution
2. แสดง “N วัสดุ / M ข้อเสนอ” ไม่สับสนจำนวนวัสดุกับจำนวน Tier
3. วัสดุแสดงเป็นกลุ่มทางสายตา ชื่อ/ความเข้มข้น/grade/form/origin เท่าที่มีข้อมูลยืนยัน ไม่สร้าง identity ใหม่จากชื่อกลุ่ม
4. แต่ละวัสดุเปิดดูผู้ขายและ Tier ภายในได้ มีปุ่มดูผลทั้งหมด/โหลดเพิ่มที่ไม่เปลี่ยนคำค้นหรือเป้าหมายแถว
5. เลือกช่องเทียบได้ 2–3 ข้อเสนอ ตารางเทียบตรึงชื่อแถวและหน่วยเดียวกัน
6. เลือกข้อเสนอด้วยตัวเอง จากนั้นกรอกปริมาณหรือใช้ปริมาณที่ RD กรอกไว้แล้ว ไม่ดึง w จาก Formula
7. คงรูปแบบบันทึก revision เดิม; ระหว่างเลือกหลายรายการต้องไม่ทำ draft ที่กรอกค้างหาย ไม่เพิ่ม auto-save

ค้นทั้งแคตตาล็อกยังเปิดได้เมื่อ RD ต้องการสำรวจ แต่เรียกตัวเลือกเดียวกัน พร้อมแสดงว่าจะเพิ่มแถวใหม่หรือเปลี่ยนแถวใด ห้ามเพิ่ม duplicate แทนแถวเดิมโดยไม่ตั้งใจ

### ข้อมูลที่เห็นก่อนกดเลือก

| กลุ่ม | ข้อมูล |
|---|---|
| เหมาะกับสูตรหรือไม่ | ชื่อที่ RD รู้จัก + ชื่อเต็ม, spec ที่มีหลักฐาน, จุดต่างระหว่างตัวเลือก, ข้อจำกัดการใช้ |

| มีผลต่อต้นทุนอย่างไร | ราคา/kg ที่ normalize แล้ว; เมื่อตั้งปริมาณและจำนวนผลิตครบจึงแสดงต้นทุนใช้จริง/เงินซื้อประมาณการ/ของเหลือแยกกัน |
| เชื่อถือได้แค่ไหน | จัดซื้อยืนยัน/รอยืนยัน, RD รับรอง spec/รอรับรอง, วันที่/เวอร์ชันและที่มาข้อมูล |
| ต้องทำอะไรต่อ | ใช้ข้อเสนอนี้ / RD ตรวจรับรอง spec / ขอจัดซื้อเติมเงื่อนไข / ขอจัดหา |

ใช้ deterministic core เดิมสำหรับราคาและจำนวนซื้อเท่านั้น ไม่มีเครื่องคำนวณใน component เพิ่ม เมื่อข้อมูลไม่ครบแสดง “ยังคำนวณผลต่อจำนวนงานไม่ได้” ไม่ใส่ 0 ไม่แสดงเงินซื้อเท่ากับต้นทุนใช้จริง และไม่อ้างว่าของเหลือขายได้

## 4. RD Data Center ควรปรับไหม

ควรปรับ “มุมมองและความหมายของข้อมูล” ถ้ายังให้ RD ใช้ค้นจริง แต่ไม่ควรปรับทั้ง 26 ตารางหรือสร้างระบบใหม่ก่อนพิสูจน์ว่าหน้าไหนยังถูกใช้อยู่

แยกสามมุมมองบนข้อมูลเดิม:
- **RD ค้นวัสดุ:** ชื่อ/ชื่อเรียก/spec/ข้อเสนอ/ความพร้อม โดยแสดงชัดว่าราคามาจากข้อเสนอไหน หน้านี้ใช้รูปแบบเดียวกับตัวเลือกในสูตร
- **จัดซื้อดูแลข้อเสนอ:** คิวขาดข้อมูลและเปลี่ยนเงื่อนไข กรองตามวัสดุ/ผู้ขาย/เหตุที่ค้าง ดูเฉพาะที่ต้องแก้ ไม่ต้องไล่ทุกคอลัมน์
- **ผู้ดูแลตรวจนำเข้า:** source row, identity, normalization warnings, rejected rows, รุ่นไฟล์และประวัติ ไม่กอง DQ ทั้งหมดให้ RD อ่าน

ถ้า RD Data Center เป็น Google Sheet:
- ปรับ filter view/freeze header/group columns/ลิงก์กลับหลักฐานในตารางเดิมก่อน
- ซ่อนคอลัมน์เชิงเทคนิคจาก default RD view แต่ไม่ลบ ไม่ใช้การซ่อนเป็น security
- ป้าย “Mapped Price/Max Price” ต้องไม่ทำให้เข้าใจว่าเป็น Tier ที่เลือกสำหรับงาน; หากคงไว้ให้เป็นข้อมูลอ้างอิงชัดเจน
- ไม่เพิ่มสูตรราคาและการแปลง MOQ ชุดที่สอง ไม่เพิ่มตารางราคาอีกชุดให้จัดซื้อกรอกซ้ำ

ถ้าเป็น web UI ของ Data Center:
- ใช้ projection ของแหล่งที่อนุมัติและ component รูปแบบเดียวกันเมื่ออยู่ในแอปเดียวกัน
- ถ้าเป็นคนละระบบ ไม่สมมติว่ามี shared API; ตรวจ repository/owner/contract ก่อนเสนอ integration
- ไม่อ้างว่าใช้ component ร่วมกันได้ทันทีเพียงเพราะหน้าตาคล้ายกัน

**คำแนะนำลำดับแรก:** ปรับ selector ใน Cost Calculation ให้ RD ไม่ต้องเปิด Data Center เพื่อเทียบราคางานประจำ ส่วน Data Center เก็บบทบาทดูแลข้อมูล/ค้นความรู้ที่ยังจำเป็นไว้ ไม่บังคับทางผ่านราคาเดิมกลับมา

## 5. เจ้าของข้อมูลและความสด

| ข้อมูล | แหล่ง/เจ้าของที่รักษาไว้ | การเปลี่ยน |
|---|---|---|
| ราคา, MOQ, increment, LT, expiry, supplier | ชีตราคา/Procurement ตามเส้นทางปัจจุบัน | นำเข้าและยืนยันตามกฎเดิม |
| RD spec acceptance | RD ผ่าน action ปัจจุบัน | อย่ารวมเป็นปุ่มยืนยันซื้อของจัดซื้อ |
| ชื่อเรียกต้นทาง | จัดซื้อในชีต ตาม REGISTRY | ไม่เพิ่มหน้า RD แก้ชื่อกลางในรอบนี้ |
| alias ของสูตร | revision ของใบงานต้นทุน | แก้เฉพาะ revision ไม่เปลี่ยน source |
| ความจำการเลือก | fs_cost.picks เครื่องนี้ | ไม่ sync/ไม่ใช้แทนการรับรอง |
| ราคา/spec ที่ใช้ในสูตร | snapshot ตาม revision | ไม่เปลี่ยนย้อนหลังเมื่อ source เปลี่ยน |

ต้นทางและ local confirmation มีสองจุดเกิดข้อมูล การออกแบบนี้ไม่ย้าย authority หรือแก้ merge policy เงียบ ๆ ต้องแสดง source version, importedAt, ผู้ยืนยัน และ field provenance เท่าที่ระบบมีจริง เมื่อขัดกันให้ตรวจ current import/confirmation behavior ก่อนแก้

แคตตาล็อกต่างเครื่องเป็นข้อยอมรับเดิม แสดงแหล่ง/เวลา/เครื่องนี้ ไม่สร้าง sync fs_cost หรืออ้างว่าคำขอที่ RD บันทึกจะไปถึงเครื่องจัดซื้อเอง ถ้าทดลองหลายเครื่องต้องระบุวิธีส่งต่อที่ยอมรับอยู่ก่อน; การเพิ่ม transport เป็นงานแยกต้องอนุมัติ

## 7. วัดว่าเร็วกกว่า manual จริงหรือไม่

ใช้โจทย์ที่มีความยากเทียบกัน สลับลำดับ manual/current/proposed เพื่อลดผลจากการจำคำตอบ มีทั้งกรณีข้อมูลครบและไม่ครบ แยกเวลารอคนออกจากเวลาทำรายการ แต่รายงานเวลารวม end-to-end ด้วย

- ชื่อคล้ายแต่ spec ต่าง; supplier เดียวหลาย Tier; ผลตรงมากกว่า 5; ชื่อไทย/อังกฤษ; ไม่พบ; รอ spec; รอเงื่อนไขซื้อ; expiry; เปลี่ยน Tier ขณะมี draft; source ใหม่หลังบันทึก revision
- วัดเวลาถึงเลือกถูก+ใส่ปริมาณ, จำนวนเปิด sheet/สลับจุดอ่าน, เลือกผิด spec/Tier, ต้องถามคนช่วย, และเหตุที่เลือก
- เกณฑ์เดิมเฉลี่ย ≤30 วินาที/รายการยังคงไว้ เพิ่มเป้าหมายเสนอว่าต้องไม่ช้ากว่า manual ในชุดงานเดียวกันและไม่เลือกผิดในชุด UAT
- แยกเวลา lookup ปกติจาก procurement exception ไม่ใช้การกดปุ่ม disabled ซ้ำเป็นความล้มเหลวของ search
- ระบบแสดงผล <100 ms ไม่ทดแทนความสำเร็จของ RD; prototype ไม่ใช่หลักฐานว่า production workflow ผ่าน
