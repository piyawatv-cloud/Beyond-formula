# CROSS_PLATFORM_DESIGN — ข้อกำหนดหน้าจอ Formula Studio Mobile (iOS / Android)

สถานะ: ร่างข้อกำหนด (Draft v0.1) · ใช้กับ `mobile-preview/` ที่ยังเป็นข้อมูลจำลอง · ยังไม่ผ่านการตรวจโดยผู้ออกแบบ/เจ้าของงาน
อ้างอิง: Apple Human Interface Guidelines (HIG), Material Design 3 (M3), WCAG 2.x, `CLAUDE.md` / `AGENTS.md` ของโปรเจกต์

> **หน้าจอที่ใช้เป็นกรณีศึกษา:** คำขอมีช่อง `[ระบุชื่อหน้าจอ]` ที่ยังไม่ได้กรอก จึงเลือกหน้าจอหลักของแอปนี้ 3 หน้า คือ
> (A) รายการงาน/ภาพรวมงาน (B) รายละเอียดงาน + อนุมัติ (C) แชตของใบงาน
> ถ้าต้องการหน้าอื่น ให้แจ้งชื่อหน้า แล้วใช้หัวข้อ 2–6 เป็นแม่แบบ
> ข้อความเรื่องสเปกของ HIG/M3 ด้านล่างเป็นค่ามาตรฐานที่ทราบทั่วไป ต้องตรวจซ้ำกับเอกสารฉบับล่าสุดก่อนใช้จริง (ดูหัวข้อ 9)

## 1. หลักการ (TPS + ISO/IEC 33000)

| หลักการ | ความหมายในเอกสารนี้ |
|---|---|
| **Standardized Work** | ทุกหน้าจอใช้โครง IA เดียวกัน (หัวข้อ 2) ต่างกันเฉพาะชิ้นส่วนที่ระบุในหัวข้อ 4 ห้ามต่างโดยไม่มีเหตุผลที่บันทึกไว้ |
| **Poka-yoke (กันพลาด)** | ปุ่มที่ทำลายหรือเปลี่ยนสถานะ (อนุมัติ, ปิดงาน) ต้องยืนยัน, ปุ่มสิทธิ์ที่ไม่มีต้องไม่ปรากฏ **และ** ต้องกันที่ฟังก์ชันจริง (กฎ `CLAUDE.md` ข้อ 8) |
| **Jidoka (หยุดเมื่อผิดปกติ)** | ข้อมูลไม่ครบ/สิทธิ์ไม่พอ/เครือข่ายหลุด ต้องหยุดและบอกสาเหตุ ห้ามเงียบหรือเดา |
| **Muda (ลดความสูญเปล่า)** | งานหลักบนมือถือต้องเสร็จด้วยมือเดียว ไม่เกิน 3 แตะจากหน้าแรก |
| **Kaizen** | ทุกการเปลี่ยนแปลง UI ต้องมีเหตุผล + หลักฐานทดสอบ + บันทึกใน changelog (หัวข้อ 8) |
| **ISO/IEC 33000** | ทุกข้อกำหนดตรวจสอบได้ (มีเกณฑ์ผ่าน/ไม่ผ่านและหลักฐาน) และระบุระดับความสามารถของกระบวนการออกแบบ (หัวข้อ 8) |

## 2. Universal UX Layout (ใช้ร่วมกันทั้งสอง OS)

### 2.1 โครงสร้างข้อมูล (IA)
```
App
├─ งาน (Jobs)            ← หน้าแรก: รายการงานที่บทบาทนั้นเห็น (Sales/Oversea เห็นเฉพาะงานที่ตนสร้าง)
│   └─ รายละเอียดงาน     ← สถานะ, สูตร/แถวสาร, อนุมัติตามส่วนของบทบาท, ประวัติแก้ไขงาน
│       └─ แชตใบงาน      ← ข้อความ, ส่งออก Excel
├─ ภาพรวม (Dashboard)    ← ตัวเลขตามนิยาม dashStats เดียวกับเว็บ
└─ เพิ่มเติม (More)      ← ประวัติการทำรายการ (Admin), ผู้ใช้, นำเข้า/ส่งออก, ออกจากระบบ
```
เมนูที่จำกัดบทบาทไม่อยู่ในแถบหลัก (จำกัดแถบหลัก ≤ 5 รายการ) ให้อยู่ใน "เพิ่มเติม"

### 2.2 โซนนิ้วโป้ง (Thumb zone)
| โซน | ตำแหน่ง | ใส่อะไร |
|---|---|---|
| ง่าย | ล่างของจอ | แถบนำทางหลัก, การกระทำหลัก (สร้างงาน, ส่งข้อความ, อนุมัติ) |
| ปานกลาง | กลางจอ | รายการ, การ์ดงาน, สถานะ |
| ยาก | บนสุด | ชื่อหน้า, ปุ่มรอง (ค้นหา, กรอง, ย้อนกลับ) — ห้ามวางการกระทำที่ทำบ่อยหรือทำลายข้อมูลไว้ที่นี่เพียงที่เดียว |

กฎ: การกระทำหลักของหน้าต้องเอื้อมถึงด้วยนิ้วโป้งมือเดียว; การกระทำที่ย้อนไม่ได้ต้องไม่อยู่ชิดขอบล่างจนกดพลาดง่าย (เว้นจากแถบนำทาง ≥ 8 pt/dp หรือใช้ขั้นยืนยัน)

### 2.3 ขนาดตัวอักษรและเลย์เอาต์ยืดหยุ่น
- ใช้หน่วยสัมพัทธ์: iOS = Dynamic Type text styles; Android = `sp` (Font Scaling) — ห้ามกำหนดขนาดตัวอักษรแบบ px ตายตัว
- ต้องใช้งานได้ถึงขนาดใหญ่สุดของระบบ (iOS รวม Accessibility sizes; Android font scale ถึง 200%)
- ที่ขนาดใหญ่: ข้อความขึ้นบรรทัดใหม่ ไม่ตัดทิ้ง (`…` ได้เฉพาะชื่อยาวและต้องเปิดดูเต็มได้); แถวข้อมูลแนวนอนเปลี่ยนเป็นแนวตั้ง; ความสูงองค์ประกอบเป็น min-height ไม่ใช่ fixed
- ข้อมูลสำคัญ (รหัสงานรูปแบบ `A00001`, สถานะ) ต้องไม่หายเมื่อขยายตัวอักษร
- รองรับ Dark mode และ Safe area/ขอบจอ (notch, gesture bar, Dynamic Island, edge-to-edge บน Android)

### 2.4 สถานะที่ทุกหน้าต้องออกแบบ (Jidoka)
โหลด · ว่าง · ผิดพลาด (บอกสาเหตุและทางแก้) · ออฟไลน์ · ไม่มีสิทธิ์ (บอกว่าสิทธิ์ใดจำเป็น) · กำลังบันทึก/บันทึกแล้ว

## 3. Accessibility & Targets (บังคับทั้งสอง OS)

| หัวข้อ | iOS | Android | เกณฑ์ผ่าน |
|---|---|---|---|
| Tap target ขั้นต่ำ | **44 × 44 pt** | **48 × 48 dp** | ทุกองค์ประกอบที่แตะได้ ขยายพื้นที่แตะได้โดยไม่ต้องขยายภาพ |
| ระยะห่างระหว่างเป้าแตะ | ≥ 8 pt | ≥ 8 dp | ปุ่มที่ติดกันต้องไม่แตะพลาดข้าม |
| Contrast ข้อความปกติ | ≥ **4.5 : 1** | ≥ **4.5 : 1** | วัดด้วยเครื่องมือ ไม่ใช้สายตา |
| Contrast ข้อความใหญ่/ไอคอนสำคัญ/เส้นขอบฟอร์ม | ≥ 3 : 1 | ≥ 3 : 1 | ตาม WCAG 1.4.3 / 1.4.11 |
| ไม่ใช้สีอย่างเดียวสื่อความ | ต้องมีข้อความ/ไอคอนคู่กัน | เหมือนกัน | สถานะ "อนุมัติแล้ว/รอ" ต้องมีตัวอักษร |
| Screen reader | VoiceOver: label, trait, ลำดับโฟกัสตามการอ่าน | TalkBack: contentDescription, role, ลำดับโฟกัส | ทุกปุ่มไอคอนมีชื่อ; ปุ่มที่ปิดใช้งานบอกเหตุผล |
| Reduce Motion | เคารพ Reduce Motion | เคารพ animator duration scale | การเคลื่อนไหวไม่เป็นเงื่อนไขของงาน |
| Focus/คีย์บอร์ดภายนอก | Full Keyboard Access | focus ที่มองเห็นได้ | ใช้งานจบงานหลักได้โดยไม่แตะจอ |

> ตัวเลขอัตราส่วนสีของพาเลตจริงของแอปยังไม่ได้วัดในเอกสารนี้ — ดูหัวข้อ 9 ข้อ 1

## 4. Platform-Idiomatic Variations (ชิ้นไหนต้องต่างกัน)

| ชิ้นส่วน | iOS (HIG) | Android (Material 3) |
|---|---|---|
| **นำทางหลัก** | **Tab Bar** ล่าง 3–5 แท็บ ไอคอน + ป้าย, แท็บ "เพิ่มเติม" เก็บส่วนที่เหลือ | **Navigation Bar** (M3) ล่าง 3–5 จุดหมาย มี active indicator (pill) ; จอกว้าง/แท็บเล็ตใช้ Navigation Rail |
| **การกระทำหลักของหน้า (สร้างงาน)** | ปุ่มใน Navigation Bar ด้านบน (“+”) หรือปุ่มเต็มความกว้างใกล้ล่างของเนื้อหา; **ไม่ใช้ FAB** | **FAB** (หรือ Extended FAB "สร้างงาน") มุมขวาล่าง เหนือ Navigation Bar |
| **ย้อนกลับ** | ปุ่ม Back ซ้ายบน + **swipe จากขอบซ้าย** ต้องใช้ได้เสมอ ห้ามชนกับ gesture ในหน้า | Predictive Back / system back gesture + ปุ่ม Up ใน Top App Bar |
| **หัวหน้าจอ** | Large Title ที่ยุบเมื่อเลื่อน | Top App Bar (Small/Medium/Large) ยุบเมื่อเลื่อน |
| **เมนูการกระทำรอง** | Context Menu / Action Sheet จากด้านล่าง | Overflow menu (⋮) / Bottom Sheet |
| **ยืนยันการกระทำที่ทำลาย/เปลี่ยนสถานะ (อนุมัติ, ปิดงาน)** | Alert / Action Sheet ปุ่มทำลายเป็นสี destructive, มีปุ่ม Cancel | Dialog (M3) ปุ่มยืนยันอยู่ขวา, ข้อความอธิบายผลชัด |
| **รายการ** | List แบบ inset grouped; swipe action ซ้าย/ขวา (ต้องมีทางเลือกที่ไม่ใช้ swipe ด้วย) | List item (M3) ; swipe-to-action ต้องมีทางเลือกอื่น |
| **ตัวควบคุมฟอร์ม** | Segmented control, Switch, Date picker แบบ iOS | Chips, Switch, Date picker (M3) |
| **ช่องค้นหา/กรอง** | Search bar ใต้ Large Title; กรองด้วย Menu/Sheet | Search bar/SearchView (M3) ; กรองด้วย Filter chips |
| **การกรอกข้อความแชต** | แถบพิมพ์ติดคีย์บอร์ด, ปุ่มส่งขวา, รองรับ Return/ส่ง | แถบพิมพ์ติด IME, ปุ่มส่งขวา, ปรับตาม edge-to-edge/IME insets |
| **Haptics / เสียง** | UIFeedbackGenerator (เบา) เมื่ออนุมัติสำเร็จ | HapticFeedback ที่เทียบเท่า; ทั้งสองต้องปิดได้ตามระบบ |
| **แจ้งเตือน** | พักไว้ตามคำสั่งเจ้าของงาน — ยังไม่ออกแบบ | พักไว้ตามคำสั่งเจ้าของงาน — ยังไม่ออกแบบ |

**ข้อสรุปเรื่อง FAB:** Android ใช้ FAB สำหรับ "สร้างงาน" เฉพาะหน้ารายการงาน; iOS ไม่ใช้ FAB ให้ใช้ปุ่มในแถบด้านบนและ/หรือปุ่มปกติ ห้ามมี FAB และปุ่มเต็มความกว้างซ้ำกันบนหน้าเดียว

## 5. พฤติกรรมรายหน้าจอ แยกตาม OS

### 5.1 (A) รายการงาน / ภาพรวมงาน
**ทั้งสอง OS:** แสดงเฉพาะงานตามสิทธิ์บทบาท; การ์ดงานแสดง รหัสงาน, ลูกค้า/แบรนด์, สถานะอนุมัติ 4 ส่วน (pd, ra, rd, sales) เป็นข้อความ+ไอคอน; ค้นหารหัสงานได้; ดึงลงเพื่อรีเฟรช

| | iOS | Android |
|---|---|---|
| หัว | Large Title "งาน", ปุ่ม “+” ขวาบน (ถ้าบทบาทสร้างได้) | Top App Bar; **FAB "สร้างงาน"** ขวาล่าง (ถ้าบทบาทสร้างได้) |
| นำทาง | Tab Bar: งาน · ภาพรวม · เพิ่มเติม | Navigation Bar: งาน · ภาพรวม · เพิ่มเติม |
| กรอง | ปุ่มกรองเปิด Sheet (medium detent) | Filter chips แถวใต้ App Bar |
| การ์ด | แตะทั้งการ์ดเข้ารายละเอียด; swipe มีทางเลือกในเมนู | แตะทั้งการ์ด; long-press/overflow เป็นทางเลือก |
| ที่ขนาดตัวอักษรใหญ่ | การ์ดเรียงข้อมูลแนวตั้ง | เหมือนกัน |

### 5.2 (B) รายละเอียดงาน + อนุมัติ
**ทั้งสอง OS (กฎธุรกิจ ห้ามต่างกัน):**
- ปุ่มอนุมัติแสดงเฉพาะส่วนที่บทบาทมีสิทธิ์: PD→pd, RA→ra, RD→rd, Sales→sales, **MKT→pd เท่านั้น**, **Oversea→sales เท่านั้น**, Admin→ทุกส่วน
- ต้องมีขั้นยืนยันก่อนอนุมัติ/ปิดงาน และแสดงผลลัพธ์ชัดเจน (สำเร็จ/ถูกปฏิเสธ + สาเหตุ เช่น ไม่มีสิทธิ์/ข้อมูลถูกแก้ซ้อน)
- ประวัติแก้ไขงานแสดงเฉพาะหมวด job/formula

| | iOS | Android |
|---|---|---|
| โครง | Large/inline title, เนื้อหาเลื่อน, แถบการกระทำติดล่าง (ปุ่มเต็มกว้างตามสิทธิ์) | Top App Bar + Bottom app bar/ปุ่มกระทำติดล่าง; ไม่ใช้ FAB ซ้อนปุ่มอนุมัติ |
| ยืนยัน | Alert/Action Sheet | Dialog |
| ปุ่มเปิดแชต | แถวในเนื้อหา + ปุ่มใน nav bar | ปุ่มในเนื้อหา + action ใน App Bar |
| ออกจากหน้าที่แก้ค้าง | ถามยืนยันก่อนทิ้ง (เหมือนพฤติกรรมแชตที่ทดสอบแล้ว) | เหมือนกัน และครอบคลุม system back |

### 5.3 (C) แชตใบงาน
**ทั้งสอง OS:** ข้อความที่ยังไม่ส่งต้องไม่หายเมื่อสลับบทบาท/ย้อนกลับโดยไม่ถามยืนยัน (ทดสอบแล้วใน `chat-draft-native.test.mjs`); ข้อความแต่ละอันมีรหัสไม่ซ้ำ ห้ามนำรหัสที่ลบแล้วมาใช้ซ้ำ; ประวัติแชตคงอยู่แม้ลบงาน (นโยบายเจ้าของงาน — ฝั่งระบบจริงยังไม่ทำ)

| | iOS | Android |
|---|---|---|
| ช่องพิมพ์ | ติดเหนือคีย์บอร์ด, ปุ่มส่งขวา | ติดเหนือ IME, จัดการ insets; ปุ่มส่งขวา |
| ส่งออก Excel | ผ่าน Share Sheet | ผ่าน Share intent / Storage Access |
| เลื่อนไปล่าสุด | ปุ่มลอยเล็ก "ข้อความใหม่" (ไม่ใช่ FAB หลัก) | เหมือนกัน (Small FAB หรือ chip) |

## 6. ข้อกำหนดเชิงตรวจสอบ (Acceptance — ทุกข้อต้องมีหลักฐาน)

| รหัส | ข้อกำหนด | วิธีตรวจ | หลักฐาน |
|---|---|---|---|
| CP-01 | tap target ≥ 44pt (iOS) / 48dp (Android) ทุกองค์ประกอบที่แตะได้ | สคริปต์วัด bounding box + ตรวจมือบนอุปกรณ์จริง | รายงานจำนวนที่ต่ำกว่าเกณฑ์ = 0 |
| CP-02 | contrast ≥ 4.5:1 (ข้อความ), ≥ 3:1 (ใหญ่/ไอคอน/เส้น) ทั้ง Light/Dark | เครื่องมือวัดอัตโนมัติ | ตารางคู่สีพร้อมค่า |
| CP-03 | ใช้งานได้ที่ตัวอักษรใหญ่สุด (iOS AX5 / Android 200%) ไม่มีข้อความถูกตัดทิ้งโดยไม่มีทางเปิดดู | ทดสอบภาพ 3 ขนาด | ภาพหน้าจอ |
| CP-04 | การกระทำหลักของหน้าอยู่ในโซนนิ้วโป้ง | ตรวจตำแหน่งเทียบ 1/3 ล่างของจอ | ภาพ + ตำแหน่ง |
| CP-05 | iOS ไม่มี FAB; Android มี FAB เฉพาะหน้ารายการงาน | ตรวจโครงหน้า | ภาพ |
| CP-06 | ปุ่มอนุมัติตรงสิทธิ์ตามหัวข้อ 5.2 ทุกบทบาท และกันที่ฟังก์ชันจริง | เทสต์บทบาท (`oversea-mkt-native.test.mjs`, `role-journey-native.test.mjs`) | ผลเทสต์ |
| CP-07 | VoiceOver/TalkBack อ่านลำดับถูกและทุกปุ่มมีชื่อ | ทดสอบด้วยมือบนเครื่องจริง | บันทึกผล |

## 7. การกันพลาดและกรณีผิดปกติ (Poka-yoke / Jidoka)
- เครือข่ายหลุดระหว่างส่งข้อความ/อนุมัติ: เก็บค้างและแสดงสถานะ "ยังไม่ได้ส่ง" ห้ามแสดงว่าสำเร็จ
- อนุมัติซ้อน (409): แสดงข้อความ "ข้อมูลเปลี่ยนแล้ว โหลดใหม่" ไม่เขียนทับ
- 401/403: บอกว่าต้องเข้าสู่ระบบ/ไม่มีสิทธิ์ส่วนใด ไม่แสดงข้อผิดพลาดทั่วไป
- ห้ามแสดงหรือบันทึกความลับ/โทเคน/ข้อมูลที่ไม่ปิดบังลงใน UI, log หรือภาพตัวอย่าง
- ห้ามเปลี่ยนโครงสร้างข้อมูลที่ถูกล็อกจากงาน UI (กฎเหล็กอันดับ 2 ของโปรเจกต์)

## 9. สิ่งที่ยังไม่ยืนยัน (ต้องมีคนตอบ)
1. ค่า contrast จริงของพาเลตปัจจุบันใน `mobile-preview/index.html` ยังไม่ได้วัด — รอรันเครื่องมือวัด
2. ชื่อหน้าจอเป้าหมายจริงที่เจ้าของงานต้องการ (ช่อง `[ระบุชื่อหน้าจอ]` ว่าง) — รอเจ้าของงาน
3. ผลิตภัณฑ์ปลายทางคือ native app สองตัว, cross-platform framework หรือ PWA — มีผลต่อวิธีทำตามตาราง 4; รอเจ้าของงาน (APK ถูกพักไว้)

5. ผู้ทบทวนอิสระ (ISO/IEC 33000 L2) ยังไม่ได้กำหนด
