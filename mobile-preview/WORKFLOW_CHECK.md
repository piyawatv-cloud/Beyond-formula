# ตรวจ workflow หน้าจำลองมือถือ

อ้างอิงสำเนา `index.html` ในเครื่อง ซึ่งอาจต่างจากรุ่นที่ใช้งานจริง ข้อมูลทั้งหมดเป็นข้อมูลจำลองในหน่วยความจำ และหายเมื่อโหลดหน้าใหม่ การตรวจปุ่มหรือบทบาทจำลองไม่ใช่การรับรองสิทธิ์ของระบบจริง

| ขั้นตอนในระบบเดิม | ตัวอย่างมือถือ | หลักฐานและข้อจำกัด |
|---|---|---|
| รายการงาน ค้นหา กรอง และดูรายละเอียด | มี | ตรวจรายการหน้าจอ 8 บทบาท; Sales จำลองกรองตามบทบาทผู้สร้าง ไม่ใช่บัญชีบุคคลจริง |
| สร้าง/แก้บรีฟและระบุสาร | มีฟอร์มแบบพับ รวมชื่อสาร ปริมาณ แหล่งกำเนิด ความเข้มข้น หมายเหตุ และสารสำคัญ | ทดลองสร้างงานพร้อมสาร 2 รายการและดูผลคำนวณ; ยังไม่ยืนยันช่อง/กฎทุกกรณีกับผู้ใช้ |
| รายละเอียดและแก้สูตร PD | มี | ทดลองแก้ปริมาณหลังอนุมัติครบและเห็นสถานะกลับเป็น 0/4; บันทึกโดยไม่แก้ยังคง 4/4 |
| ตรวจสถานะ อย. | แสดงว่ายังไม่ตรวจ | ไม่มีฐานข้อมูลอ้างอิงในตัวอย่าง; ห้ามใช้ผลนี้ตัดสินใจด้านกฎระเบียบ |
| ห้องแชตและการอนุมัติ | มีข้อความและปุ่มจำลอง | เดินผ่านหน้าจอ Sales, PD, RA, RD จนครบ 4/4; ชุดทดสอบตรวจห้ามอนุมัติแทนฝ่ายอื่น; ไม่ส่งข้อความจริง |
| เงื่อนไขส่งออกจากแชต | ส่งออก Excel จำลองเมื่อครบ 4 ฝ่ายสำหรับ Admin/OPC | ทดสอบกรณีไม่ผ่านสิทธิ์และอนุมัติไม่ครบ; ตรวจหัวคอลัมน์สองชีตเทียบโค้ดเดิมและเปิดไฟล์ด้วยเครื่องมืออื่นแล้ว; ไม่ใช่เอกสารอนุมัติจริง |
| ปิด/เปิดงาน | มีสำหรับบทบาทจำลองที่กำหนด | ชุดทดสอบตรวจสิทธิ์และเปิดกลับ; ไม่เปลี่ยนสถานะระบบจริง |
| นำเข้า/ส่งออก | CSV, Excel งานเดียวและหลายงาน พร้อมแม่แบบตัวอย่าง | ทดลองนำเข้าแม่แบบเดิมที่ใส่ข้อมูลจำลอง, ตรวจรายการ 2 งานก่อนสร้างและจับคู่สาร, เปิดไฟล์ส่งออกงานเดียวด้วยโปรแกรมตรวจ Excel แล้ว; ทดสอบ XLS ในแบบจำลอง แต่ยังไม่ยืนยันความเข้ากันได้ครบกับระบบเดิม; มีหน้าพิมพ์ตัวอย่างสำหรับเลือกบันทึกเป็น PDF ผ่านอุปกรณ์ แต่ไม่ใช่รูปแบบ PDF เดิมและยังต้องทดสอบบนอุปกรณ์จริง |
| ประวัติและผู้ใช้งาน | กิจกรรมและบทบาทจำลอง | ไม่ใช่ประวัติ audit หรือบัญชีจริง; เพิ่ม/แก้บัญชีจริงไม่ได้ |

การตรวจรับที่ยังต้องทำ: ให้ตัวแทน Admin, Sales, PD, RA, RD, OPC, MKT และ Purchasing ทดลองงานของตนด้วยข้อมูลจำลอง รวมกรณีแก้ไข ย้อนกลับ ข้อมูลไม่ครบ และจอ/แป้นพิมพ์จริง; เปรียบเทียบรายละเอียดกับ baseline ที่เจ้าของระบบยืนยัน และบันทึกข้อแตกต่าง การตรวจนี้ยังไม่ใช่การอนุมัติใช้งานจริง

## ข้อมูลสูตรก่อนเชื่อมระบบเดิม (28 ต.ค. 2026)

**ห้ามใช้ตัวเชื่อมทดลองเขียนข้อมูลจริงในสภาพปัจจุบัน:** ฟังก์ชันแสดงผลของสำเนา `app/index.html` ในชุดส่งมอบใช้ `r.fda.cls`, `r.w.toFixed(2)` และ `r.actual.toFixed(2)` แต่หน้ามือถืออาจสร้างรายการสารที่ไม่มี `fda`, เก็บ `w` เป็นข้อความ และใช้ `actual: null` เมื่อข้อมูลไม่ครบ จึงอาจเปิดรายการในหน้าระบบเดิมไม่ได้ นอกจากนี้หน้าบรีฟมือถืออาจคง `fda` ที่มีอยู่เดิมโดยไม่ตรวจใหม่เมื่อแก้สาร ซึ่งอาจไม่สอดคล้องกับสูตรที่แก้; ยังไม่ได้ยืนยันผลต่อสถานะ อย. จริง

หลักฐานที่ทำซ้ำได้: `node mobile-preview/integration/legacy-render-compat.test.cjs` นำฟังก์ชัน `renderDashboard` จากสำเนาในชุดส่งมอบมาทำงานกับข้อมูลจำลอง ผ่านการตรวจว่าทั้งสามรูปแบบทำให้เกิดข้อผิดพลาด และแถวตัวอย่างที่มีรูปแบบครบผ่านถึงขั้นเพิ่มแถวในตาราง การตรวจหยุดที่ขั้นนั้น ไม่ใช่การทดสอบหน้าระบบเดิมทั้งหน้า หรือหลักฐานว่าชุดส่งมอบตรง production

ขั้นถัดไปต้องยืนยันรุ่นระบบเดิมและข้อกำหนดชนิดข้อมูล/ข้อมูล อย. กับเจ้าของงาน แล้วออกแบบการส่งต่อที่ไม่สร้างข้อมูล อย. ขึ้นเอง ไม่แปลงค่าว่างเป็นค่าจริง และเก็บข้อมูลที่ไม่ได้แก้ รวมทดสอบเปิดรายการข้ามสองระบบด้วยข้อมูลจำลองก่อนพิจารณาเชื่อมจริง

หลักฐานเพิ่มเติม `integration/legacy-derived-fixture.test.cjs`: เรียก `getRows` และ `checkFDA` ที่มีอยู่จริงจากสำเนาระบบเดิมทั้งสองชุด โดยเปลี่ยนเฉพาะ DOM และรายการอ้างอิงให้เป็นข้อมูลสมมติ เมื่อเปลี่ยนน้ำหนักจาก 100 เป็น 120 ที่ 50% ผลเปลี่ยนจาก 50 เป็น 60 และสถานะจำลองเปลี่ยนตามเกณฑ์สมมติ แถวที่ได้ไปถึงขั้นเพิ่มตารางของตัวแสดงผลชุดส่งมอบ วิธีนี้ชี้ว่าระบบเดิมสร้างค่าตัวเลขและสถานะประกอบด้วยกัน ไม่ควรนำสถานะเก่ามาใช้กับปริมาณใหม่ แต่ยังไม่ใช่ API ที่มือถือเรียกได้ ไม่ใช่ผล อย. และไม่ยืนยันรายการอ้างอิงหรือรุ่นที่ใช้งานจริง

### ตรวจข้ามตัวกลางและฐานข้อมูลจำลอง

- `node mobile-preview/integration/runtime-job-save.gateway.test.cjs`: 6 กรณีผ่าน รวมกรณีส่งแถวสารที่น้ำหนักเป็นข้อความผ่านตัวกลาง Formula Runtime จากชุดส่งมอบโดยใช้ upstream/IAM จำลอง พบการตอบบันทึกสำเร็จ แต่ฟังก์ชันแสดงผลเดิมแสดงแถวนั้นไม่ได้ upstream จำลองแทนฐานข้อมูล จึงไม่ใช่การทดสอบตัวกลางและ SQL จริงร่วมกัน
- `node mobile-preview/integration/runtime-job-save.pg.test.cjs`: ส่งข้อมูลตัวอย่างเดียวกันตรงไปยัง SQL ใน PostgreSQL ชั่วคราว ผลบันทึกสำเร็จและฟังก์ชันแสดงผลเดิมแสดงแถวไม่ได้ ชุดนี้ข้ามตัวกลางและระบบสิทธิ์ ทั้งสองการทดลองไม่ใช้ข้อมูลจริง
- หลักฐานสองส่วนประกอบกันแสดงช่องว่างของการตรวจรูปแบบ แต่ยังไม่ยืนยัน deployment ปัจจุบัน และไม่ใช่ข้อสรุปว่ามีข้อมูลเสียใน production ต้องเพิ่มจุดตรวจความเข้ากันได้ที่กำหนดร่วมกับเจ้าของระบบ พร้อมทดสอบข้ามระบบครบก่อนอนุญาตเขียนข้อมูลจริง

### แก้บรีฟและอ่านกลับผ่านตัวกลางจำลอง

`node mobile-preview/integration/runtime-job-save.gateway.test.cjs` ผ่าน 8 กรณี โดยจำลองบันทึกเดิมที่มีชนิดข้อมูลสารตามสำเนาระบบเดิม อ่านผ่านตัวกลาง ใช้โค้ดอ่านฟอร์มมือถือจริงแก้เฉพาะแบรนด์ บันทึกและอ่านกลับ พบค่าที่ไม่ได้แก้ยังตรงต้นฉบับและตัวแสดงผลเดิมไปถึงขั้นเพิ่มแถวในตาราง

ในการทดลองก่อนแก้ ใช้โค้ดฟอร์มเดียวกันแก้น้ำหนักจาก 100 เป็น 120 พบว่า `actual` เดิมยังเป็น 50 และค่าน้ำหนักกลายเป็นข้อความ แม้ตัวกลางทดลองตอบบันทึกสำเร็จ ตัวอย่างได้ปรับให้คำนวณ `actual` เป็น 60 แล้ว แต่ค่าน้ำหนักยังเป็นข้อความและข้อมูล อย. ไม่ได้ตรวจใหม่ ตัวแสดงผลเดิมยังเกิดข้อผิดพลาด ความเข้ากันได้จึงยังไม่ผ่าน ไม่ใช่หลักฐานว่ามีข้อมูลผิดใน production; ชุดทดสอบใช้บริการข้อมูลและตัวตนจำลอง ตัวแสดงผลหยุดหลังตรวจตาราง ไม่ใช่การทดลองทั้งหน้าหรือการทดสอบกับระบบจริง

### ตลาดปลายทางในบรีฟจำลอง

เพิ่มตลาด Domestic / Oversea และประเทศปลายทางตามสำเนา `app/index.html` ของชุดส่งมอบ: เลือก Oversea ต้องระบุประเทศ งานเก่าที่ไม่ได้เลือกตลาดยังเปิดได้ ไม่เชื่อมฐานข้อมูล; ตรวจกรอกและอ่านกลับบนหน้าทดลอง รวมทั้ง CSV, Excel งานเดียว และอ่าน Excel หลายงานที่มีหัวคอลัมน์ดังกล่าว ผลยังไม่ยืนยันกับเจ้าของงานหรือรุ่น production และ Excel หลังอนุมัติจากแชตจำลองรวมสองช่องนี้แล้ว แต่ช่องประวัติที่ไม่มีข้อมูลยังว่าง

### ตรวจไฟล์ Excel หลังอนุมัติจำลอง

เทียบหัวคอลัมน์และลำดับทั้งสองชีตกับ `CHAT_XLS_HEAD` และ `CHAT_ING_HEAD` จากสำเนาชุดส่งมอบโดยตรง ครอบคลุมตลาด ประเทศ และสารหลัก ทดสอบค่าตัวอย่างผ่าน `node mobile-preview/workbook.test.cjs` และเปิดไฟล์จำลองแยกด้วย openpyxl เพื่อตรวจชื่อประเทศ สารหลัก ป้ายอนุมัติจำลองและข้อความไม่ใช่ผลตรวจ อย. ผลไม่ยืนยันรุ่น production หรือข้อมูลประวัติที่หน้าตัวอย่างยังไม่มี ช่องดังกล่าวว่างและไม่ใช่เอกสารรับรอง

**ยังไม่ครบทุกบทบาท:** สำเนา `app/index.html` และ `runtime/formula-proxy.mjs` ในชุดส่งมอบมี 9 บทบาท รวม `oversea`; หน้ามือถือมี 8 บทบาทและยังไม่มี `oversea` สำเนาหน้าเดิมระบุว่า Oversea สร้างงาน แชต อนุมัติ Sales ส่งออกและปิดงานได้ โดยเห็นเฉพาะงานของตน; ตัวอย่างปัจจุบันไม่มีบัญชีบุคคลจริงและตัวกรอง Sales อาศัยชื่อบทบาท จึงไม่พิสูจน์การแยกงานรายบุคคล

## การคัดลอกงานและเจ้าของ — ยังต้องตัดสินใจ

หน้าเดิม `copyRecordToNewId` คัดลอกข้อมูลทั้งใบ กำหนดรหัสใหม่และเอาสถานะปิด/Reject ออก แต่คง `createdBy` และ `ownerEmail` เดิม; หน้ามือถือยังไม่มีขั้นตอนคัดลอก

ทดลองฟังก์ชันจากหน้าเดิมโดยจำลองส่วนหน้าจอ แล้วส่งข้อมูลที่ได้ผ่านตัวกลาง GitHub commit คงที่ถึง PostgREST/PostgreSQL ชั่วคราว: Sales เจ้าของเดิมคัดลอกสำเร็จและงานใหม่ยังเป็นของเดิม; MKT ผู้ใช้อื่นถูกปฏิเสธเมื่อสำเนายังคงเจ้าของเดิม; Admin ผู้ใช้อื่นบันทึกได้และสำเนายังคงเจ้าของเดิม ใช้บริการสิทธิ์/บัญชีสมมติ ไม่ได้ทดสอบปุ่มหน้าระบบเดิมจริง หรือ production และไม่ตัดสินว่านโยบายที่ถูกต้องควรเป็นอย่างไร
