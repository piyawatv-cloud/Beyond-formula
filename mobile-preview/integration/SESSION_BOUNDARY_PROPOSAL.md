# ข้อเสนอทดสอบการผูกคำขอบันทึกกับ session

สถานะ: รอเจ้าของระบบอนุมัติขอบเขตการทดลอง — ไม่ใช่การเปลี่ยนระบบจริงหรือการอนุมัติใช้งาน

## เหตุที่ต้องพิจารณา

การตรวจ session ก่อนและหลังส่งคำขอช่วยไม่ให้หน้าจอรับผลของบัญชีที่เปลี่ยนแล้ว แต่ไม่รับประกันว่าคำขอที่ส่งไปถึงตัวกลางใช้ session เดิม: คุกกี้อาจเปลี่ยนในช่วงระหว่างตรวจและส่ง ในการทดสอบ localhost ที่สลับบัญชีจำลองก่อนส่ง ตัวกลางรับคำขอด้วยบัญชีใหม่และบันทึกข้อมูล แม้ตัวเชื่อมรายงานว่าไม่สามารถยืนยันผลได้ นี่เป็นผลจากการจัดสถานการณ์จำลอง ไม่ใช่หลักฐานว่ามีเหตุการณ์นี้ใน production หรือช่องโหว่ของ client เดิมทั้งหมด

## ทางเลือก

1. **เสนอ:** ตัวกลางออกตัวระบุรอบ session แบบทึบที่ผูกกับ session ฝั่งบริการ แล้วตรวจว่าตรงกับ session ของคำขอบันทึกก่อนรับเข้าคิวหรือเขียนข้อมูล ต้องไม่ให้ตัวระบุนี้ใช้แทนการเข้าสู่ระบบ และไม่บันทึกลง log ตัวตนหรือ token ต้องไม่ถูกส่งมาเป็นสิทธิ์จากหน้าเว็บ
2. ตรวจ session ที่หน้าเว็บก่อนและหลังส่งเท่านั้น: แสดงผลผิดบัญชีน้อยลง แต่ไม่ป้องกันคำขอที่ถึงบริการภายใต้บัญชีใหม่ จึงไม่เพียงพอสำหรับการเขียนข้อมูลร่วม
3. ห้ามสลับบัญชีในหน้ามือถือ: ลดโอกาสในหน้าเดียว แต่ยังควบคุมการเปลี่ยน session จากแท็บหรืออุปกรณ์อื่นไม่ได้ จึงไม่เพียงพอเพียงลำพัง

## ขอบเขตการทดลองที่เสนอ

- ทำเฉพาะสำเนาทดสอบของตัวกลางและข้อมูลสมมติ บน localhost พร้อมให้เจ้าของระบบยืนยันว่าชุดส่งมอบนี้เป็น baseline ที่เหมาะสม ห้ามเปลี่ยน production, schema, ระบบสิทธิ์จริง หรือ secrets
- ทำ endpoint ตรวจ session และคำขอบันทึกให้รับหลักฐานการผูกกับรอบ session โดยตัวกลางตรวจร่วมกับคุกกี้/การยืนยันตัวตนเดิมก่อนสร้างคิวหรือส่งเขียนฐานข้อมูล; ออกแบบรูปแบบให้สอดคล้องกับวิธี login/logout และระบบสิทธิ์เดิมหลังตรวจโค้ดเพิ่มเติม
- ทดสอบเซสชันเดิมสำเร็จ, สลับบัญชี/ออกแล้วเข้าบัญชีเดิม, คำขอเก่า, บัญชีหมดอายุ, สิทธิ์ถูกถอน, คำขอซ้ำ, คำตอบหาย และไม่ส่งรายละเอียด session ลง log; ตรวจว่าการปฏิเสธเกิดก่อนสร้างคิวและก่อนบันทึก
- หากต้องแก้ `runtime/formula-proxy.mjs` หรือสัญญา session ถือเป็น Critical Change ตาม [AGENTS.md](../../AGENTS.md) ต้องอยู่ใน repository/feature branch ที่ถูกต้อง ผ่าน independent review, ผู้รับผิดชอบ และขั้นทดสอบก่อน release; ไม่ใช้ไฟล์ handoff ที่ยังไม่ยืนยันรุ่นเป็นหลักฐานว่าตรงกับ production
- วิธีถอย: นำโค้ดทดลองออกจากสำเนาทดสอบ; ไม่มีการย้ายข้อมูลหรือปรับสิทธิ์จริงในขั้นทดลอง

## การตัดสินใจที่ต้องการ

System Owner อนุญาตให้พัฒนาต้นแบบและทดสอบการผูกคำขอกับ session **เฉพาะพื้นที่จำลอง** หรือไม่ และชุดส่งมอบ Formula Runtime ในเครื่องควรใช้เป็น baseline ทดสอบหรือมีรุ่นอื่น? การอนุญาตนี้ไม่รวมการเชื่อมฐานข้อมูลจริงหรือ deploy

## หลักฐานเพิ่มจากรุ่น GitHub ที่ตรวจ

`run-current-approval-e2e.py` ใช้ gateway commit `91d5fde5a17abf70d9ac5764b6b31529d69f913c`, PostgREST และ PostgreSQL ชั่วคราว กับบริการสิทธิ์จำลอง ในสถานการณ์กำหนดให้ role/session เปลี่ยนจาก Sales เป็น Admin หลังตัวตรวจฝั่งตัวเชื่อมแต่ก่อนส่ง คำขอถูกบันทึกในฐานข้อมูลจำลองแม้ตัวเชื่อมรายงานไม่ยืนยันผล กรณีตรวจว่ารอบเปลี่ยนก่อนเรียกตัวส่งไม่ส่งคำขอ ผลนี้ใช้ central user ID จำลองเดิมและผู้ส่งจำลอง ไม่ยืนยันการสลับบัญชีจริง คุกกี้ในเบราว์เซอร์ หรือระบบที่ deploy อยู่ การตัดสินใจและขอบเขตอนุมัติข้างต้นยังคงเดิม

## หลักฐานเพิ่ม: ผู้ใช้จำลองคนละรหัส

การทดสอบขยาย fake IAM ในสำเนาชั่วคราวให้รับรหัสผู้ใช้สมมติสองคน โดยไม่เปลี่ยน gateway จริงหรือสิทธิ์ production จากนั้นจัดให้ตัวส่งเปลี่ยน session ระหว่างตรวจฝั่งมือถือกับส่งคำขอ ผู้ใช้ใหม่ role Admin ได้รับอนุญาตและคำขอถูกเขียนใน PostgreSQL ชั่วคราว แม้ตัวเชื่อมรายงาน `session-changed-unconfirmed`; เมื่อผู้ใช้ใหม่เป็น RA คำขอถูกปฏิเสธและข้อมูลเดิมไม่เปลี่ยน ชุด `run-current-approval-e2e.py` ผ่าน 6/6 กรณี (รวมอนุมัติและ session)

เป็นการควบคุมตัวส่งและบริการ IAM จำลอง ไม่ใช่การสลับ session ผ่านเบราว์เซอร์จริงหรือหลักฐานว่าระบบที่ deploy มีปัญหา ยังต้องอนุมัติต้นแบบการแก้และยืนยัน baseline ก่อนเปลี่ยนระบบสิทธิ์หรือเชื่อม production

## หลักฐานเพิ่มจากคุกกี้ใน Chromium จำลอง

รัน `run-current-approval-e2e.py` ด้วย Chromium profile ใหม่และบัญชีสมมติสองคน ตัวทดสอบหยุดตัวส่งหลังตัวเชื่อมตรวจรอบ เปลี่ยนคุกกี้จาก Sales เป็น Admin อีกคนด้วยเครื่องมือควบคุมเบราว์เซอร์ แล้วปล่อยคำขอผ่าน relay เฉพาะ localhost ไป gateway, PostgREST และ PostgreSQL ชั่วคราว relay ตรวจว่าคุกกี้ที่เบราว์เซอร์ส่งระบุผู้ใช้สมมติคนใหม่ ตัวเชื่อมรายงาน `session-changed-unconfirmed` แต่ฐานข้อมูลจำลองเปลี่ยน ชุดรวมผ่าน 7/7

ข้อจำกัด: เป็นหน้า HTML ทดสอบที่โหลดตัวเชื่อมเดียวกันและควบคุมจังหวะด้วยเครื่องมือ ไม่ใช่การเดินหน้ามือถือจริงหรือสลับบัญชีผ่านหน้าล็อกอิน; IAM เป็นบริการสมมติ จึงไม่ยืนยันพฤติกรรมอุปกรณ์หรือ production การทดสอบรอบแรกไม่ผ่านเพราะตัวทดสอบอ่านรูปแบบผลตอบกลับเครื่องมือผิด แก้ตัวทดสอบและตรวจคุกกี้จริงแล้วจึงรันผ่าน ยังไม่ได้เปลี่ยนตัวกลางหรือ session binding
