# Formula Studio — หน้าทดลองมือถือ

เปิด `index.html` ด้วยเบราว์เซอร์ หรือรัน `python3 -m http.server 8767 --bind 127.0.0.1 --directory mobile-preview` จากโฟลเดอร์โครงการ แล้วเปิด `http://127.0.0.1:8767/`.

การทดสอบเชื่อมบางชุดต้องใช้ `_IT-handoff/formula-studio` และเครื่องมือในเครื่องแยกจากโฟลเดอร์นี้; ชุด gateway/PostgreSQL ปัจจุบันยังอ้าง commit จาก repository เดิมและ Docker images ที่มีอยู่แล้ว การคัดลอกโฟลเดอร์ตัวอย่างเพียงอย่างเดียวยังไม่ทำให้ทุกชุดทดสอบรันได้ ต้องกำหนดแหล่งอ้างอิงที่อนุมัติและขั้นตอนติดตั้งก่อนส่งงานให้ผู้ตรวจอื่น

เฉพาะชุด `integration/run-current-approval-e2e.py` สามารถใช้หน้าระบบเดิมจาก GitHub รุ่นคงที่แทนสำเนา `_IT-handoff` ได้ โดยรัน `FORMULA_TEST_PAGE_FROM_GITHUB=1 python3 mobile-preview/integration/run-current-approval-e2e.py` จากโฟลเดอร์โครงการ ต้องมีสิทธิ์อ่าน repository ที่ระบุผ่าน `gh`, Docker images ทดสอบที่เตรียมไว้, Node และ Chromium; ระบุ `FORMULA_BROWSER_TEST_CHROME` เมื่อจำเป็น ชุดนี้ตรวจ SHA-256 ของหน้าระบบและตัวกลางก่อนทดสอบ สร้างทรัพยากรชั่วคราวและใช้ข้อมูลสมมติ รุ่นคงที่นี้ยังไม่ได้รับการยืนยันว่าเป็นรุ่น production; ชุดทดสอบอื่นยังอาจต้องใช้ `_IT-handoff`

ตรวจหน้ามือถือในเบราว์เซอร์ 7 กรณีโดยไม่ต้องมี `_IT-handoff` ได้ด้วย `python3 mobile-preview/integration/run-portable-browser-tests.py`: ต้องมีสิทธิ์อ่าน repository เดิมผ่าน `gh`, Node และ Chromium; ระบุ `FORMULA_BROWSER_TEST_CHROME` หากเครื่องไม่พบ Chromium อัตโนมัติ ชุดนี้ดาวน์โหลดตัวช่วยทดสอบสองไฟล์จาก commit คงที่ ตรวจ SHA-256 แล้วใช้เฉพาะในโฟลเดอร์ชั่วคราว ก่อนลบทิ้งเมื่อจบ การผ่านชุดนี้ไม่ได้ยืนยันฐานข้อมูลจริงหรือทุก workflow

หน้าทดลองใช้ข้อมูลที่สร้างขึ้นเพื่อทดสอบเท่านั้น เก็บสถานะไว้ในหน่วยความจำของหน้าปัจจุบันและหายเมื่อรีโหลด ไม่เชื่อมบัญชี ฐานข้อมูล หรือส่งข้อความ/การแจ้งเตือนจริง นโยบายของหน้าไม่อนุญาตการเชื่อมเครือข่าย

เมื่อมีร่างหรือข้อมูลจำลองเปลี่ยนไป เบราว์เซอร์อาจแสดงคำเตือนก่อนรีโหลดหรือปิดหน้า การเตือนขึ้นอยู่กับเบราว์เซอร์และไม่รับประกันเมื่อระบบปิดแอป โดยไม่ได้ทำให้ข้อมูลอยู่ต่อหลังรีโหลด

เปิดเมนูซ้ายเพื่อเลือกบทบาทจำลองทั้ง 8 แบบ จากนั้นทดลองรายการงาน ฟอร์มแบบพับหัวข้อ รายละเอียด สูตร แชต การอนุมัติ ปิด/เปิดงาน และการแจ้งเตือนในหน้า สิทธิ์ที่แสดงเป็นตัวอย่างจากโค้ดเดิม ไม่ใช่หลักฐานว่าสิทธิ์ที่เซิร์ฟเวอร์ปลอดภัย

`integration/role-journey-native.test.mjs` ทดลองผ่านหน้าจอ Chrome ในเครื่อง: Sales สร้างงานสมมติ, PD เพิ่มสาร, ทั้ง 8 บทบาทส่งข้อความ, สี่ฝ่ายอนุมัติ และ Admin ปิด/เปิดงาน พร้อมตรวจปุ่มอนุมัติที่แต่ละบทบาทเห็น การทดสอบใช้โปรไฟล์เบราว์เซอร์ชั่วคราว ไม่ใช่การรับรองโดยผู้แทนบทบาทหรือการทดสอบสิทธิ์จริง

**ข้อจำกัดการถอนอนุมัติ:** ในหน้าทดลอง การถอนหนึ่งฝ่ายยังไม่ล้างฝ่ายอื่นหรือเปิดงานที่ปิดแล้ว ขณะที่สำเนาระบบเดิมที่ตรวจมีพฤติกรรมดังกล่าว จึงยังใช้ตัวอย่างรับรองขั้นตอนนี้ไม่ได้ รอเจ้าของงานยืนยันกติกาและรุ่นระบบเดิม

**บทบาทยังไม่ครบ:** สำเนาระบบเดิมที่ตรวจมี Oversea รวม 9 บทบาท แต่หน้าทดลองมี 8 บทบาท และสิทธิ์จำลองของ MKT ต่างจากสำเนานั้น กำลังรอเจ้าของระบบยืนยันก่อนปรับ การสลับบทบาทไม่ได้พิสูจน์สิทธิ์บัญชีจริง

**ยังไม่เทียบเท่าระบบจริง:** การตรวจ อย., PDF แบบเดียวกับระบบเดิม, ประวัติจริง, การจัดการผู้ใช้, การสร้างรหัสพร้อมกัน, การรับประกันการบันทึก, การซิงก์ และการแจ้งเตือนเมื่อปิดหน้า/ข้ามอุปกรณ์ ยังไม่ทำงานในหน้าทดลอง การคำนวณสารที่ได้จริงในตัวอย่างใช้ปริมาณ × ความเข้มข้นเท่านั้น ไม่ใช่การยืนยันสูตรหรือสถานะ อย. ฟอร์มและกติกาของบางส่วนเป็นแบบย่อ ต้องเทียบกับระบบเดิมและให้เจ้าของงานตรวจรับก่อนเชื่อมข้อมูลจริง

ตรวจเพิ่มด้วย `integration/preview-legacy-compat-native.test.mjs`: สร้างบรีฟและเพิ่มสารผ่านหน้ามือถือจำลองใน Chrome แล้วส่งข้อมูลที่ได้ให้ส่วนแสดงผลของชุดส่งมอบเดิมในเครื่อง พบว่ารายการขาด `allConcepts` และเมื่อเติมรายการว่างเพื่อแยกสาเหตุยังขาดข้อมูล อย. ที่ส่วนแสดงผลนั้นต้องใช้ ข้อมูล อย. ที่ใส่ในชุดทดสอบเป็นเพียงค่าปลอมเพื่อพิสูจน์จุดตรวจ ห้ามนำไปใช้เป็นผลตรวจจริง ต้องยืนยันรุ่นระบบและวิธีสร้างข้อมูลที่ถูกต้องก่อนเชื่อมระบบเดิม

การแก้คอนเซปยังไม่เทียบเท่าระบบเดิม: การทดลองก่อนหน้าแสดงว่าข้อมูลรายการคอนเซป สรรพคุณ และจุดขายเดิมอาจคงอยู่แม้ข้อความคอนเซปเปลี่ยน ตัวเชื่อมตัวอย่างจึงหยุดการเปลี่ยนคอนเซปของงานเดิมที่มี `allConcepts` หรือ `allSP` ก่อนส่ง และให้ตรวจในระบบเดิม งานตัวอย่างที่มีเพียงสรรพคุณซึ่งกรอกเองยังแก้ได้ การไม่มีช่องสองช่องนี้ไม่ได้ยืนยันว่าข้อมูลเข้ากันได้ ต้องกำหนดกติกาและแหล่งข้อมูลเดิมร่วมกันก่อนเชื่อม

`integration/legacy-purity-parity.test.cjs` ตรวจสูตรจากโค้ดสองสำเนาในเครื่องด้วย DOM สมมติ: น้ำหนัก 100 และความเข้มข้น 50% ได้ 50 เหมือนกัน แต่เมื่อความเข้มข้นเป็น 0 หรือว่าง ทั้งสองสำเนาระบบเดิมให้ 100 ขณะที่ตัวอย่างมือถือให้ 0 หรือยังไม่คำนวณตามลำดับ ต้องให้เจ้าของกระบวนการยืนยันกติกาก่อนเชื่อม ไม่ใช่ผลตรวจสูตรหรือสถานะ อย. และยังไม่ยืนยันรุ่นที่ใช้งานจริง

มีต้นแบบเฉพาะทดสอบ `integration/legacy-row-adapter.cjs`: `adaptLegacyRows(rows, derive)` รับแถวและตัวคำนวณที่ผู้ทดสอบจัดให้ ตรวจลำดับ ชื่อ ปริมาณ ผลคำนวณ และโครงสร้างข้อมูลประกอบ แล้วคงช่องอื่นของแถวเดิม ตัวต้นแบบไม่มีฐานข้อมูล อย. และไม่ได้ตรวจว่าตัวคำนวณหรือข้อมูลอ้างอิงได้รับอนุมัติ จึงห้ามใช้เขียนข้อมูลจริง ขอบเขตทดลองปฏิเสธความเข้มข้นว่างหรือน้อยกว่าหรือเท่ากับศูนย์ระหว่างรอกติกาที่เจ้าของงานยืนยัน ไม่ใช่ข้อสรุปทางธุรกิจ

ชุด `legacy-row-adapter.test.cjs` และ `runtime-job-save.gateway.test.cjs` ทดลองใช้ฟังก์ชันจากชุดส่งมอบกับข้อมูลอ้างอิงสมมติ ผ่านตัวกลางและบริการจำลอง แล้วไปถึงขั้นเพิ่มแถวในตัวแสดงผลเดิม รวมทั้งตรวจการคงช่องเพิ่มเติม ต้นแบบนี้ยังไม่ได้เชื่อมกับหน้ามือถือ ระบบยืนยันตัวตน หรือฐานข้อมูลจริง และยังไม่ยืนยันรุ่นที่ใช้งานอยู่ ผลสถานะในชุดทดสอบไม่ใช่ผลตรวจ อย.

ตัวอ่านทดลอง `integration/runtime-chat-read.cjs` รับรหัสงาน ตัวอ่านบริการ และตัวตรวจรุ่น session จากผู้เรียก; เรียก scoped chat history แล้วปฏิเสธข้อมูลที่ขาด ซ้ำ หรือเป็นของงานอื่น พร้อมไม่ส่งผลให้หน้าจอเมื่อรุ่น session เปลี่ยนก่อนหรือหลังอ่าน ผล `no-chat` ใช้เฉพาะเมื่อบริการตอบข้อมูลว่างทั้งห้องและข้อความ; ผล `unconfirmed` ไม่ได้หมายถึงไม่มีแชต ตัวอ่านไม่ได้ยืนยันตัวตน/สิทธิ์เอง ไม่ส่งข้อความ ไม่รวมอนุมัติ ไม่จัดเรียงข้อความ และยังไม่เชื่อมกับหน้ามือถือ

`runtime-chat-read.test.cjs` ตรวจข้อมูลสมมติผิดรูป/ข้ามงาน/ซ้ำ/บริการล้มเหลวและ session เปลี่ยน ส่วน `run-current-approval-e2e.py` ทดลองตัวอ่านนี้ผ่าน gateway และ PostgreSQL ชั่วคราวกับบัญชี Sales สมมติ รวมงานนอกขอบเขตและ session จำลองเปลี่ยนหลังอ่าน ชุดรวมผ่าน 17/17; ยังไม่พิสูจน์ login จริง สิทธิ์จริง การผูก session ที่ตัวกลาง หรือรุ่น production การตรวจ session ในหน้าเพียงอย่างเดียวไม่เพียงพอ

รองรับการตรวจพบประวัติรุ่นเก่าที่ฝังในข้อมูลห้อง: ถ้ามีเฉพาะข้อความฝังคืน `legacy-history` พร้อมข้อความเดิม; ถ้ามีข้อความทั้งฝังและตารางแยกคืน `requires-reconciliation` พร้อมข้อมูลทั้งสองชุด ไม่สรุปว่าชุดใดครบหรือรวมให้โดยอัตโนมัติ ทั้งยังปฏิเสธเมื่อรหัสงานหรือรหัสข้อความภายในขัดแย้งกับแถว ชุดทดสอบ gateway และ PostgreSQL ชั่วคราวล่าสุดผ่าน 18/18 โดยใช้ข้อมูลสมมติ ยังต้องกำหนดวิธีรวมและตรวจซ้ำกับระบบเดิมก่อนแสดงในแอปจริง

เพิ่มกรณีใน `integration/run-current-approval-e2e.py`: ใช้ตัวกลาง commit `91d5fde5a17abf70d9ac5764b6b31529d69f913c` และ PostgreSQL ชั่วคราวร่วมกัน ส่งบรีฟสมมติผ่านตัวแปลงและฟังก์ชันชุดส่งมอบที่ใช้รายการอ้างอิงปลอม อ่านฐานข้อมูลทดสอบกลับแล้วถึงจุดเพิ่มแถวของตัวแสดงผลเดิม; จากนั้นจำลองข้อมูลใหม่กว่าและตรวจว่าคำขอข้อมูลเก่าขัดแย้งโดยไม่เขียนทับ ชุดรวมผ่าน 10/10 การทดลองใช้ IAM ปลอม ตัวคำนวณจากชุดส่งมอบและตัวกลางคนละชุด จึงไม่ยืนยันว่า baseline ตรง production หรือว่าความเข้ากันได้ครบ

กรณีเพิ่มภายหลังเริ่มจากหน้าบรีฟมือถือจริงใน Chromium: เครื่องมือทดสอบใส่ข้อมูลสมมติลงหน้า ดักค่าขณะแก้สาร และแยกนำค่าดังกล่าวผ่านตัวแปลงและตัวกลางไป PostgreSQL ชั่วคราว อ่านกลับแล้วตรวจถึงจุดเพิ่มแถวในตัวแสดงผลเดิม ชุดรอบนั้นผ่าน 11/11 การส่งจากหน้าจอไปบริการถูกจำลองและดำเนินการต่อโดยเครื่องมือทดสอบ ไม่ใช่การเข้าสู่ระบบหรือการเชื่อมตัวแปลงจากหน้ามือถือจริง

ทดสอบเพิ่มสองสารผ่านตัวแปลงและตัวกลาง: หากตัวคำนวณจำลองคืนรายการสลับลำดับ ตัวแปลงปฏิเสธ; บทบาท RA จำลองส่งแล้วถูกปฏิเสธโดยข้อมูลไม่เปลี่ยน และ Admin จำลองบันทึกได้โดยค่ากับช่องเพิ่มเติมยังอยู่กับสารเดิม อ่านผลตรงจาก PostgreSQL ชั่วคราว ชุดรวมล่าสุดผ่าน 12/12 เป็นการตรวจในเงื่อนไขที่กำหนด ไม่ยืนยันสิทธิ์บัญชีจริงหรือการทำงานของมือถือที่เชื่อมบริการจริง

เพิ่มการอ่านผ่านตัวกลางและ PostgreSQL ชั่วคราว: งาน ห้องแชต และอนุมัติอ่านจากคนละรายการ บัญชี Sales สมมติอ่านทั้งสามรายการที่ทดสอบได้ ส่วนคำขออ่านงานที่ไม่มี session ถูกปฏิเสธ ชุดรอบนั้นผ่าน 13/13 กรณี หน้ามือถือยังไม่ได้ประกอบข้อมูลจากบริการเหล่านี้ และการอ่านหลายรายการแยกกันยังไม่ยืนยันว่าได้สถานะ ณ เวลาเดียวกัน สิทธิ์จริงต้องตรวจในระบบทดสอบที่ได้รับอนุญาต

กรณีเพิ่ม: อ่านงานที่ปิดแล้ว จากนั้นถอนอนุมัติผ่านตัวกลางจำลองซึ่งเปิดงานกลับ แล้วอ่านอนุมัติ พบว่าหากนำผลสองครั้งมารวมกันจะได้งานปิดจากเวลาก่อนกับอนุมัติว่างจากเวลาหลัง ชุดรอบนั้นผ่าน 14/14 โดยยืนยันความเสี่ยงนี้ ยังไม่ได้แก้ ต้องออกแบบการอ่านให้ตรวจความสอดคล้องก่อนแสดงหรือดำเนินการต่อ

ทดลองเปรียบเทียบด้วยคำสั่ง SQL เดียวใน PostgreSQL ชั่วคราว: เริ่มอ่านงานและอนุมัติ แล้วถอนอนุมัติผ่านตัวกลางระหว่างคำสั่งกำลังทำงาน ผลอ่านได้สถานะงานปิดและอนุมัติเดิมที่สอดคล้องกัน ส่วนการอ่านครั้งถัดไปได้งานเปิดและอนุมัติว่าง ชุดรวมล่าสุดผ่าน 15/15 เป็นการอ่านฐานทดสอบโดยตรง ไม่ใช่บริการอ่านผ่านตัวกลางที่มีสิทธิ์ครบ และไม่ได้รับประกันว่าข้อมูลไม่เปลี่ยนหลังอ่าน

ตรวจเพิ่มในชุดเดียวกันโดยนำแถวที่อ่านจาก PostgreSQL ชั่วคราวไปเรียกส่วนแสดงผลบนหน้าเว็บเดิมทั้งหน้าใน Chromium ที่ปิดการเชื่อมเครือข่าย ตรวจพบชื่อสาร ปริมาณ 120 และผล 60 ตามข้อมูลสมมติ การเปิดข้อมูลทำผ่านเครื่องมือทดสอบโดยตรง ไม่ใช่การล็อกอินหรือเปิดรายการตาม workflow จริง และข้อมูลสถานะเป็นค่าปลอม

หากปริมาณหรือความเข้มข้นว่างหรือไม่ใช่ตัวเลข หน้าทดลองแสดงว่า “ยังคำนวณไม่ได้” และช่องผลคำนวณใน Excel จะว่าง; ค่าศูนย์ที่กรอกจริงยังแสดงเป็นศูนย์ การบันทึกข้อมูลที่ไม่ใช่ตัวเลขจะถูกปฏิเสธ ส่วนข้อมูลที่ยังว่างบันทึกเป็นฉบับไม่สมบูรณ์ได้ กติกานี้เป็นข้อตกลงสำหรับตัวอย่างและต้องให้เจ้าของงานยืนยันก่อนใช้งานจริง

นำเข้า Excel `.xlsx` หรือ `.xls` งานเดียวและหลายงาน ส่งออก `.xlsx` งานเดียว และดาวน์โหลดแม่แบบทั้งสองแบบได้ในหน้านี้ ใช้ข้อมูลจำลองเท่านั้น ไฟล์ที่มีสูตรในเซลล์จะถูกปฏิเสธ ไฟล์งานเดียวที่มีแถวสารขาดชื่อ คอลัมน์สารซ้ำ หรือข้อมูลในคอลัมน์สารที่ไม่รองรับจะถูกปฏิเสธเพื่อให้แก้ไฟล์ก่อน ไฟล์หลายงานต้องมีรหัสต้นทางไม่ซ้ำและจับคู่สารได้ครบ พร้อมให้ตรวจรายการก่อนสร้าง; จำกัดไฟล์ 1 MB และครั้งละไม่เกิน 100 งาน; ถ้าชีตที่เกี่ยวข้องมีช่วงข้อมูลหรือรูปแบบถึงแถว 1003 เป็นต้นไป ตัวอย่างจะปฏิเสธไฟล์เพื่อไม่ให้ข้อมูลท้ายไฟล์หาย แม้บางแถวนั้นจะว่าง; ยังไม่ยืนยันความเข้ากันได้ครบทุกช่องกับระบบเดิม รายการที่มีจุลภาคจะมีข้อมูลเสริมสำหรับหน้าทดลองซึ่งระบบเดิมอาจไม่อ่าน

ตัวอ่าน Excel ฝัง SheetJS 0.20.3 ภายในหน้าเพื่อทำงานโดยไม่เชื่อมเครือข่าย รหัสต้นฉบับ [SheetJS](https://docs.sheetjs.com/docs/getting-started/installation/standalone/), สัญญาอนุญาตอยู่ใน `SHEETJS-LICENSE.txt` และ SHA-256 ของสคริปต์ต้นทางคือ `cc015130aa8521e7f088f88898eba949ccdcbfb38df0bd129b44b7273c3a6f41` การนำไปใช้จริงต้องผ่านการทบทวนความปลอดภัยและดูแลรุ่นของส่วนประกอบก่อน

ฟอร์มตัวอย่างเพิ่มตลาดปลายทางและประเทศ โดยอิงสำเนาระบบเดิม: เมื่อเลือกต่างประเทศต้องระบุประเทศ; ข้อมูลนี้นำเข้า/ส่งออก CSV และ Excel งานเดียวในตัวอย่างได้ และนำเข้า Excel หลายงานที่มีหัวคอลัมน์ตลาด/ประเทศได้ ไฟล์ Excel หลังอนุมัติในแชตตัวอย่างรวมสองช่องนี้แล้ว แต่ยังไม่ได้ยืนยันความเข้ากันได้กับระบบจริง

ในห้องแชตจำลอง Admin และ OPC สามารถเริ่มดาวน์โหลด Excel เมื่ออนุมัติจำลองครบ 4 ฝ่าย ไฟล์มีหัวคอลัมน์และลำดับตามสำเนาระบบเดิมที่ตรวจ รวมตลาด ประเทศและสารหลัก พร้อมชีตระบุว่าเป็นข้อมูลจำลอง ช่องประวัติที่ตัวอย่างไม่มีข้อมูลจะว่าง และสถานะอนุมัติระบุว่าเป็นการจำลอง สถานะ อย. แสดงว่ายังไม่ตรวจ ตัวนับบันทึกเพียงการเริ่มดาวน์โหลดในหน่วยความจำ ไม่ยืนยันว่าอุปกรณ์บันทึกไฟล์สำเร็จ

หน้ารายละเอียดงานมีหน้าพิมพ์ตัวอย่าง เลือกบันทึกเป็น PDF ได้หากอุปกรณ์รองรับ; เอกสารนี้ไม่ใช่ PDF แบบเดียวกับระบบเดิม และต้องทดสอบหน้าต่างพิมพ์บนอุปกรณ์จริง

ตรวจ Excel ด้วย `node mobile-preview/workbook.test.cjs` และตรวจแบบจำลองด้วย `node mobile-preview/test.cjs` จากโฟลเดอร์โครงการ และใช้ [แบบทดลองรายบทบาท](UAT_แบบทดลองตามบทบาท.md) เพื่อให้เจ้าของงานและผู้แทนบันทึกผลด้วยตนเอง

## ชุดจำลองแจ้งเตือนเมื่อไม่มีหน้าจอแอป

รัน `node mobile-preview/simulation/push.test.cjs` จากโฟลเดอร์โครงการ ชุดนี้จำลองตัวส่ง ผู้รับ และเหตุการณ์ให้โค้ด service worker โดยไม่มีหน้าต่างแอป ไม่มีเครือข่าย บัญชีจริง หรือ token จริง ตรวจการส่งซ้ำ การส่งพร้อมกัน ผู้รับที่ไม่มีสิทธิ์ อุปกรณ์ถูกถอนสิทธิ์ การไม่ใส่เนื้อหาลับบนหน้าจอล็อก และส่งใหม่หลังผิดพลาด

ผลทดสอบนี้ **ไม่ใช่** การทดสอบ push provider หรือป๊อปอัปจริงของระบบปฏิบัติการ โค้ด worker ยังไม่ได้ลงทะเบียนในหน้าทดลอง และไม่ได้รับหรือส่ง push จริง การทดสอบอุปกรณ์ปิดแอปต้องใช้บริการจำลองที่ส่งผ่านช่องทาง push ที่อุปกรณ์รองรับ บัญชี/สิทธิ์ทดสอบ และการอนุญาตแสดงแจ้งเตือนก่อน จึงจะยืนยันได้

สามารถดาวน์โหลดแม่แบบ CSV จำลอง ทดลองนำเข้า CSV รูปแบบ Formula Studio เพื่อกรอกฟอร์ม โดยไฟล์ที่มีข้อมูลในช่องไม่รองรับ หัวข้อซ้ำ หรือสารที่ไม่มีชื่อจะถูกปฏิเสธก่อนเปลี่ยนฟอร์ม และส่งออก CSV ของข้อมูลงานจำลองสำหรับ Admin/OPC; ยังไม่เทียบเท่าการนำเข้า/ส่งออก Excel และต้องตรวจความเข้ากันได้กับข้อมูลจริงภายหลัง. การส่งออกเพิ่มเครื่องหมายป้องกันค่าที่อาจถูกโปรแกรมตารางตีความเป็นสูตร จึงอาจแปลงค่าที่ขึ้นต้นด้วยอักขระเหล่านั้น CSV ที่ส่งออกเพิ่มช่องข้อมูลและสถานะสารสำคัญสำหรับนำกลับเข้าในหน้าจำลอง; ระบบเดิมอาจไม่อ่านส่วนที่เพิ่มและยังไม่ได้ยืนยันการนำกลับเข้าระบบเดิม ห้ามถือว่าข้อมูลส่งต่อครบถ้วน

`node mobile-preview/simulation/scenario.test.cjs` ตรวจการเชื่อมแบบจำลองระหว่างการเปลี่ยนงาน/ส่งแชตกับตัวส่งแจ้งเตือน รวมทั้งการห้ามผู้ส่งทำรายการที่ไม่มีสิทธิ์ การไม่แจ้งผู้ส่งหรือผู้ที่ไม่เห็นงาน การถอนอุปกรณ์ การส่งเหตุการณ์เดิมซ้ำ และการลองอีกครั้งเมื่อส่งไม่สำเร็จ ตัวตนและสิทธิ์ในชุดนี้เป็น fixtures ในหน่วยความจำ ไม่ใช่การยืนยันตัวตนจริงหรือการทดสอบสิทธิ์ฐานข้อมูล

## คิวแจ้งเตือนจำลองที่อยู่หลังเริ่มบริการใหม่

`node mobile-preview/simulation/durable.test.cjs` ใช้ SQLite ชั่วคราวที่เก็บเฉพาะข้อมูลจำลอง ตรวจการเริ่มโปรเซสใหม่ การไม่สร้าง/ส่งเหตุการณ์ซ้ำ การเปลี่ยนหรือถอนสิทธิ์ก่อนส่ง และสถานะไม่แน่ใจหลังขัดข้องระหว่างส่ง ตัวจำลองนี้ใช้ SQLite รุ่นทดลองใน Node และออกแบบสำหรับการทดสอบแบบโปรเซสเดียว; ไม่ใช่บริการ production หรือหลักฐานว่าส่งถึงแน่นอน

หากส่งออกไปแล้วแต่ไม่ทราบว่าบริการปลายทางรับหรือไม่ รายการจะเป็น `uncertain` และไม่ลองส่งซ้ำอัตโนมัติ เพื่อไม่อ้างว่าป้องกันซ้ำได้สมบูรณ์ ต้องมีแนวทางตรวจสอบและดำเนินการต่อก่อนใช้งานจริง

## บริการเข้าสู่ระบบจำลองในเครื่อง

`node mobile-preview/simulation/auth-http.test.cjs` เปิดบริการ HTTP แบบ local ที่ตรวจรหัสผ่านของบัญชีทดสอบและตรวจลายเซ็นของ session จริงในขอบเขตทดสอบ พร้อมเชื่อมคิวข้อมูลจำลอง ตรวจรหัสผ่านผิด การปลอม token/บทบาท งานนอกสิทธิ์ บัญชีถูกระงับ การออกจากระบบ และการเริ่มบริการใหม่ โดยไม่ติดต่อบริการบัญชีจริง

นี่คือบริการทดสอบที่สร้างขึ้นเฉพาะงาน ไม่ใช่ Supabase Auth และไม่ใช่ระบบยืนยันตัวตนที่อนุมัติให้ใช้จริง การผ่านชุดนี้ไม่ยืนยันสิทธิ์ของ Supabase หรือ PostgreSQL production

## ตรวจความเข้ากันได้กับสำเนาฐานข้อมูลเดิมในเครื่อง

รัน `sh mobile-preview/simulation/legacy-compat.test.sh` เพื่อสร้าง PostgreSQL ชั่วคราว ใช้ `tests/sql/bootstrap.sql` และ `supabase/schema.sql` ในสำเนา repository พร้อมบัญชีและงานสมมติ แล้วลบฐานข้อมูลชั่วคราวเมื่อเสร็จ ชุดตรวจสร้าง/แก้ตามบทบาททั้ง 8, การบันทึกจากข้อมูลเก่า, การส่งเหตุการณ์ซ้ำ และการอ่านงานของ Sales รายอื่นโดยตรง

ณ ผลตรวจครั้งนี้คำสั่ง **ตั้งใจออกด้วยสถานะไม่ผ่าน** เมื่อพบว่าเขียนข้อมูลเก่าทับข้อมูลใหม่ได้, การใช้รหัสเหตุการณ์เดิมกับข้อความต่างกันคืนเหตุการณ์เดิม, Sales อ่านงานคนอื่นผ่านฐานข้อมูลได้ และเมื่อจำลองให้ Sales/OPC/MKT แก้งานแล้วส่งเหตุการณ์ล้างอนุมัติ บริการปฏิเสธเหตุการณ์นั้น ข้อสุดท้ายต้องให้เจ้าของงานยืนยันสิทธิ์ ส่วนการทดลอง SQL ที่ตรวจค่าก่อนแก้ปฏิเสธข้อมูลเก่าได้ในกรณีจำลอง แต่ยังไม่ใช่ API ของแอปหรือการเชื่อม Supabase ผลนี้ไม่ใช่หลักฐานของ schema, สิทธิ์ หรือข้อมูลใน production

`sh mobile-preview/simulation/concurrency-guard.test.sh` ทดลอง SQL แบบตรวจข้อมูลเดิมด้วยการเชื่อมต่อสองทางที่ทำงานซ้อนกันจริงบน PostgreSQL ชั่วคราว รวมทั้งจำลองการแก้งานและล้างการอนุมัติในธุรกรรมเดียวกัน หากขั้นตอนใดผิดพลาดจะย้อนกลับทั้งคู่ การทดลองนี้ยังไม่สร้าง API หรือ migration และไม่ได้แปลว่า API ปัจจุบันรองรับวิธีนี้ ผลไม่ยืนยันสิทธิ์จริงหรือการใช้งานจริง

## เตรียมการบันทึกผ่าน Formula Runtime จากชุดส่งมอบ

ชุดส่งมอบ `_IT-handoff/formula-studio` ระบุว่าระบบเดิมประกอบด้วยหน้าเว็บ, ตัวกลาง และ PostgreSQL โดยมีฟังก์ชัน `fs_save_record` ตรวจข้อมูลตั้งต้นก่อนบันทึก ผลตรวจ `legacy-compat.test.sh` ข้างต้นใช้ schema Supabase อีกชุดหนึ่งโดยตรง จึงไม่เพียงพอจะสรุปพฤติกรรมตัวกลาง Formula Runtime หรือระบบที่ใช้งานจริง ต้องยืนยันรุ่นและโครงสร้างที่ใช้งานก่อนเลือกช่องทางเชื่อม

`integration/runtime-job-save.js` เป็นตัวเชื่อมที่หน้าฟอร์มแก้ไขใช้ผ่านตัวจำลองในเครื่องเท่านั้น ยังไม่ต่อกับเครือข่าย สร้างคำขอ `p_id`, `p_data`, `p_expected` จากข้อมูลตั้งต้นที่ผู้เรียกต้องยืนยันเอง คงข้อมูลเดิมที่ฟอร์มไม่ได้แก้ และตรวจคำตอบก่อนแสดงว่าบันทึกสำเร็จ สถานะรอคิว ขัดแย้ง หรือไม่แน่ใจไม่ถือว่าบันทึกแล้ว ส่วนการยืนยันตัวตน/สิทธิ์เป็นหน้าที่ตัวกลางเดิม ไม่ใช่โค้ดนี้ ห้ามใช้เรียกฐานข้อมูลโดยตรง

ทดสอบด้วย `node mobile-preview/integration/runtime-job-save.test.cjs` และ `node mobile-preview/integration/runtime-job-save.pg.test.cjs` ชุดหลังใช้ PostgreSQL ชั่วคราวกับ SQL จากชุดส่งมอบและข้อมูลสมมติ โดยข้ามตัวกลาง จึงไม่ได้ทดสอบ session, สิทธิ์, การเชื่อม UI หรือการ deploy ข้อมูลตั้งต้นต้องมาจากการอ่านที่ยืนยันแล้ว; ยังต้องออกแบบการเก็บร่าง การรับผลรอคิว การสร้างรหัส และการจัดการอนุมัติก่อนนำไปใช้จริง

ผลตรวจชุดส่งมอบในเครื่องรอบนี้: `node --test tests/job-sync-sql.test.mjs tests/job-integrity-gateway.test.mjs` ผ่าน 54 กรณี และ `node --test tests/job-sync-client.test.mjs tests/job-sync-bootstrap.test.mjs tests/job-sync-gateway.test.mjs` ผ่าน 396 กรณี (รันจาก `_IT-handoff/formula-studio`) ชุดเหล่านี้ทดสอบด้วยบริการ/ข้อมูลจำลองของชุดส่งมอบ ไม่ยืนยันว่ารุ่นเดียวกันถูกติดตั้งจริงหรือว่าตัวเชื่อมมือถือผ่าน gateway แล้ว

`node mobile-preview/integration/runtime-job-save.gateway.test.cjs` นำตัวเชื่อมมือถือไปผ่านกระบวนการ `formula-proxy.mjs` จากชุดส่งมอบจริงในเครื่อง โดยใช้บริการ IAM, ฐานข้อมูล, session และรหัสทั้งหมดเป็นข้อมูลจำลองใน localhost ตรวจบันทึก/ข้อมูลเก่าขัดแย้ง, บทบาทที่ถูกปฏิเสธ, รอคิวเมื่อฐานข้อมูลไม่พร้อม และการกู้เมื่อคำตอบสูญหาย ชุดนี้ใช้ upstream จำลอง ไม่ได้ทดสอบ gateway ร่วมกับ PostgreSQL จริงหรือบัญชีจริง

ในฟอร์มสร้างบรีฟ แก้บรีฟ หรือแก้สูตร เลือกหัวข้อ “ทดลองผลการบันทึก” เพื่อจำลองสำเร็จ รอคิว ขัดแย้ง ไม่มีสิทธิ์ ระบบไม่พร้อม หรือไม่ทราบผล ทุกกรณีที่ไม่สำเร็จคงข้อมูลที่กำลังกรอกไว้ในฟอร์มขณะเปิดหน้าเท่านั้น ไม่มีคิวจริงและข้อมูลหายเมื่อรีโหลด การนำเข้าแบบหลายงานยังไม่ได้ใช้ตัวจำลองสถานะนี้; รหัสงานสำหรับสร้างรายการในหน้านี้เป็นรหัสจำลองในหน่วยความจำ ไม่ใช่การจองรหัสจากระบบเดิม ทดสอบแบบจำลองและความตรงของโค้ดในหน้าได้ด้วย `node mobile-preview/integration/ui-save-simulation.test.cjs`

ตัวเชื่อมมี `reconcileSave` สำหรับตรวจอ่านรายการผ่านตัวกลางหลังตอบรอคิวหรือไม่ทราบผล: หากข้อมูลที่อ่านตรงทั้งหมดจะรายงานเฉพาะว่า “ข้อมูลรายการตรง” หากไม่ตรงยังถือว่ารอหรือไม่ทราบผล ไม่สั่งบันทึกซ้ำ และไม่ยืนยันสถานะอนุมัติ/ประวัติ ผู้เรียกต้องตรวจว่าเป็นรุ่น session เดิมตลอดคำขอ รวมกรณีสลับออกแล้วกลับเข้าบัญชีเดิม; ฟังก์ชันนี้ยังไม่ได้เชื่อมกับหน้าจอหรือร่างถาวร ผลทดสอบ gateway ใช้ upstream จำลองที่เพิ่มข้อมูลแบ่งหน้าให้เหมือนสัญญาที่ gateway ต้องการ

ข้อจำกัดเพิ่มเติมจาก gateway ชุดส่งมอบในเครื่อง: เมื่อส่งคำขอสร้างรหัสเดียวกันด้วยข้อมูลต่างกันขณะฐานข้อมูลจำลองไม่พร้อม ตัวกลางจำลองหยุดทั้งสองคำขอเป็นข้อมูลขัดแย้งและไม่เขียน ส่วน `reconcileSave` อ่านเฉพาะรายการงาน จึงคืน `pending` ทั้งสองคำขอแม้คิวหยุดแล้ว คำนี้หมายถึงยังยืนยันข้อมูลไม่ได้ ไม่ใช่หลักฐานว่าคิวยังทำงานหรือควรกดส่งซ้ำ ต้องออกแบบวิธีตรวจผลคำขอที่ได้รับอนุญาตก่อนเชื่อมระบบจริง

การตรวจ session ใน `submitSave` ต้องมีตัวตรวจรอบ session จากผู้เรียก ถ้ารอบเปลี่ยนก่อนส่งจะไม่เรียกตัวส่ง; ถ้าเปลี่ยนหลังเริ่มส่งจะแสดง `session-changed-unconfirmed` เพราะคำขออาจไปถึงบริการแล้ว ไม่ใช่การยืนยันว่าคำขอถูกยกเลิก ชุด `runtime-job-save.gateway.test.cjs` สร้างสถานการณ์ให้ session เปลี่ยนก่อนคำขอถึงตัวกลางและพบว่าตัวกลางจำลองอาจรับคำขอในนาม session ใหม่ได้ ดังนั้นการตรวจฝั่งหน้าจอเพียงอย่างเดียวไม่เพียงพอ ตัวเชื่อมนี้ห้ามใช้กับระบบจริงจนกว่าจะมีมาตรการฝั่งบริการ ตรวจความเข้ากันได้ของรูปแบบสารและข้อมูล อย. กับระบบเดิม และตรวจครบตาม governance ดู `integration/SESSION_BOUNDARY_PROPOSAL.md`
